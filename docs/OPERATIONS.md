# RYFT — operations

How to deploy, where the secrets come from, what the network policy allows, and how to
back up and restore. Manifests are kustomize-only and applied by hand.

```text
deploy/k8s/
  base/<service>/          namespace-neutral manifests per workload (ingest, scoring, api,
                           notify, migrate, smoke, web) and base/common (default-deny + DNS)
  services/<service>/      puts one workload into its namespace ryft-<service>
  overlays/eks/            the five namespaces on EKS: Traefik + Let's Encrypt, gp3-encrypted,
                           pinned images; no Secrets, no Namespace objects (infra/vault owns them)
  overlays/vault-namespaces/<service>/   generated by infra/vault: the operator objects that
                           sync Secret ryft-secrets from the service's own Vault namespace
  overlays/local-postgres/ self-hosted: the same five namespaces plus ryft-postgres, API-key
                           auth, one RabbitMQ node, Secrets from scripts/local-secrets.sh
deploy/rabbitmq/           the broker (RabbitMQ section below): operators/, cluster/,
                           topology/ (generated), clients/ (the services' certificates)
```

Render without applying: `kubectl kustomize deploy/k8s/overlays/eks`. Validate everything
offline: `make k8s-validate` (needs `kubeconform`).

## Namespaces and identities

Each workload runs in its own namespace, under its own service account, with its own
credentials and nothing else ([`ARCHITECTURE.md`](ARCHITECTURE.md#namespaces-and-trust)):

| Namespace | Workload | Vault namespace (HCP) | Holds |
| --- | --- | --- | --- |
| `ryft-ingest` | Deployment `ingest` | `admin/ryft/ingest` | DB role `ryft_ingest`, RabbitMQ user `ingest`, project ref |
| `ryft-scoring` | Deployment `scoring` | `admin/ryft/scoring` | DB role `ryft_scoring`, RabbitMQ user `scoring` |
| `ryft-api` | Deployment `api` | `admin/ryft/api` | DB role `ryft_api`, RabbitMQ user `api`, project ref, Supabase secret key, `ADMIN_API_KEY` |
| `ryft-notify` | Deployment `notify` | `admin/ryft/notify` | DB role `ryft_notify`, RabbitMQ user `notify`, the APNs key (once there is one) |
| `ryft-rabbitmq` | RabbitmqCluster `rabbitmq` (three pods) | `admin/ryft/rabbitmq` | the four users' passwords (Secrets `amqp-user-<service>`, for the Topology Operator) |
| `ryft-smoke` | Job `smoke` (Argo CD's PostSync hook) | `admin/ryft/smoke` | the smoke user's sign-in |
| `ryft-migrate` | Job `migrate` | `admin/ryft/migrate` | the database owner, the four role passwords |

On EKS `infra/vault` creates the namespaces (Pod Security `restricted`), the service
accounts, the Vault side and the operator manifests; the overlay only deploys workloads.

## EKS (api.ryftapp.de)

The AWS side is Terraform in three roots, then Vault in a fourth, each applied by hand
in order. Details, cost and teardown: [`infra/aws/README.md`](../infra/aws/README.md) and
[`infra/vault/README.md`](../infra/vault/README.md).

| Step | Command | Done when |
| --- | --- | --- |

| 5. Supabase | the checklist in [`SUPABASE.md`](SUPABASE.md) | project ref, pooler host, database password, secret key at hand |

| 8. App | Argo CD from step 4; `kubectl apply -f deploy/argocd/project.yaml -f deploy/argocd/root.yaml` | **Deploy and roll back** → Cutover to Argo CD |
| 9. Metrics | rotate the Grafana Cloud token, put it into `infra/vault`, `make monitoring-apply` | see **Monitoring** below |

Every Terraform root keeps its state in its HCP Terraform workspace (execution mode
Local): `terraform init` in a fresh checkout connects to it after `terraform login`.

Argo CD deploys the app (step 8; **Deploy and roll back**). Its waves keep the order
the break-glass `make k8s-apply-eks` enforces by hand, which runs these steps, waiting
at each one:

0. It checks that kubectl is logged in (`k8s-check-auth`): kubectl takes its EKS
   token from `aws eks get-token`, so expired AWS credentials fail every call with
   "the server has asked for the client to provide credentials". Refresh them and
   check with `aws sts get-caller-identity`.
1. It applies the operator objects for every namespace and waits until each
   `ryft-secrets` (and in `ryft-rabbitmq` each `amqp-user-<service>`) exists; it stops
   at the first one that fails.
2. RabbitMQ (`make k8s-rabbitmq`): the operators, then `deploy/rabbitmq`, and waits until
   all three nodes are ready.
3. It deletes the finished migrate Job, since a Job's pod template is immutable, applies
   the first stage, the migrate Job (label `ryft.dev/stage=first`), and waits for it.
4. Only then it applies everything, so the services start after their role passwords
   exist, and waits for the four rollouts.

A new service (notify, M7) needs `infra/vault` applied first: that creates its
namespace, service account and secrets, writes its operator manifests to
`deploy/k8s/overlays/vault-namespaces/notify`, and gives the broker's namespace its
RabbitMQ password (a new user also needs its `User`, permissions and certificate in
`amqpbus/topology.go` and `deploy/rabbitmq/clients`). Without it the `vault-notify`
application cannot render (and `make k8s-apply-eks` stops at the missing directory).

**After an `infra/vault` apply that adds keys, let the operator sync before the
deploy.** It re-reads Vault only hourly, so the Kubernetes Secrets lag behind Vault
(2026-10-19, NATS then: it crash-looped on a password its Secret did not have yet):

```bash
kubectl -n vault-secrets-operator-system rollout restart deploy vault-secrets-operator-controller-manager
```

Order matters because Supabase's pooler blocks a database user for a while after
repeated failed logins (`ECIRCUITBREAKER`). Starting the services next to migrate on
the first deploy cost a few minutes of crash loops. The services now also retry the
database and RabbitMQ with backoff (5 s doubling to 60 s, jittered) instead of exiting,
and wait up to 10 minutes (startup probe).

```bash
make k8s-validate && make k8s-apply-eks
kubectl -n ryft-migrate logs job/migrate                     # "role password set" ×4, "schema current"
for s in ingest scoring api notify migrate; do kubectl -n ryft-$s get vaultstaticsecret,secret ryft-secrets; done
kubectl -n ryft-rabbitmq get vaultstaticsecret,secret,rabbitmqcluster          # amqp-user-*, ALLREPLICASREADY
kubectl -n ryft-api get ingress,certificate                  # certificate READY True (DNS-01, ~1–2 min)
kubectl -n ryft-ingest get ingress,certificate
dig +short api.ryftapp.de                                    # NLB addresses (ExternalDNS, from the api Ingress)
curl -sI https://api.ryftapp.de/v1/me                        # 401 without a token
```

If a pod is stuck in `CreateContainerConfigError`, its namespace has no `ryft-secrets`
yet. `kubectl -n ryft-<svc> describe vaultstaticsecret ryft-secrets` shows why: usually
the Vault login. Check it by hand with `terraform -chdir=infra/vault output login_check`.
Kubernetes auth needs HCP Vault to reach the EKS API (TokenReview), so
`endpoint_public_access_cidrs` must admit Vault's egress addresses.

The public host only routes `/v1/*`; `/healthz`, `/readyz` and `/metrics` stay internal.
Port 80 is not exposed at all, so clients must use `https://`.

**Production smoke test.** `make smoke-supabase` runs against the public host with the
real project. It never touches real accounts:

```bash
SUPABASE_URL=https://<ref>.supabase.co SUPABASE_ANON_KEY=<publishable key> \
SMOKE_EMAIL=<test user> SMOKE_PASSWORD=<…> SUPABASE_SECRET_KEY=sb_secret_… \
API_URL=https://api.ryftapp.de INGEST_URL=https://api.ryftapp.de make smoke-supabase
```

1. **Contract checks:** it signs in the dedicated test user (`SUPABASE.md` checklist)
   and runs the full contract checks with 10 synthetic days in that account.
2. **Account flows** (`scripts/check_accounts.py`, needs `SUPABASE_SECRET_KEY`): it
   creates two throwaway, confirmed users through the Supabase admin API and signs them
   in. It checks that `/v1/me` creates the row, that one user's sync stays invisible to
   the other, and the `apple-authorization` endpoint. It then deletes both through
   `DELETE /v1/me` and checks the tokens get `401` and the Supabase sign-ins are gone.
   It cleans up even when a check fails.

The email-confirmation link itself is tested by hand from the app. Don't run plain
`make smoke` against the public host: it is for apikey mode.

**Rescoring** after a scoring rule or constant changed (`SCORING.md`):
`scripts/rescore_all.sh [days]` (default 400) runs `scoring rescore` inside the scoring
pod. Each user's last *days* days are rescored, oldest first, with scoring's own role;
the log shows `user rescored … n of N`, then `rescore done`. Locally:
`RESCORE_LOCAL=1 scripts/rescore_all.sh 30`.

Days scored before their history (a backfill newest first, a late sample) need no
rescore by hand: scoring re-scores the days after a changed day itself, a retried
event included (log `rescored days after a history change`), and its 15-minute pass
picks up about 50 days a pass whose `baseline_days` (or one of its two counts) is
behind their stored history or whose baseline is missing (log `rescored days behind
their history`;
`ryft_days_rescored_total`, `OBSERVABILITY.md`). A user whose re-score there failed is
left until their next local day (the error is logged). Only users who synced in the
last 48 hours get the pass; the others get it with their next sync, or now with
`POST /v1/recompute` or `scripts/rescore_all.sh`. A scoring letter replayed from
`dlq.scoring` arrives as a first delivery: follow it with a `POST /v1/recompute` of its
days if late data was involved.

**Learned sleep baseline** (`SCORING.md` → Sleep): scoring estimates it every Sunday from
04:00 local on its own. To run it for every user now (after a deploy, or after changing
its rules): `kubectl -n ryft-scoring exec deploy/scoring -- /app learn-baselines`
(locally `podman compose exec -T scoring /app learn-baselines`). The log ends with
`learn-baselines done` and the counts `applied` (the baseline moved; that user's last
7 days were rescored), `kept`, `insufficient` and `failed`. Users who set their baseline
by hand keep it.

Certificates: cert-manager renews 30 days before expiry. Each Ingress has its own
certificate for the same host, because a Secret cannot be shared across namespaces. To
try issuance without touching Let's Encrypt's production rate limits, point both
Ingress annotations at `letsencrypt-staging` first.

**Rotation.** The operator re-reads each namespace's `kv/config` hourly and restarts
the workload on a change.

- **Supabase secret key:** create a new one in Supabase, put it in `terraform.tfvars`,
  run `terraform apply`, then revoke the old one.
- **RabbitMQ password:** `terraform apply -replace='random_password.amqp["api"]'`. The
  operator updates both sides within the hour (OPERATIONS → RabbitMQ → Credentials);
  to skip the wait, restart the Vault Secrets Operator.
- **Database role password:** Postgres must get the new password before the service
  does, or its new pods fail their logins and may trip the pooler's circuit breaker.
  So force the order instead of waiting for the hourly refresh (here for `api`):

  ```bash
  terraform -chdir=infra/vault apply -replace='random_password.db["api"]'
  kubectl -n ryft-migrate delete secret ryft-secrets      # the operator re-creates it from Vault
  kubectl -n ryft-migrate wait --for=create secret/ryft-secrets --timeout=2m
  kubectl -n ryft-migrate delete job migrate --ignore-not-found
  kubectl apply -k deploy/k8s/overlays/eks -l ryft.dev/stage=first
  kubectl -n ryft-migrate wait --for=condition=complete job/migrate --timeout=10m   # Postgres has the new password
  kubectl -n ryft-api delete secret ryft-secrets          # re-created; the operator restarts the Deployment
  kubectl -n ryft-api rollout status deploy/api
  ```

  Open connections survive a password change, so the old pods keep serving until the new
  ones are ready. If a `wait --for=create` times out, the operator did not re-create the
  Secret at once; it does at the next hourly refresh at the latest
  (`kubectl -n ryft-<svc> describe vaultstaticsecret ryft-secrets`).

## Deploy and roll back

Git is the only way anything reaches `ryft-prod-euc1` (D94–D96). Argo CD syncs the
applications in `deploy/argocd/apps`; CI promotes images by a PR that pins
`deploy/k8s/overlays/eks`. Nobody runs `kubectl apply` against production, except
break-glass below.

**How a change reaches production:**

1. **Merge to main** (or push, as admin). CI runs every check, then builds an image for
   each **group** whose directory differs from its running pin in
   `deploy/k8s/overlays/eks` (D107): **services** (ingest, scoring, api, notify, migrate)
   from `backend/`, **web** (the apex site) from `web/`. Tags are
   `ghcr.io/timkrebs/ryft/<image>:<the commit's first 7 characters>`.
2. **promote** opens one PR "deploy: images <sha>" that pins the groups it built, each
   with its old pin and its commits since, and closes every older open `deploy/*` PR as
   superseded. It runs only when every group it needs was built: if one image job failed,
   nothing is pinned (fix the cause, then "Re-run failed jobs" on the **latest** run on
   main). The PR merges itself once its checks pass (`manifests` also asks ghcr.io for
   every pinned image). Close it to stop the deploy and `hold.sh add` the group (a closed
   deploy PR with the group still different from its pin makes the deploy watch fail every
   day). A change to manifests only (no new
   image) deploys on its own merge. The job runs in the GitHub environment `deploy`
   (below) and signs with the deploy App's key from there.
3. **Argo CD syncs.** It picks a merge up within two to six minutes (the repository is
   polled and cached; the rollback drill saw 2:20 and 6:08); a release, from the merge of the change to the new pods, takes about 15
   minutes, because the images are built and the deploy PR passes its checks first. Waves
   order the applications: wave 0 the Vault objects, wave 1 the RabbitMQ operators, wave 2
   the broker, wave 3 `ryft-platform`. Inside `ryft-platform` there are no sync waves
   (the services roll together, in no set order); only the hooks are ordered: **migrate
   first** (PreSync: a failed migration fails the sync and nothing rolls), the apply,
   wait until everything is healthy, **the smoke last** (PostSync, `ryft-smoke`: every
   `/readyz`, the smoke user's sign-in, one sync, the day rescored within 90 s).
4. **Watch:** `kubectl -n argocd get applications`, the UI, or the alerts
   (`ArgoSyncFailed`, `ArgoAppDegraded`, `ArgoAppOutOfSync`). From outside, `make
   smoke-prod` still checks the edge and probes the gates. After a model bump,
   `scripts/rescore_all.sh`. Once a day the deploy watch (below) looks for a deploy that
   did not happen.

**What Argo CD may no longer do** (T12-f, D120). Its ClusterRoles are written in
`infra/aws/kubernetes/argocd.tf` (the chart's defaults give the controller `*` and the
server delete/get/patch on everything), so a compromised Argo CD, or a commit to
`deploy/argocd`, cannot switch off the admission layer. Each rule has a reason; a kind
that is not listed is refused with `forbidden` in the sync:

| Who | Rule | Why |
| --- | --- | --- |
| controller | get, list, watch, create, update, patch, delete on configmaps, services, serviceaccounts, Deployments, HPAs, Jobs, Ingresses, NetworkPolicies, PDBs, Traefik Middlewares and ServersTransports, cert-manager Certificates and Issuers, the Vault Secrets Operator's VaultAuth, VaultConnection and VaultStaticSecret, the nine `rabbitmq.com` kinds | What `kustomize build` of the paths in `deploy/argocd/apps` renders. Jobs: the PreSync migrate and PostSync smoke hooks (created, and deleted by `BeforeHookCreation`). Server-side apply and the server-side diff need `patch` |
| controller | get, list, watch on pods, ReplicaSets, StatefulSets | The resource tree (read only) |
| controller | get, list, watch, create, update, patch on namespaces and CustomResourceDefinitions; no `delete` | Namespace `ryft-web`, `rabbitmq-system`, the operators' 14 CRDs (project `ryft-operators`). Deleting either removes everything in it, the broker's data included, so pruning one is an admin's act |
| controller | all verbs on ClusterRoles, ClusterRoleBindings, Roles, RoleBindings | The operators' app (`deploy/rabbitmq/operators`) |
| controller | `escalate` on the five operator ClusterRoles and the two leader-election Roles; `bind` on the three bound ClusterRoles and the two Roles, all by `resourceNames` | Kubernetes only lets you write or bind a role whose permissions you hold. The cluster operator's role has `pods/exec`, which Argo CD must not hold. By name, so Argo CD cannot create a new powerful role |
| controller | get, list, watch, create on the two webhook-configuration resources; update, patch, delete only on the four operator-owned names | The operators' two Mutating and two ValidatingWebhookConfigurations. Never `ValidatingAdmissionPolicy` or `-Binding` |
| controller | nothing on `secrets` in the cluster, `pods/exec`, `pods/ephemeralcontainers`, non-resource URLs | No Secret is in git (VSO makes them). Its own Secrets in `argocd` come from the namespaced Role |
| server | get on the same kinds (and pods/log), list and create events, get/list/update/watch Applications | The UI's live manifests and logs. Nothing on `admissionregistration.k8s.io`, no secrets |
| server | delete pods and Jobs, patch Deployments and StatefulSets | The UI's actions (delete a pod, restart a Deployment); nothing else is written |
| both | `resource.respectRBAC: strict`; `exec.enabled: false` | The controller then skips resource types it may not list instead of failing on them; no terminal in the UI |
| ApplicationSet | controller at 0 replicas (this chart version has no enabled flag) | Applications are the files in `deploy/argocd/apps` |

The namespaced Roles in `argocd` stay the chart's (Secrets and ConfigMaps there are
Argo CD's own state: the admin account, repository credentials, `argocd-cm`).

What an operator does instead:

- **A shell in a pod, or an ephemeral debug container:** the cluster admin's job (your own
  AWS identity and `kubectl exec` / `kubectl debug`). The Argo CD UI has no terminal.
- **Read a Secret:** `kubectl get secret` as admin; Argo CD cannot show it.
- **Delete a namespace or a CRD:** `kubectl delete` as admin, after the commit that removes
  it from git; the sync reports it as an orphan to prune and stays OutOfSync until then.
- **Anything on admission policies:** only `terraform apply` (`infra/aws/kubernetes`).
- **A new kind in a path of `deploy/argocd/apps`:** add its rule to `argocd.tf` and apply
  that first (Terraform plan: only `helm_release.argocd`), then merge the manifests;
  otherwise the sync fails with `forbidden` on that kind.
- **Where it shows:** `argocd app get <app>` names the refused kind. A controller log line
  `Failed to ... forbidden` or a sync condition `ComparisonError` means a rule is missing.
- **Roll back the narrowing:** revert the commit and apply `infra/aws/kubernetes`; the chart
  returns to its defaults. (Only then, if an urgent sync is blocked.)

**Pause** (a deploy must not happen now, or break-glass): the root re-applies every
Application from git, so pause it first, then the one application:

```bash
argocd app set ryft-root --sync-policy none
argocd app set ryft-platform --sync-policy none
# resume: argocd app set ryft-root --sync-policy automated --self-heal --auto-prune
#         (the root then restores ryft-platform's policy from git)
```

**A failed sync:** `argocd app get ryft-platform` names the operation's failing step.
PreSync: `kubectl -n ryft-migrate logs job/migrate`; a refused apply: the object's
message; PostSync: `kubectl -n ryft-smoke logs job/smoke` (the step and the user it
failed for). Argo CD retries a failed sync twice (1 and 2 minutes later); after that it
waits for the next commit, or `argocd app sync ryft-platform`. The release itself is in
when only the smoke failed: decide between a fix and a rollback.

**A migration that hits the lock timeout.** The migrator sets `lock_timeout` to 5 s in
every migration's transaction (`internal/db`, `lockTimeout`; a migration may set its own
`SET LOCAL`, which wins; 0027 does, also 5 s). A migration that cannot get its lock in
that time fails with `apply 00NN_name.sql: hit the lock timeout ...` (SQLSTATE 55P03).
Its transaction rolls back: `schema_migrations` and the schema stay as they were, the
earlier migrations of the run stay applied. The migrate Job exits 1 (the Job retries up
to its `backoffLimit`, with the same outcome while the blocker lives), the PreSync hook
fails, the sync fails before anything rolls and Argo CD retries it twice; the running
pods are untouched and keep serving. The wait for the migration lock itself (a second
migrator, e.g. an overlapping sync) is not cut by this timeout; it ends with the Job's
10 minute context. The services never migrate, they only wait for the schema
(`WaitMigrated`). `statement_timeout` is not set: a migration that runs long (a backfill)
is not killed, but it holds its locks while it runs.

Find the blocker (as the database owner, in the Supabase SQL editor or `psql`):

```sql
-- sessions holding or waiting for locks on the table the migration names
SELECT a.pid, a.state, a.xact_start, now() - a.xact_start AS open_for, a.wait_event_type,
       l.mode, l.granted, left(a.query, 120) AS query
FROM pg_locks l JOIN pg_stat_activity a USING (pid)
WHERE l.relation = 'public.daily_scores'::regclass       -- the migration's table
ORDER BY a.xact_start;
-- long-open transactions (the migrator has given up by now, so nobody is blocked any more)
SELECT pid, backend_type, state, wait_event, xact_start, now() - xact_start AS open_for,
       left(query, 100) AS query
FROM pg_stat_activity
WHERE xact_start < now() - interval '5 seconds' AND pid <> pg_backend_pid()
ORDER BY xact_start;
```

Usually the blocker is a long transaction (`state = 'idle in transaction'`, or a long
read). Let it finish, or end it if it is safe. `idle in transaction`: only
`SELECT pg_terminate_backend(pid)` helps; `pg_cancel_backend(pid)` returns true but the
session keeps its lock. `pg_cancel_backend` ends a running query (`state = 'active'`)
only. Never kill an autovacuum worker whose query says "to prevent wraparound"; it can
be the blocker, and the migration waits for it or goes first.

A failed run is not free: each attempt queues every query on the target table for up to
5 s. With `backoffLimit` 4 (5 pods per Job) and three syncs that is up to about 15 short
stalls over about 10 minutes. No alert fires, but latency spikes; so rerun once the
blocker is gone, not blindly: `argocd app sync ryft-platform` (the hook Job is
recreated), or at a quiet time. Nothing needs undoing.

`Seed` (built-in exercises and plans, run by the same Job after the migrations) also runs
under `locked()` and gets the same 5 s timeout. Its error is the raw `55P03` ("canceling
statement due to lock timeout") without the `apply ...` wrapper, from the `migrate` log
line `seed`; the same rerun applies.

The migrate Job has `ttlSecondsAfterFinished: 3600`: an hour after it finished its Pod
and logs are gone. What the hooks did stays in the operation state of the application:

```bash
kubectl -n argocd get app ryft-platform -o jsonpath='{.status.operationState.phase}{"\n"}{range .status.operationState.syncResult.resources[?(@.hookType)]}{.kind}/{.name} {.hookType} {.hookPhase}{"\n"}{end}'
# Succeeded / Job/migrate PreSync Succeeded / Job/smoke PostSync Succeeded
```

**A selective sync skips the hooks** (user only): `argocd app sync ryft-platform
--resource apps:Deployment:web` runs no PreSync and no PostSync, and is not recorded in the
history (Argo CD's selective sync documentation: "Hooks are not run."). Use it only when
migrate is the blocker and the change is safe without it; the smoke has not vouched for
the result, so run `make smoke-prod` afterwards.

**A wave that does not get healthy holds every later change:** the root's sync waits for
it, so even a fix to another application is not delivered. `argocd app terminate-op
ryft-root`, then `argocd app sync ryft-root` (seen in the kind test with a broker that
could not start).

**Roll back** one group: the old pin(s) **and a hold** in the same commit. Without the
hold the next push to main builds the rolled-back code again and pins it within about 15
minutes (D107). Argo CD does not roll back by itself (D95). Migrations stay (below), so
the previous release runs on the newer schema; how far back that works is under
"Lockouts and rolling back across releases".

**Configuration is part of the rollout** (F1). api, ingest, scoring and notify read
`ryft-config-<hash>`, generated from `deploy/k8s/base/<service>/config.env` (migrate's
`ryft-config` stays plain). Any edit renames the ConfigMap, so the Deployment rolls with the
images that are pinned; Argo CD deletes the old ConfigMap only after the sync is healthy
(`PruneLast`), and a failed rollout leaves it for the old pods. Roll back in git, never with
`kubectl rollout undo` or by scaling an old ReplicaSet: it may name a pruned ConfigMap
(`CreateContainerConfigError`) and self-heal reverts it anyway. Which commit to revert:

- a **configuration** problem (a `config.env` value such as `LOG_LEVEL`, or a hand-made change
  of `overlays/eks`): revert the merge that changed it. The old content gives the old name, so
  the pods roll back. Not for `PRIVACY_POLICY_VERSION`: a policy PR cannot be reverted (the
  versions list is append-only and the check wants the newest page); see "Withdrawing a
  version" under Beta → Consent, where a new version is the way.
- an **image** problem: the pins and a hold as above (`pin_images.sh <old> <group>` and
  `hold.sh add <group> "<reason>"`), not a revert of the deploy PR's merge when it pinned
  both groups. Leave the pin commits of the other group alone.

**A web rollback moves the policy in force too.** `pin_images.sh <old> web` sets the version
in force (api and ingest) to what the site at `<old>` serves: base's `config.env` there, or the
newest privacy page for a commit from before `config.env` existed (the foreign `f437747`: the
first listed version). If that differs from today's, api and ingest roll with web and the
testers who consented to the newer version consent again (`consent_required` rises). The
`manifests` job (`check_policy_in_force.sh`) refuses a web pin whose commit does not serve the
version in force, so pin and version always go back together. A draft version on main blocks
every deploy PR (services too), because the deploy PR would put a draft into force: publish the
text, or hold web (`./scripts/hold.sh add web "<reason>"`).

**Before you start** (a planned rollback or a drill; in an incident the first three may be
red, which is why you are rolling back, the rest still holds):

- Nothing pending: `./scripts/deploy_targets.sh` prints `services=false web=false
  held=false`, and the overlay has no `# hold:` line.
- No deploy PR is open (`gh pr list --state open --search 'head:deploy/'`,
  `git ls-remote --heads origin 'deploy/*'`), the last `ci` run on main is green and none
  is in progress, `GH_REPO=timkrebs/ryft-platform ./scripts/deploy_watch.sh` reports OK.
- Argo CD: `kubectl -n argocd get applications` all Synced and Healthy.
- The images you roll back to exist: `./scripts/check_registry.sh
  ghcr.io/timkrebs/ryft/{ingest,scoring,api,notify,migrate}:<old>` for the services, and
  `./scripts/check_registry.sh ghcr.io/timkrebs/ryft/web:<old>` for the site (`web:<old>` is
  its own tag: the services' SHA is no proof that it exists).
- Nothing else merges while the hold stands (a merge that touches the group's directory
  would be built after the release, not before, but a second deploy PR confuses the proof).
- Know the way back (the undo below) before you merge.

**Abort and way back:**

| Where | Abort if | Way back |
| --- | --- | --- |
| Before the merge | a local check or CI is red, no approval | Close the PR, delete the branch. |
| PreSync | migrate fails or hangs | Nothing rolled; Argo retries twice; then the undo. |
| Rollout | a pod crash-loops or stays unready for 3 minutes, or api or ingest has fewer than one ready | The old ReplicaSet keeps serving; the undo. |
| PostSync / verify | the smoke fails, `/v1/me` is not 401, dead letters grow (`scripts/dlq.sh list`), `ArgoSyncFailed` | The undo. |
| Hold window | a deploy PR appears | Close it, then the undo; find out why promote ran. |

1. Find the last "deploy: images" merge that moved the group, and the pins before it.
   `git log -- <overlay>` lists the web-only deploys too (they leave the five service
   lines alone), so read what each merge changed. Name the branch anything but
   `deploy/<7 hex>`: CI treats those as the App's own and refuses their change of a held
   pin.
   ```bash
   git fetch origin && git switch -c fix/rollback-services origin/main     # or fix/rollback-web
   f=deploy/k8s/overlays/eks/kustomization.yaml
   git log --oneline -8 -- $f                                              # the deploy merges
   git show <merge> -- $f | grep -E '^[-+] +newTag'                        # five lines a side: services; one: web
   git show <merge>^:$f | grep -A1 -E 'ryft/(ingest|scoring|api|notify|migrate)$'   # the old tags (services)
   git show <merge>^:$f | grep -A1 'ryft/web$'                             # the old tag (web)
   ```
2. Set the pins and hold the group. `pin_images.sh` sets all five services tags at once
   (never edit them by hand: one forgotten tag is a mixed release) and prints the pin you
   roll back from; `hold.sh` refuses a services hold while the five disagree.
   ```bash
   ./scripts/pin_images.sh <old> services       # or: web   (the site may also go to "f437747", see Apex site)
   ./scripts/hold.sh add services "bad migration, see #57"      # or: web "broken AASA, see #57"
   ```
   A **web** rollback also sets the version in force to what the site at `<old>` serves, and
   `manifests` refuses the pair when the older site would bring back a draft text: if the
   version in force was published in place (the same version label, `status: draft` then
   `published`), rolling web back past the commit that published it, or to `f437747`, fails
   `check_policy_in_force.sh` ("would bring the draft text back"). Pick an `<old>` at or after
   the publishing commit, or hold web at the current pin.
   `hold.sh` writes exactly `# hold: <services|web> <YYYY-MM-DD UTC> <reason>` above the
   group's first image (the **ingest** entry for the services, **web** for the site), is
   idempotent, and runs `deploy_targets.sh --check` (any other line that starts like a
   hold fails `manifests`: a mistyped hold would otherwise be ignored). **The reason is
   public** (the overlay, deploy PR bodies, run summaries): printable ASCII, one line, an
   issue number and nothing else, no names, ids, e-mail addresses or health details;
   `hold.sh` refuses `@` and "fixes/closes/resolves" before `#N`, `GH-N` or an issue URL (the
   merge would close the issue); `deploy_targets.sh --check` applies the same rules to every
   hold line in the overlay, so a hand-edited line fails `manifests` too. `--check` also reads the
   whole overlay as an allowlist: only the six plain image entries, a single `images:` key and
   the known top-level keys; anything else fails.
   When the deploy PR moved both groups and only one is bad, change only that one; do not
   `git revert` the whole merge. GitHub's Revert button works too (its `Revert "…"` title
   passes `pr-title`), but you still add the hold.
3. Commit as `deploy: roll back services to <old>`, `gh pr create --fill`, then merge.
   `gh pr merge --squash --auto` merges as soon as the required checks pass; main has no
   required reviews, so no human sits in between. When someone must approve, merge by
   hand (no `--auto`) after the review. Pushing as admin to skip the checks (D96) is for
   the user only; an agent never does.
4. Argo CD picks the merge up within two to six minutes (drill: 2:20 and 6:08) and rolls the group back like
   any release. For a **services** rollback the hooks are the OLD release's: PreSync
   migrate and PostSync smoke run the `migrate:<old>` image (limits below). A web
   rollback leaves migrate and the smoke on the services pin.
5. **Proof that the hold works:** the run on main of the rollback merge itself is the
   first proof. Its `changes` job and summary print `services held since 2026-10-23 (…)`,
   `images` and `web-image` are skipped, and promote ends with `promote: no group differs
   from its running pin (services: held since 2026-10-23 …; web: …): no deploy`. No
   `deploy/<sha>` branch or PR appears. `held=true` is what lets promote run when nothing
   else is pending; it then closes older open deploy PRs, so one cannot undo the rollback.

**Undo a rollback** (the old release was fine after all): one commit on a branch that is
not `deploy/<7 hex>` that sets the pins back to what you rolled back from and runs
`./scripts/hold.sh rm <group>`. Merge it; Argo CD rolls forward. If the group's directory
moved past the pin you roll back to in the meantime, the merge also targets it: CI builds
and deploys a new SHA instead of the one you rolled back from.

**A hold stops promote for that group only.** While it stands, every run on main prints
`web held (…)` in the `changes` job and its summary, and the next deploy PR shows
`held: <reason>`; the group deploys nothing, not even a fix. `manifests` fails a deploy
PR that moves a held group's `newTag`. Your own PRs may still move a held pin (a second
rollback). If a red `web-image` (Trivy, GHCR) blocks a backend hotfix, hold web
(`./scripts/hold.sh add web "ci red"`) and merge the hotfix. The deploy watch fails a hold
older than seven days: a hold is a rollback in progress, not a state.

**Release a hold** once the fix is on main (or the bad code reverted). It takes **two
merges**, and the cluster stays on the rolled-back pin until the second is through:

1. Before opening the PR, see what its merge will target: `./scripts/hold.sh rm services`
   on a branch, then `./scripts/deploy_targets.sh` (`services=true` and why).
2. Merge the PR that deletes the `# hold:` line. CI on main finds `backend/` different
   from the rolled-back pin, builds new images at the **new** SHA, and promote opens a
   deploy PR that merges itself. Plan for about 12 to 15 minutes. The final pin is that
   new SHA, not the one you rolled back from.
3. If the group's directory already equals the pinned tree (the cause was not code, e.g. the
   `SUPPORT_EMAIL` variable), nothing is targeted: `gh workflow run ci --ref main -f
   force=web` (or `services`, `all`). A hold always wins over `force`.

**Verify after a rollback or a release:**

```bash
kubectl get deploy -A -o custom-columns='NS:.metadata.namespace,NAME:.metadata.name,IMAGE:.spec.template.spec.containers[*].image' | grep ghcr.io/timkrebs/ryft
kubectl get rs -A -o custom-columns='NS:.metadata.namespace,NAME:.metadata.name,DES:.spec.replicas,READY:.status.readyReplicas,IMG:.spec.template.spec.containers[0].image' | grep -E '^(NS|ryft-)'   # one ReplicaSet with replicas per service, the old at 0
kubectl -n argocd get app ryft-platform -o jsonpath='{.status.operationState.phase}{"\n"}{range .status.operationState.syncResult.resources[?(@.hookType)]}{.kind}/{.name} {.hookType} {.hookPhase}{"\n"}{end}'
curl -s -o /dev/null -w '%{http_code}\n' https://api.ryftapp.de/v1/me     # 401 (alive, wants a token)
make smoke-prod                   # needs SUPABASE_* and SMOKE_* in the environment
```

The consumers: `kubectl -n ryft-scoring logs deploy/scoring | grep -E 'amqp (connected|consuming)'`
(likewise notify), or `ryft_amqp_connected` in Grafana. The pods' `/metrics` cannot be
reached through the API server's pod proxy (NetworkPolicy), so use the logs or Grafana.

**Disruptions:** api, ingest and `web` (two replicas, `maxUnavailable: 1`) have a
PodDisruptionBudget, so a node drain takes one site pod at a time.

**Re-run promote:** "Re-run failed jobs" on the latest run on main. An older run's
promote exits with "not main's tip" and does nothing; use `gh workflow run ci --ref main
-f force=<group>` instead. promote touches only the App's own `deploy/<sha>` PRs, and does
not reopen one you closed. A stalled deploy PR (red checks) is closed by the next push or
by hand.

**If migrate blocks the rollback** (a failed PreSync, e.g. the Supabase lockout below),
the rollback PR rolls nothing: web shares the `ryft-platform` application with migrate.
Follow "Lockouts" first. A broken manifest change is reverted like code.

**Break-glass** (Argo CD itself is down): pause it if it is half up, then `make
k8s-apply-eks` (prints a warning; applies the Vault objects, RabbitMQ, migrate, then the
services, without the PostSync smoke; checks the registry first). Afterwards make git
hold exactly what you applied, and resume.

### The deploy watch

`.github/workflows/deploy-watch.yml` runs `scripts/deploy_watch.sh` every day at 05:17 UTC
(and on `gh workflow run deploy-watch`) with a read-only token. It reuses
`deploy_targets.sh`, changes nothing and fails with its findings in the run summary:

| Finding | Meaning | What to do |
| --- | --- | --- |
| `<group> has been held for N days` (`HOLD_MAX_DAYS`, 7) | A rollback never finished. | Ship the fix and release the hold (above), or renew it on purpose: `hold.sh rm`, then `hold.sh add` in a PR. |
| `<group> is held since <date>, which is N day(s) in the future` | A typo in the date would keep the age check from ever firing. | Fix the date in the overlay (UTC `YYYY-MM-DD`; `hold.sh` writes today's). |
| `#N (deploy/<sha>) has been open for N min` (`DEPLOY_PR_MAX_HOURS`, 2) | The deploy PR should have merged itself. | Open it: red checks (fix or re-run), no auto-merge, a branch rule. Close it **and hold the group** to stop the deploy. |
| `<group> differs from its pin, main's tip is N h old and no deploy PR is open` | promote failed (a missing key is this: with no `RYFT_DEPLOY_APP_KEY` in the environment and none in the repository, `create-github-app-token` fails and the job is red, not skipped), was skipped (only `RYFT_DEPLOY_APP_CLIENT_ID` unset skips it), or its PR was closed on purpose. | The latest `ci` run on main: re-run failed jobs, or `gh workflow run ci --ref main -f force=<group>`; to keep a stopped deploy stopped, hold the group. |
| `scripts/deploy_targets.sh failed` | A hold that does not parse, or a byte in the overlay that is not printable ASCII (a CR, U+2028, U+2029, U+0085: line breaks to YAML). A missing or disagreeing pin is not this: it targets the group. | Fix the overlay first. |
| `could not list the open pull requests` / `a creation time I cannot read` | The token lacks `pull-requests: read`, or GitHub's answer changed. | The workflow's `permissions`; the script. |

A warning (not a failure) names a PR from a `deploy/<sha>` branch that is not by the
App: the App was renamed (set `DEPLOY_APP_SLUG` in the workflow) or a person used the
reserved name. It is not counted as a deploy PR. Run it on an up-to-date main: it reads
the checkout, which a scheduled run is. Exit 2 means the watch itself could not run (a
shallow clone, a bad setting).

A failed scheduled run is mailed to whoever last changed the `cron` line of the workflow
(GitHub's rule for scheduled workflows), not to the repository owner by default, and only
if that account's Actions notifications (Settings → Notifications → Actions) are on. Do
not let a bot be the last to edit that line. A scheduled workflow in a public repository
is switched off after 60 days without repository activity; a failed run is the only
signal, so also look at the Actions tab now and then.

### The `deploy` environment and the App key

The `promote` job runs in the GitHub environment `deploy`, restricted to the branch
`main` and not bypassable by administrators, and the deploy App's private key
`RYFT_DEPLOY_APP_KEY` lives there. Only a job on `main` that names the environment can
read it: a workflow edited in a pull request, or run from another branch, cannot. The
environment has no required reviewers (the promote is unattended). CI's `manifests` job
(`scripts/check_workflows.sh`, which parses the workflows with `yq`) fails if any other job
names an environment or reads the key (in any spelling: flow style, quoted keys, any case
of the secret's name), if a workflow uses `pull_request_target` or `workflow_run`, calls an
external reusable workflow (`uses:` other than `./.github/workflows/<file>`), uses
`secrets: inherit` or reads `secrets` other than as `secrets.<NAME>`, or names one of the
test hooks of the scripts, or a YAML merge key. CI's `bytes` job (no path filter, on every run; `ci-ok` and the image jobs need it) fails on a hidden line break,
control or other invisible character (format, private use, odd spaces), bidi control or BOM
in ANY tracked file, by content and not by extension (kustomize also reads `Kustomization`
and any file a `resources:` entry names), on the file names `Kustomization`,
`kustomization.yml`, `.gitattributes` and `.gitmodules`, and (`make k8s-validate`) on a
kustomization under `deploy/` that references a remote base or anything outside `deploy/`
(`scripts/check_bytes.sh`, `scripts/check_kustomize_refs.sh`; the pre-commit hook runs the
byte check on every staged file and needs python3, `make hooks`). `deploy/argocd/apps/`
holds `*.yaml` files only. "Not bypassable by administrators" is a
setting you confirm in the browser (step 3).

**Set it up by rotating the key, not by moving it** (user only; the file that was on your
disk and in the repository secret is gone afterwards, and the old key stops working):

1. In GitHub → Settings → Developer settings → GitHub Apps → the deploy App → Private
   keys: **Generate a private key**. The browser saves `ryft-deploy.<date>.private-key.pem`.
2. Find it: one line must print.
   ```bash
   key=$(ls ~/Downloads/ryft-deploy.*.private-key.pem); echo "$key"
   ```
3. Create the environment with the branch policy `main`:
   ```bash
   gh api -X PUT repos/timkrebs/ryft-platform/environments/deploy --input - <<'JSON'
   {"can_admins_bypass": false, "deployment_branch_policy": {"protected_branches": false, "custom_branch_policies": true}}
   JSON
   gh api -X POST repos/timkrebs/ryft-platform/environments/deploy/deployment-branch-policies -f name=main -f type=branch
   gh api repos/timkrebs/ryft-platform/environments/deploy --jq '{p: .deployment_branch_policy, bypass: .can_admins_bypass}'
   gh api repos/timkrebs/ryft-platform/environments/deploy/deployment-branch-policies --jq '.branch_policies[] | [.name,.type]'
   ```
   **Then confirm "admin bypass off" in the browser:** Settings → Environments → `deploy` →
   "Allow administrators to bypass configured protection rules" must be **unchecked**
   (untick it and Save if not). `can_admins_bypass` is not in GitHub's REST schema, so the
   `PUT` above may be ignored and the `bypass` field of the `GET` may print `null` or
   `true`: the checkbox is the proof. Do not go on to step 4 before it is off.
4. Put the new key in the environment and check that it is there:
   ```bash
   gh secret set RYFT_DEPLOY_APP_KEY --env deploy -R timkrebs/ryft-platform < "$key"
   gh secret list --env deploy -R timkrebs/ryft-platform
   ```
5. Merge the change that adds `environment: deploy` to `promote`. **Then delete the
   repository-level secret at once**, do not wait for a promote: from the merge on, the
   environment's secret wins and the repository copy is never read, and until it is gone
   any workflow run in this repository can read it:
   ```bash
   gh secret delete RYFT_DEPLOY_APP_KEY -R timkrebs/ryft-platform
   gh secret list -R timkrebs/ryft-platform          # no RYFT_DEPLOY_APP_KEY any more
   ```
6. In the App's settings → Private keys delete the old key(s): exactly one key is left,
   the new one.
7. `rm -- "$key"`, remove any older `~/Downloads/ryft-deploy.*.private-key.pem`, empty the
   Trash.
8. The first promote after the merge (a real deploy, or `gh workflow run ci --ref main -f
   force=web`, which pins the site once) is the proof that the environment's key works. If
   it fails at `create-github-app-token`, the secret in the environment is wrong: repeat
   step 4 and "Re-run failed jobs" on the latest run on main; nothing was deployed.

**Prove the branch policy once** (optional, user only): a pull request that names the
environment is refused.
```bash
git switch -c ci/env-proof origin/main
printf 'name: env-proof\non: pull_request\npermissions: {}\njobs:\n  proof:\n    runs-on: ubuntu-latest\n    environment: deploy\n    steps:\n      - run: "true"\n' > .github/workflows/env-proof.yml
git add .github/workflows/env-proof.yml && git commit -m "ci: environment proof (do not merge)" && git push -u origin ci/env-proof
gh pr create --draft --fill && gh pr checks     # proof: failed, "not allowed to deploy to deploy" (and manifests: only promote may name it)
gh pr close --delete-branch                    # then
```

**Order matters:**
- Delete the repository copy before the merge (step 5 before the merge) and the old
  `promote` still reads it: it fails at `create-github-app-token` with no private key.
  Nothing deploys and nothing breaks; merge, set the secret, re-run the failed job.
- Merge before the environment exists: GitHub creates `deploy` on the first run with no
  branch policy. The job works (it falls back to the repository's secret), but the key is
  not yet protected.
- Delete the repository copy before step 4: the first promote fails the same way.
- Never delete it: the environment protects nothing while a copy any workflow can read
  exists.
- A policy that names the wrong branch refuses the job outright (red, nothing deploys).

### What a kustomization or an Argo CD app may contain

Both are read by an allowlist, not by a list of forbidden things: kustomize reads `Resources:`
and the U+017F spelling `reſources:` like `resources:`, and decodes `!!binary`, so no list of
bad spellings is complete. The schema is `scripts/lib/yamlpolicy.py`:

- exact, case-sensitive keys. A kustomization: `apiVersion`, `kind`, `namespace`, `resources`,
  `patches` (`path`, `patch`, `target`), `images` (`name`, `newTag`), `labels`,
  `configMapGenerator` / `secretGenerator` (`envs`, `literals`, `options.labels`),
  `generatorOptions`. An app: one `spec.source` (`repoURL`, `targetRevision`, `path`), never
  `sources`, `kustomize`, `helm`, `plugin` or `directory`;
- the YAML tags `!!map !!seq !!str !!int !!bool !!null` only; no `<<`, `!!binary`, anchor or alias;
  one document per file (a trailing `---` is a second one); regular files, no symlink in the tree;
- an inline `patch:` is a literal block (`|` or `|-`), and no key or string may DECODE to a line break
  or invisible character (a double-quoted `\L` or `\x85` would);
- every field that names a file is typed `Path(...)` in the schema and is checked by what it names
  (`scripts/check_kustomize_refs.sh`): plain relative paths below `deploy/`, no symlink, and in
  `resources:` no name that kustomize could read as a remote URL (a segment with a dot, such as
  `github.com/org/repo`, is refused even when a directory of that name exists: kustomize clones first);
- an app's path is below `deploy/`, one application per path; the project is one of `ryft`,
  `ryft-operators` (bound to `deploy/rabbitmq/operators`) and `ryft-root` (`root.yaml` only);
  every path is rendered (git limited to `file://`) and the render keeps a SMALL set of production
  invariants (`scripts/lib/renderpolicy.py`): no `argoproj.io` object; for the `ryft` project only
  our six images with 7-hex tags (plus a digest-pinned rabbitmq, compared by pattern); no
  `API_KEY`, `ALLOW_INSECURE_APIKEY_AUTH` or `USER_ID` and `AUTH_MODE=supabase` in ConfigMaps,
  Secrets (decoded) and container env, no `valueFrom` for them, no `envFrom[].prefix`; default-deny
  intact in every `ryft-*` namespace with a workload; no NetworkPolicy rule that allows every peer
  (empty, `from: []` / `to: []`, ports only).

**Not checked** (the follow-up is an admission policy, see `docs/STATUS.md`): pod security
(privileged, `host*`, `hostPath`), Namespace objects and Pod Security labels, which image runs in
which namespace, `command` / `args`, the broker image beyond its pattern, NetworkPolicy shapes
beyond the above (`ipBlock`, `namespaceSelector`), workloads without `metadata.namespace`, Vault
Secrets Operator objects (the `VaultConnection` address, transformation templates), the power of
the operators project's cluster roles, and `project.yaml` itself (the check reads it from the
pull request). Do not read a green check as "production-safe".

`make k8s-validate` (CI's `manifests` job) runs these checks. The byte check
(`scripts/check_bytes.sh`, CI's `bytes` job) refuses tracked symlinks, reads every file under
`deploy/` and `.github/` as text whatever its extension, and has no exemption by path: characters
that render as nothing are written as `\u` escapes in sources. CI's `yq` is the release
binary from `scripts/install_yq.sh` (version and sha256 in that file; `manifests` and `smoke` both run it).

**To add a key**, change the schema in `scripts/lib/yamlpolicy.py` and the test in
`scripts/tests/check_kustomize_refs_test.sh` in the same PR as its first use; a new path-carrying key
is a `Path(kind)` there, so its references are followed automatically.

failures` in every service's log, pods unready): Supabase's pooler blocks the project for
the cluster's NAT address (`63.188.104.25`, `3.120.13.212`) for 120 s after 10 failed
logins in 150 s, and repeated failures get the address banned on the database host.
**Do not re-run deploys** (`make k8s-apply-eks`, or syncs by hand): before D93 every
migrate run rewrote the role passwords and caused the next round of failures. Wait two minutes; find the failing
login (`kubectl -n ryft-<svc> logs -l app=<svc> --tail=-1 --since=15m | grep -v
ECIRCUITBREAKER | grep -i 'password\|28P01'`), and look at Supabase → Database →
Settings → Network Bans (or `supabase network-bans get --project-ref <ref>`) and remove
bans on those addresses. The pods reconnect on their own (incident of 2026-10-20 20:43,
`STATUS.md`).

**No down-migrations.** Migrations only add (tables, nullable or defaulted columns,
grants, backfills; never a drop or a rename), so the previous release runs on the newer
schema: it ignores what it does not know, and its migrate job skips every file it has
and does not mind newer rows in `schema_migrations`. A rollback is therefore never a
schema change.

**Rolling back past the RabbitMQ cutover** (D102): images from `fd36a9a` on carry both
brokers and follow `EVENTS_BACKEND`/`EVENTS_CONSUME`, which `overlays/eks/events.yaml`
sets to RabbitMQ, so they run without NATS. Images before `fd36a9a` know only NATS:
rolling back that far means restoring NATS first (revert the R4 commit, `infra/vault`
with the `nats` service again).

**Rolling back past the gate modes** (to a release before `beta: gate modes and admin
access grant`, e.g. `21eb0fa`) with `BETA_GATE = "warn"` in `infra/vault`: that release
knows only `on` and `off` and api and ingest do not start ("BETA_GATE must be on or
off"). Set it to `off` or `on` first (apply, restart the operator), then roll back.
`CONSENT_ENFORCE` it ignores: consent is then enforced again.

**Rolling back past the `smoke` subcommand** (`361e34a`): a rollback runs the hooks of
the OLD release, PreSync migrate and PostSync smoke from the `migrate:<pin>` image of the
rolled-back pin. A pin before `361e34a` has no `smoke` subcommand, so the PostSync hook
fails and the sync is reported failed although the pods rolled (the rollout itself is in).
Prefer a fix forward to a rollback that far.

**The UI and the CLI:**

The UI is at `https://rabbitmq.ryftapp.de` (D103), with the operator's default user:

**Healthy is:** `kubectl -n ryft-rabbitmq get rabbitmqcluster rabbitmq` with
`ALLREPLICASREADY` and `RECONCILESUCCESS` True; every topology object Ready (`kubectl -n
ryft-rabbitmq get vhosts,exchanges,queues,bindings,policies,users,permissions,topicpermissions`);
`rabbitmq-queues -q quorum_status scoring --vhost ryft` lists three voters;
`rabbitmq-diagnostics -q alarms` reports none. The alerts: `RabbitMQBacklog`,
`RabbitMQDeadLetters`, `RabbitMQAlarm`, `RabbitMQNodeDown`, `AMQPDisconnected`,
`EventsUnroutable`, `OutboxBacklog`, `OutboxStuck` (OBSERVABILITY → Alerts).

**Dead letters** (`dlq.scoring`, `dlq.notify`, 14 days): an event that did not decode, or
failed six attempts (5 s, 30 s, 5 min apart). `scripts/dlq.sh` port-forwards to the
management API itself:

```bash
scripts/dlq.sh list                       # per queue, one line per letter: subject, attempts, error
scripts/dlq.sh show dlq.scoring 5         # in full
scripts/dlq.sh replay dlq.scoring all     # after fixing the cause: back on ryft.events with its key
scripts/dlq.sh purge dlq.notify           # notify's: a push hours late is wrong (replay refuses without --force)
```

Re-drive after fixing the cause (a deploy, a data fix). scoring's letters only name a
user and days, so `POST /v1/recompute` or `scripts/rescore_all.sh` repair the same if a
letter is gone; notify's are listed and purged, never re-sent late.

**The outbox** (D101): events waiting for the broker are rows of `outbox` in Postgres
(SQL editor, as the owner):

```sql
SELECT publisher, count(*), min(created_at) FROM outbox WHERE published_at IS NULL GROUP BY 1;
SELECT id, publisher, routing_key, attempts, last_error FROM outbox WHERE published_at IS NULL AND attempts >= 50;
UPDATE outbox SET attempts = 0 WHERE id = 1234;   -- a stuck row, once its cause is fixed: the relay sends it again
```

Waiting rows mean the relay cannot reach the broker or the broker refuses (a full queue,
an alarm); they go by themselves once it accepts. A stuck row (50 failed sends) is
usually a key no queue is bound for: a topology change missed.

**Changing the topology:** edit `backend/internal/events/amqpbus/topology.go`, run
`go run ./cmd/rabbitmq-topology` in `backend/`, commit both files; Argo CD applies it. A
queue's arguments cannot change (the Topology Operator refuses): tune with its policy.
Queues and the vhost have `deletionPolicy: retain`, so removing one from the topology
leaves it in the broker; delete it in the UI once it is empty.

**A node drain** (a node group rotation): the PDB lets one RabbitMQ pod go at a time, and
the pod waits up to 10 minutes to hand over its quorum queues. Two of three nodes keep
every queue working; with one left, publishes are refused (the outbox keeps them) and
consumers stop until a second node is back.

**Alarms:** the memory watermark is 60 % of what the operator gives RabbitMQ of the
1 GiB limit (80 %): about 0.52 GB a node (`rabbitmq-diagnostics -q status`; a node uses
about 130 MiB idle); the disk alarm
at 1 GB free of 10 GiB. Either blocks every publisher until it clears
(`RabbitMQAlarm`); first look at the queue depths (a consumer that stopped consuming).

**Upgrades:** RabbitMQ: change the image digest in
`deploy/rabbitmq/cluster/rabbitmqcluster.yaml`; the operator replaces the nodes one at a
time. The operators: vendor the new release files byte for byte into
`deploy/rabbitmq/operators/`, update `SHA256SUMS`, read the release notes (a Cluster
Operator upgrade rolls every cluster).

**Backups:** none beyond git. Messages are triggers, the topology and users are in git
and Vault, Postgres is the truth. A broker rebuilt from nothing comes back through Argo
CD; then `scripts/rescore_all.sh 3` covers what was in flight.

**Credentials:** a user's password: `terraform -chdir=infra/vault apply
-replace='random_password.amqp["api"]'`, restart the Vault Secrets Operator; it rewrites
`amqp-user-api` (the Topology Operator changes the broker's user) and the api's
`ryft-secrets` (the api restarts). Until both have it, the api's logins fail and it
retries. Certificates: cert-manager renews them 30 days before expiry; if a service
cannot connect after a renewal of the broker's, `kubectl -n ryft-rabbitmq rollout
restart statefulset rabbitmq-server` (untested, D98).

## Network policy

Every namespace starts with `default-deny` (no ingress, no egress) and `allow-dns`
(`base/common`). Each workload then allows exactly its own flows
(`base/<service>/networkpolicy.yaml`):

| Workload | In | Out |
| --- | --- | --- |
| ingest, api | 8080 from Traefik in `kube-system` (or ingress-nginx in `ingress-nginx`); 9090 (`/metrics`) from namespace `monitoring`, and on EKS from the VPC range (the host-network collector) | RabbitMQ (`ryft-rabbitmq`, 5671), TCP 443 + 5432 to public addresses (Supabase Auth, the pooler) |
| scoring | 9090 from `monitoring` (and the VPC range on EKS) | RabbitMQ (5671), TCP 5432 to public addresses |
| notify | 9090 from `monitoring` (and the VPC range on EKS) | RabbitMQ (5671), TCP 5432 (the pooler) and 443 (APNs: `api.push.apple.com`, `api.sandbox.push.apple.com`) to public addresses |
| web (`ryft-web`) | 8080 from Traefik | nothing |
| rabbitmq | 5671 from the `ingest`, `scoring`, `api` and `notify` pods, each in its own namespace; 15671 from the Topology Operator; 15692 (metrics) from the VPC range; the Erlang ports from its own nodes | its own nodes, the Kubernetes API (peer discovery) |
| migrate | nothing | TCP 5432 to public addresses |
| postgres (`local-postgres`) | 5432 from the five client namespaces and the backup pods | nothing |

"Public addresses" means `0.0.0.0/0` minus RFC 1918, CGNAT and link-local ranges, so no
workload can reach anything inside the VPC or the cluster on those ports. NetworkPolicy
cannot name hosts, so the ports are the restriction for the internet. The
`local-postgres` overlay adds `allow-local-postgres` egress for the in-cluster
database. Kubelet probes come from the node and are admitted by the EKS VPC CNI (and
k3s, Calico, Cilium). Namespaces are matched by `kubernetes.io/metadata.name`, which the
API server sets and nobody can relabel.

Adjust the `from` of ingest/api for another Ingress controller, or add a `cloudflared`
peer if a Cloudflare tunnel targets the services directly.

### Edge rate limit

Before any token is checked, Traefik limits each client IP to 20 requests a second on
average, with bursts of 50 (`overlays/eks/ratelimit.yaml`, a `Middleware` in `ryft-api`,
`ryft-ingest` and `ryft-web`). Each of the two Traefik replicas counts on its own, so
the effective limit is up to twice that. Over it, Traefik answers `429` with a
plain-text body. The NLB preserves client addresses, which this needs (a target-group
attribute in `infra/aws/kubernetes`). Check it from one machine, expecting `429`s
after the first ~100:

```bash
for i in $(seq 1 150); do curl -s -o /dev/null -w '%{http_code}\n' https://api.ryftapp.de/v1/me; done | sort | uniq -c
```

The services' own per-user limit (D36) applies after the token, so the two complement
each other.

**Consent.** `POST /v1/sync` answers `403 consent_required` until the account consented
to the current `PRIVACY_POLICY_VERSION` (`config.env` of api and ingest, in force per
`overlays/eks`; `2026-10-20` today), and
scoring computes nothing for an account without consent. Nothing was backfilled, so the
operator's own account consents once too: with the app build that has the consent
screen, or by hand with its access token:

```bash
curl -s -X POST -H "Authorization: Bearer $TOKEN" $API/v1/me/consent -d '{"policy_version": "2026-10-20"}'
```

**A new policy text** (only on the user's decision: everyone consents again) is **one
PR and no restart**: `web/content/legal/{en,de}/privacy/<version>.mdx` (the old versions
stay), `<version>` appended to `web/content/legal/privacy-versions.json`, and
`PRIVACY_POLICY_VERSION` in `deploy/k8s/base/api/config.env`,
`deploy/k8s/base/ingest/config.env` and `docker-compose.yml`. The base value is the version
that is *published*. The version in force on EKS is a pin in
`overlays/eks/kustomization.yaml` (two `ryft-config` literals, api and ingest) that CI's
promote moves to the base's value in the same deploy PR that pins the web image carrying the
page. So the page, web, api and ingest go live in one Argo CD sync: the merge itself changes
nothing on EKS, and there is no interim restart. A service's ConfigMap is generated as
`ryft-config-<hash>`, so a changed value renames it and rolls exactly the pods that read it.
`manifests` runs `node web/scripts/check-policy-version.mjs --strict` (published version,
pages, compose) and `scripts/check_policy_in_force.sh` (api and ingest agree, the pinned web
commit serves the version at `/privacy`, newest page in both languages). If web is held or its build fails, the old version stays in force
with the old site. The deploy PR body shows `privacy policy in force: A → B`.

What to watch after the deploy PR merges (read-only):

```bash
for n in api ingest scoring notify; do kubectl -n ryft-$n get cm -o name; done   # ryft-config-<hash> (+ configmap/kube-root-ca.crt)
kubectl -n ryft-api get deploy api -o jsonpath='{.spec.template.spec.containers[0].envFrom}'; echo
for s in api ingest; do kubectl -n ryft-$s logs -l app=$s --tail=-1 --since=30m | grep '"msg":"beta"'; done
make smoke-prod
```

The roll is a rolling update of a minute or two in which old pods still serve the old
version: `ryft_consents_total{action="stale"}` and `consent_required` refusals bump briefly
and recover. The PostSync smoke consents through api and syncs through ingest, so it proves
the two agree. Argo CD deletes the old `ryft-config-<old>` only after the sync is healthy
(`PruneLast`); until then the old hash is still listed. Rolling a ReplicaSet back by hand is
not a rollback path (its ConfigMap may be pruned, and self-heal reverts it): revert in git.

Withdrawing a version. A policy PR itself cannot be reverted as a whole (the versions list is
append-only), and the check requires the in-force version to be the NEWEST page of the pinned
web commit (that is what `/privacy` serves). So setting the in-force pin back alone fails the
check, and would be undone by the next web deploy anyway. A withdrawal is durable only as a
NEW version (the corrected text, appended) or with web held and pinned back (`pin_images.sh`
and `hold.sh add`, in one commit), never as the pin alone. If a sync fails in the middle (web
stuck while api and ingest are already on the new version, or the reverse), move web and the
in-force pin back together in one commit; the check refuses a pair that disagrees.
On a pull request `check_policy_in_force.sh` also refuses a version that becomes the one in
force, or the published one in `config.env`, unless its page in both languages says exactly
`status: published` (read as the site reads it; a tag, flow frontmatter or a block scalar
refuse even when published). Anything else is a draft for this check. Going back to a version
listed before the one in force now is allowed. So a policy PR stays red until `status:
published` is set in that same PR, and a draft version on main blocks every deploy PR, services
too, until it is published or web is held. A text that is published cannot be un-published in
place: the check also refuses a PR that sets a published page back to a draft, and a web pin
that would serve the draft again under the same version (a rollback past the commit that
published it, or to `f437747`, which carries 2026-10-20 as a draft). Publish a new version
instead.

Every tester consents again before the next sync;
`ryft_gate_refusals_total{code="consent_required"}` shows who has not yet.

## Two accounts for one person

**How it happens:** someone signs in with email and later with Apple (or the other way
round). Supabase links the two only when Apple hands over the same verified email; with
"Hide My Email" it is a relay address, and a second account appears. The app syncs into
whichever is signed in, so the data splits.

**How to see it:** `scripts/beta_report.sh` → `dup` (accounts that synced from the same
device id in the last 30 days); `scripts/user.sh <id>` names them under "possible
duplicate", with provider, last sync and days scored. The app is told too
(`GET /v1/me` → `account_hint`, API.md).

**How to merge** (D90): the smaller account into the one with the history. The plan
first, then the merge, which moves everything in one transaction, rescores the kept
account over the moved days, and deletes the other one like `DELETE /v1/me` (Supabase
sign-in and Apple grant included):

```bash
scripts/user.sh <from> --merge-into <to> --dry-run      # per table: moved, dropped (to's row kept), and why
scripts/user.sh <from> --merge-into <to>                # shows the plan again, asks for MERGE
```

Where both accounts have the same row (a sample, a device id, a session id, a journal
day, a custom exercise's slug), the kept account's wins and the other's is counted as
dropped. A consent and beta access are copied only when the kept account has none.
Merging the account with more scored days into the smaller one is refused (`409`) unless
`--force`. A second run answers `404` (from is gone). Afterwards, the person signs in the
way the kept account uses; if both identities should open it, they link Apple to the
email account in the app (Supabase **manual linking**, `SUPABASE.md`).

## When a tester's scores do not appear

What the app sees is `GET /v1/me/sync` (D91): which gate it is behind, the last sync and
device, the newest record per kind, today's state (`pending`: synced, scoring has not
finished; `waiting_for_sleep`: no night yet; `stale`: nothing for 20 hours; `scored`),
the days still queued and how long scoring takes now (`expected_within_sec`, the p95 of
the last 6 hours). The operator sees the same and more:

```bash
scripts/trace.sh <request id>        # the sync: status, code, gate; then scoring's lines for the same id
scripts/user.sh <id>                 # devices, what the last sync carried and ignored, days, duplicates
```

| Sign | Means | Do |
| --- | --- | --- |
| sync `403`, `code` on the access line | a gate refused (`consent_required`, `invite_required`) | the gate's mode (Beta), the account's consent and access in `user.sh` |
| last sync carried 0 accepted, many `ignored.*.duplicate` | the phone re-sends what the server has | nothing; new data comes with the next sync |
| many `ignored.*.unknown_type` / `outside_window` | an app build sending a type the server does not know, or a clock far off | the app's version in `user.sh`; the API's sample types |
| days stay `pending` for minutes | scoring is behind or failing | `SyncToScoreSlow`, `RabbitMQBacklog`, `DeadLetters`, `OutboxBacklog`; scoring's logs for the id |
| no sync for days, the phone has data | the app's background sync or its anchors | `user.sh <id> --resync-hint`: the app re-reads its window without anchors |
| scored, but the app shows yesterday | the silent refresh did not arrive (iOS budgets them) | `ryft_push_notifications_total{category="REFRESH"}`; the app polls `GET /v1/me/sync` too |

## Feature flags

`GET /v1/config` serves the flags in table `feature_flags` (D69). Change them with the
admin routes and the api's `ADMIN_API_KEY` (generated by `infra/vault`):

```bash
ADMIN=$(terraform -chdir=infra/vault output -raw admin_api_key)    # locally: dev-admin-key-change-me-0123456789abcdef
API=https://api.ryftapp.de
curl -s -H "Authorization: Bearer $ADMIN" $API/v1/admin/flags | jq            # every flag
# On for two testers only (their user IDs: GET /v1/me → id):
curl -s -X PUT -H "Authorization: Bearer $ADMIN" $API/v1/admin/flags/today.redesign \
  -d '{"enabled": true, "rollout_pct": 0, "allow_user_ids": ["<uuid>", "<uuid>"]}'
# 10 % of everyone, then everyone:
curl -s -X PUT -H "Authorization: Bearer $ADMIN" $API/v1/admin/flags/today.redesign -d '{"enabled": true, "rollout_pct": 10}'
curl -s -X PUT -H "Authorization: Bearer $ADMIN" $API/v1/admin/flags/today.redesign -d '{"enabled": true, "rollout_pct": 100}'
# Kill switch (off for everyone, testers included):
curl -s -X PUT -H "Authorization: Bearer $ADMIN" $API/v1/admin/flags/today.redesign -d '{"enabled": false, "rollout_pct": 100}'
curl -s -X DELETE -H "Authorization: Bearer $ADMIN" $API/v1/admin/flags/some.old_flag      # 204
```

`PUT` replaces the whole flag (`enabled` and `rollout_pct` required, a missing
allow-list is empty) and answers `201` for a new key, `200` otherwise; the api logs
every change (`msg="feature flag set"`). The app caches its answer for up to six hours,
so a change reaches everyone within that. Rotate the key with
`terraform apply -replace='random_password.admin_key["api"]'` in `infra/vault`.

## Scaling and disruptions

api and ingest run 2–4 replicas under a CPU HPA (70 % of the 50m request; needs
metrics-server), with a `PodDisruptionBudget` of `minAvailable: 1`, spread across nodes
when there are several. On a **single-node** cluster a drain blocks on the second pod,
because the first has nowhere to reschedule. Use `kubectl drain --disable-eviction`, or
`kubectl -n ryft-api delete pdb api; kubectl -n ryft-ingest delete pdb ingest` before
maintenance and re-apply afterwards. web (the apex site, two replicas) has a
`PodDisruptionBudget` of `maxUnavailable: 1`: a drain or node group update takes one site pod
at a time (it is not in local-postgres). Pods that are not ready never count
(`unhealthyPodEvictionPolicy: AlwaysAllow`): during an outage, when no pod is ready, a
drain or a node group update still goes through. Their Deployments carry no `replicas`, so
re-applying never fights the HPA. scoring stays at one replica: it owns the 15-minute
timer and processes recompute ranges in order. RabbitMQ has its own PDB (one node at a
time, OPERATIONS → RabbitMQ → A node drain).

### When a synthetic alert fires

The checks run from outside every 5 minutes from two probes (OBSERVABILITY → Synthetic
Monitoring). First look, read-only; the `job` label names the check:

```bash
# what the probes see, the way they see it (no redirects followed)
curl -sI https://ryftapp.de/ | grep -iE "^HTTP|content-type"                                     # ryft-site-home: 200, text/html
curl -s https://ryftapp.de/privacy | grep -c 'Art. 9(2)(a) GDPR'                               # ryft-site-privacy: 1 or more
curl -sI https://ryftapp.de/.well-known/apple-app-site-association | grep -iE "^HTTP|content-type|location"   # ryft-site-aasa: 200, application/json, no location
curl -s https://ryftapp.de/.well-known/apple-app-site-association | grep -c 'M77SKHKG63.dev.timkrebs.ryft'    # 1 or more
curl -s -o /dev/null -D - https://www.ryftapp.de/ | grep -iE "^HTTP|location"                                    # ryft-site-www-redirect: 301, https://ryftapp.de/
echo | openssl s_client -connect ryftapp.de:443 -servername ryftapp.de 2>/dev/null | openssl x509 -noout -enddate   # the served certificate
# inside
kubectl -n argocd get applications ryft-platform
kubectl -n ryft-web get pods -l app=web -o wide
kubectl -n ryft-web get ingress,certificate
kubectl -n ryft-web logs -l app=web --tail=50
```

- **SiteDown, all `curl`s fine:** the probes' view differs from yours, so look at the check
  in Grafana (Synthetics → the check → the failed run's logs name the assertion that
  failed: status code, header or body regexp). A regexp that no longer matches after a web
  deploy is the usual cause: the privacy marker (`Art. 9(2)(a) GDPR`) after a policy
  revision, the AASA after an app ID change. If the page is right and the regexp is stale,
  fix `deploy/grafana/synthetics/ryftapp.json` and `make synthetics-apply`; if the page is
  wrong, roll back the web pin ("Deploy and roll back") and fix forward.
- **SiteDown, `curl` fails:** pods not ready or none (`get pods`), the Ingress or the
  Traefik service (`kubectl -n kube-system get pods -l app.kubernetes.io/name=traefik`), DNS (`dig +short ryftapp.de`, ExternalDNS
  in `infra/aws/kubernetes`), the certificate. The AASA wrong or missing means universal
  links and password AutoFill stop working for testers: treat it like a down site.
- **SiteProbeFlapping:** a single failed run is noise, which is why the rule needs two in
  30 minutes. Open the check, compare the probes, and look at the failed runs' reason: a
  timeout from one probe (its network), a 429 (the edge's rate limit in `overlays/eks/web.yaml`,
  20 requests/s per address; the probes send about 1 per minute each, so a 429 means
  something else is hitting the limit), a 5xx (one pod: `kubectl -n ryft-web logs <pod>`). If it recurs for days,
  replace the probe in the JSON.
- **SiteWwwRedirectBroken:** the `www-to-apex` Middleware (`overlays/eks/web.yaml`) and the
  Ingress' second host; the check wants 301 or 308 with `Location: https://ryftapp.de/`.
- **SiteCertificateExpiring:** `kubectl -n ryft-web describe certificate ryftapp-de-tls`
  and `get challenges,orders -n ryft-web` (DNS-01), cert-manager's log (the flow:
  "EKS", Certificates). A renewed certificate shows in the next run; Traefik may need a
  moment to pick up the secret.
- **SyntheticsMissing:** the `job` label names the check that stopped reporting (one alert
  per job; all four at once means Synthetic Monitoring itself). In the Synthetics app: is
  that check there and enabled, is the stack inside its execution limit. The apply (the
  subshell in "Monitoring (Grafana Cloud)", with a fresh token) recreates deleted checks.
  Until it is fixed that URL is unwatched: run the block above after every web deploy.

The block above uses GET where it matters: `curl -I` sends HEAD, and Traefik answers a HEAD
for `www` with 308 where a GET gets 301 (the check accepts both).

## Mail for ryftapp.de

The site prints `support@ryftapp.de` (support, the privacy contact, the Impressum), and
the zone has **no MX record**: mail to it bounces until a mail service is set up. The
records go into the `ryftapp.de` zone in `infra/aws/dns` (Terraform, the user applies),
next to the CAA records, as `aws_route53_record`s:

- **MX** at the apex, the service's mail servers with their priorities.
- **TXT at the apex: one record set** with every value that belongs there, the SPF
  (`v=spf1 include:<the service> -all`) and the service's verification string. Route 53
  holds one TXT set per name; the apex has none today, and ExternalDNS keeps its ownership
  records under prefixed names (`a-www.ryftapp.de`), so nothing collides.
- **DKIM:** the service's selector records (`<selector>._domainkey`, CNAME or TXT, as it
  says).
- **DMARC:** TXT at `_dmarc`, starting with `v=DMARC1; p=none; rua=mailto:…` (a report
  address at the service, not a private one), tightened to `quarantine` once the reports
  are clean.

How: the user picks an EU mail service with forwarding and send-as, pastes the records it
asks for into the session, and they come back as a PR to `infra/aws/dns` (with a test in
`tests/dns.tftest.hcl`); then `(cd infra/aws/dns && terraform plan -out=tfplan &&
terraform apply tfplan)` and `dig +short MX ryftapp.de`. **The forwarding target, the
user's private address, is configured in the mail service only**: it never appears in a
DNS record, this repository or a Terraform variable.

## Data protection (logs)

- **What is logged:** one access line per request (method, path, status, bytes,
  duration, route, request id, user id) and what the services decide: a sync's counts
  and device id, which day was scored by which model (`scored day`: `day`,
  `model_version`, `inputs_changed`), a push's category and day, errors with their
  cause. Paths carry dates and resource ids (`/v1/days/2026-10-19`,
  `/v1/workouts/<uuid>`), so the lines still show when someone used the app and which
  days they opened: personal data, read and kept as below.
- **Never logged:** health values (no score, sample, sleep or workout value, baseline,
  learned sleep need or readiness state, neither as a field nor in an error's text: a
  body that does not decode is named by its field and type, not by its value), request
  or response bodies, query strings, tokens (APNs device tokens too: a failed push's
  error does not quote its URL), the `Authorization` header, email addresses (the smoke
  user's too), device names, feedback messages and diagnostics, invite notes. Supabase's
  admin API errors are logged as the status and GoTrue's `error_code`, never the body.
- **Exceptions**, both from bugs and rare: a panic's stack trace (`debug.Stack()` in
  `httpx.Recover`) shows the arguments of the calls on it as hex words, and pgx's error
  for an argument it cannot encode (an int64 too large for an `int4` column) quotes that
  argument. Fixing the bug needs both; read such lines as health data.
- **Tests pin it:** `TestEngineLogsNoHealthValues` (scoring at debug level, every
  line's keys allowlisted), `TestSyncLogsCountsOnly` and
  `TestSyncErrorPathsLogNoHealthData` (ingest), `TestWritesLogNoBodies` and
  `TestErrorPathsLogNoBodies` (api), `TestDecodeErrorsQuoteNoValues` (events),
  `TestJSONErrorDropsTheValue` (logx), `TestTransportErrorsHideTheDeviceToken` (apns),
  `TestAdminErrorsHoldNoBody` (auth). A new line on the paths they run fails them until
  its keys are listed there.
  - **Value kinds:** each allowed key also has a kind of value, pinned by the test-only
    package `internal/logx/logcheck` (a depguard rule keeps production code from importing
    it): UUIDs for user, request and device ids, `YYYY-MM-DD` for days, closed enums for
    category, code, gate, method, level, service and model version, booleans for flags,
    non-negative integers for counts (bounded where a bound is known: `request_ids` at most
    20, rescored days at most `MaxRangeDays`), an integer 100 to 599 for a status, RFC 3339
    for the time. A float, a score or a string under a count key fails; so does a key that
    appears twice on a line (`encoding/json` keeps the last, and logx appends `user_id` and
    the request's keys after the call site's, so a duplicate would hide one). The known
    values of each test (recovery, readiness, device tokens, the seeded samples) are
    scanned for in the raw line. `TestSyncLogKindsRejectMutations`,
    `TestWriteLogKindsRejectMutations`, `TestEngineLogKindsRejectMutations` and
    `TestNotifyLogKindsRejectMutations` feed the checker synthetic lines (a float under
    `applied`, a score under a renamed key, a non-UUID `user_id`, a duplicate key, …) and
    require a problem that names the mutated key; `TestNotifyLogsNoHealthValuesOrTokens`
    pins the notify service's lines.
  - **Third-party errors:** the admin (GoTrue), Sign in with Apple and APNs errors that are
    logged or shown hold the response's status code with the standard phrase
    (`logx.StatusLine`, never `resp.Status`, whose text is the server's), and from the body
    only a bare code: `error_code` / `error` as `[a-z_0-9]{1,64}`, an APNs `reason` as
    letters only (else "no error code" / "unrecognised"); an undecodable GoTrue body is a
    fixed "undecodable response". The AMQP URL is logged redacted.
  - **Accepted gaps:** an integer health value under an integer count key (`samples`,
    `days`, `bytes`) passes by type; only a known bound or the test's known values catch
    it. `err` is free text up to 1 KiB (including pgx's "unable to encode" quote of an
    argument, see above), covered only by the scans for the values a test knows.
    `client_request_id` accepts what httpx accepts (`[A-Za-z0-9._:-]{1,128}`, the
    contract of `X-Request-ID`), digits and dots included. The lines of the amqpbus and
    events panic paths, of auth, httpx and the account, admin and train handlers, and of
    `cmd/notify`'s stale-check loop have no key test yet.
- **Older lines:** before this change `scored day` carried the day's scores and inputs
  (readiness, state, recovery, strain, sleep, nap, sleep need, HRV, resting HR), a
  failed push's error the device token (`refresh push`, `sync stale` and the broker's
  retry lines), and a `bad event` line the number it could not decode, which the dead
  letter's `Ryft-Error` header kept as well. CloudWatch and the dead-letter queues keep
  14 days, so all of it is gone 14 days after the deploy of this change (the first
  `deploy: images` PR after it merged; `docs/STATUS.md` has the date).
- **A rescore by hand** (`scripts/rescore_all.sh`: `kubectl exec … /app rescore`)
  prints to the operator's terminal, not to the pod's log, so none of it reaches
  CloudWatch; its `scored day` lines hold no values now. Output saved from a run before
  this change holds every day's scores: delete it.
- **Where and how long:** stdout of each pod (on the node until the pod goes); CloudWatch
  Logs (Fluent Bit ships the `ryft-*` namespaces), **14 days**, encrypted with a key only
  `/ryft/*` groups may use (`infra/aws/kubernetes/logs.tf`, D52). **Not in Grafana
  Cloud** (the user's decision, 2026-10-21): `ryft-.*` is excluded from pod-log
  collection in Fleet Management, so Grafana Labs receives the services' metrics only
  (counters and route labels, no user data), and the privacy text names it for that. Check
  in Grafana → Explore → Loki that `{namespace=~"ryft-.*"}` returns nothing.
- **Who can read them:** the AWS account's administrators (CloudWatch, `kubectl logs`).
  Nobody else.

## Backups

**Supabase (EKS).** The database is Supabase's, and so are the backups: Database →
Backups. **The free plan keeps none and pauses a project after a week without
activity**, so the project moves to **Pro** before the first tester's data arrives: daily
backups kept 7 days; point-in-time recovery is an add-on (worth it once losing a day of
syncs matters more than its price; the app re-uploads only what HealthKit still holds).
There is no dump job in the cluster. Before restoring a backup:

1. In the SQL editor, run `SELECT * FROM deleted_users` and download the result as CSV.
   Accounts deleted after the backup was taken would otherwise come back.
2. Restore in the dashboard.
3. Insert the tombstones back: SQL editor → import the CSV into a temporary table,
   then `INSERT INTO deleted_users SELECT * FROM <tmp> ON CONFLICT (id) DO NOTHING`.
4. `argocd app sync ryft-platform` to run the migrate hook again, which sets the role
   passwords in case the backup predates them. The api's deletion reconciler erases the restored
   accounts at start-up.

**Restore drill, monthly** (Pro): restore the latest backup into a new scratch project
(Database → Backups → *Restore to a new project*). Then:

1. Compare `SELECT count(*)` of `users`, `samples` and `daily_scores` with production.
2. Run the services against it and smoke them: the compose stack in Supabase mode with
   the scratch project's pooler URL (`DATABASE_URL`, its `postgres` user) and project ref,
   then `make smoke-supabase` with the scratch project's `SUPABASE_URL` and anon key and
   the smoke user (restored with the backup, auth included):

   ```bash
   AUTH_MODE=supabase SUPABASE_PROJECT_REF=<scratch ref> DATABASE_URL='postgres://postgres.<scratch ref>:…@aws-…pooler.supabase.com:5432/postgres?sslmode=require' make up
   SUPABASE_URL=https://<scratch ref>.supabase.co SUPABASE_ANON_KEY=… SMOKE_EMAIL=… SMOKE_PASSWORD=… make smoke-supabase
   ```
3. Note the date and how long the restore took in `STATUS.md`, then delete the scratch
   project and `make down`: it holds real health data.

**In-cluster Postgres (`local-postgres`).** `pg-backup` in `ryft-postgres` runs
`pg_dump --format=custom` nightly at 03:30 Europe/Berlin into the `pg-backups` PVC
(10 Gi) and deletes dumps older than 14 days. Files are named
`ryft-YYYYMMDDTHHMMSSZ.dump`; a dump is written as `.partial` and renamed when complete.

```bash
kubectl -n ryft-postgres create job --from=cronjob/pg-backup pg-backup-manual   # back up now
kubectl -n ryft-postgres logs job/pg-backup-manual                              # lists /backups
```

The PVC lives in the cluster, often on the same disk as Postgres. Copy dumps off it:
`kubectl -n ryft-postgres cp pg-restore:/backups/<file> ./<file>`, using the restore pod
below.

### Restore (local-postgres)

Verified against the compose stack: restoring into an empty database and over an
existing one both reproduce every row. Dumps hold the `public` schema only, so they also
restore into Supabase. Restoring a plain-Postgres database into Supabase needs the RLS
step from `SUPABASE.md`, and then the migrate job. Accounts deleted after the dump was
taken come back with it, so keep the current tombstones across the restore (steps 2b
and 3b).

```bash
# 1. stop writers (HPA does not scale a Deployment that is at 0)
for s in api ingest scoring; do kubectl -n ryft-$s scale deploy/$s --replicas=0; done

# 2. a pod with the backups mounted, allowed to reach Postgres (label app: pg-backup)
kubectl apply -f - <<'EOF'
apiVersion: v1
kind: Pod
metadata: { name: pg-restore, namespace: ryft-postgres, labels: { app: pg-backup } }
spec:
  restartPolicy: Never
  automountServiceAccountToken: false
  securityContext: { runAsNonRoot: true, runAsUser: 70, runAsGroup: 70, fsGroup: 70, seccompProfile: { type: RuntimeDefault } }
  containers:
    - name: restore
      image: postgres:17-alpine
      command: ["sleep", "3600"]
      securityContext: { allowPrivilegeEscalation: false, capabilities: { drop: [ALL] } }
      env:
        - name: DATABASE_URL
          valueFrom: { secretKeyRef: { name: ryft-secrets, key: DATABASE_URL } }
      volumeMounts: [{ name: backups, mountPath: /backups }]
  volumes:
    - name: backups
      persistentVolumeClaim: { claimName: pg-backups }
EOF
kubectl -n ryft-postgres wait --for=condition=Ready pod/pg-restore
kubectl -n ryft-postgres exec pg-restore -- ls -lh /backups

# 2b. save the current tombstones (deleted accounts)
kubectl -n ryft-postgres exec pg-restore -- sh -c 'psql "$DATABASE_URL" -c "\copy deleted_users TO /tmp/tombstones.csv CSV"'

# 3. restore (drops and recreates every object in the dump)
kubectl -n ryft-postgres exec pg-restore -- sh -c 'pg_restore --clean --if-exists --no-owner -d "$DATABASE_URL" /backups/ryft-20261018T013000Z.dump'

# 3b. put the tombstones back
kubectl -n ryft-postgres exec pg-restore -- sh -c 'psql "$DATABASE_URL" -v ON_ERROR_STOP=1 \
  -c "CREATE TEMP TABLE t (LIKE deleted_users)" -c "\copy t FROM /tmp/tombstones.csv CSV" \
  -c "INSERT INTO deleted_users SELECT * FROM t ON CONFLICT (id) DO UPDATE SET auth_deleted_at = COALESCE(deleted_users.auth_deleted_at, EXCLUDED.auth_deleted_at)"'

# 4. clean up; re-run migrate (grants and role passwords), restart; the HPAs take api/ingest back to 2
kubectl -n ryft-postgres delete pod pg-restore
make k8s-apply-local
for s in api ingest scoring; do kubectl -n ryft-$s scale deploy/$s --replicas=1; done
```

To restore a dump from your machine instead, run
`kubectl -n ryft-postgres cp ./ryft-….dump pg-restore:/backups/` before step 3. The PVC
must have room.

## Upgrading

From the scaffold: api and ingest no longer set `replicas` (the HPA owns it). Because the
old manifest did, the first `kubectl apply` drops the field and the Deployments briefly
fall back to 1 replica until the HPA scales them to 2 — harmless, but expect it.

Migrations run in the migrate job before the services (they wait for it; advisory lock,
so two migrate runs at once are safe).
New columns on `daily_scores` (readiness, sleep detail, strain detail, baselines) are
filled when a day is scored (`steps` and `active_kcal` too), and source
de-duplication (`SCORING.md`) changes strain and sleep for anyone with two devices. Rescore history once after upgrading to this
version:

```bash
curl -fsS -X POST https://<host>/v1/recompute -H "Authorization: Bearer $ACCESS_TOKEN" \
  -H 'Content-Type: application/json' \
  -d "{\"from\":\"$(date -v-90d +%F 2>/dev/null || date -d '-90 days' +%F)\",\"to\":\"$(date +%F)\"}"
```
