# RYFT — operations

How to deploy, where the secrets come from, what the network policy allows, and how to
back up and restore. Manifests are kustomize-only and applied by hand.

```text
deploy/k8s/
  base/<service>/          namespace-neutral manifests per workload (ingest, scoring, api,
                           nats, migrate) and base/common (default-deny + DNS, per namespace)
  services/<service>/      puts one workload into its namespace ryft-<service>
  overlays/eks/            the five namespaces on EKS: Traefik + Let's Encrypt, gp3-encrypted,
                           pinned images; no Secrets, no Namespace objects (infra/vault owns them)
  overlays/vault-namespaces/<service>/   generated by infra/vault: the operator objects that
                           sync Secret ryft-secrets from the service's own Vault namespace
  overlays/local-postgres/ self-hosted: the same five namespaces plus ryft-postgres, API-key
                           auth, Secrets from scripts/local-secrets.sh
```

Render without applying: `kubectl kustomize deploy/k8s/overlays/eks`. Validate everything
offline: `make k8s-validate` (needs `kubeconform`).

## Namespaces and identities

Each workload runs in its own namespace, under its own service account, with its own
credentials and nothing else ([`ARCHITECTURE.md`](ARCHITECTURE.md#namespaces-and-trust)):

| Namespace | Workload | Vault namespace (HCP) | Holds |
| --- | --- | --- | --- |
| `ryft-ingest` | Deployment `ingest` | `admin/ryft/ingest` | DB role `ryft_ingest`, NATS user `ingest`, project ref |
| `ryft-scoring` | Deployment `scoring` | `admin/ryft/scoring` | DB role `ryft_scoring`, NATS user `scoring` |
| `ryft-api` | Deployment `api` | `admin/ryft/api` | DB role `ryft_api`, NATS user `api`, project ref, Supabase secret key, `ADMIN_API_KEY` |
| `ryft-notify` | Deployment `notify` | `admin/ryft/notify` | DB role `ryft_notify`, NATS user `notify`, the APNs key (once there is one) |
| `ryft-nats` | StatefulSet `nats` | `admin/ryft/nats` | bcrypt hashes of the four NATS passwords |
| `ryft-migrate` | Job `migrate` | `admin/ryft/migrate` | the database owner, the four role passwords |

On EKS `infra/vault` creates the namespaces (Pod Security `restricted`), the service
accounts, the Vault side and the operator manifests; the overlay only deploys workloads.

## EKS (api.ryftapp.de)

The AWS side is Terraform in three roots, then Vault in a fourth, each applied by hand
in order. Details, cost and teardown: [`infra/aws/README.md`](../infra/aws/README.md) and
[`infra/vault/README.md`](../infra/vault/README.md).

| Step | Command | Done when |
| --- | --- | --- |
| 0. State | the four HCP Terraform workspaces with execution mode Local, Terraform 1.16.6, `terraform login` | see **Terraform state** below; states from before HCP: `make tf-migrate-hcp` once |
| 1. Zone | `cd infra/aws/dns && terraform init && terraform apply` | `terraform output name_servers` lists four awsdns servers |
| 2. Delegate | GoDaddy → ryftapp.de → Nameservers → *I'll use my own* → those four | `dig NS ryftapp.de @a.nic.de +short` shows them |
| 3. Cluster | `cd infra/aws && terraform apply`, then `aws eks update-kubeconfig --region eu-central-1 --name ryft-prod-euc1 --alias ryft-prod-euc1` | `kubectl get nodes` Ready; `kubectl get sc` has no unencrypted default |
| 4. Edge | `cd infra/aws/kubernetes && terraform apply` (`acme_email` in tfvars) | `kubectl get clusterissuer` Ready; Traefik Service has an NLB hostname; `gp3-encrypted (default)`; `kubectl -n vault-secrets-operator-system get deploy` Ready |
| 5. Supabase | the checklist in [`SUPABASE.md`](SUPABASE.md) | project ref, pooler host, database password, secret key at hand |
| 6. Vault | `cd infra/vault && terraform apply` (values in `terraform.tfvars`) | `terraform output secret_keys` lists the keys per namespace; `kubectl get ns -l app.kubernetes.io/part-of=ryft` shows six |
| 7. Images | first CI run on GitHub pushes `ghcr.io/timkrebs/ryft/{ingest,scoring,api,notify,migrate}:<sha>` | set `newTag` in `deploy/k8s/overlays/eks/kustomization.yaml` to that SHA |
| 8. App | `make k8s-apply-eks` | see below |
| 9. Metrics | rotate the Grafana Cloud token, put it into `infra/vault`, `make monitoring-apply` | see **Monitoring** below |

Every Terraform root keeps its state in its HCP Terraform workspace (execution mode
Local): `terraform init` in a fresh checkout connects to it after `terraform login`.

`make k8s-apply-eks` runs these steps, waiting at each one:

0. It checks that kubectl is logged in (`k8s-check-auth`): kubectl takes its EKS
   token from `aws eks get-token`, so expired AWS credentials fail every call with
   "the server has asked for the client to provide credentials". Refresh them and
   check with `aws sts get-caller-identity`. Then `NATS_PASSWORD_*` (`k8s-check-nats-secret`,
   after step 1).
1. It applies the operator objects for every namespace and waits until each
   `ryft-secrets` exists; it stops at the first one that fails.
2. It deletes the finished migrate Job, since a Job's pod template is immutable.
3. It applies the first stage, NATS and the migrate Job (label `ryft.dev/stage=first`),
   and waits for the Job and NATS.
4. Only then it applies everything, so the services start after their role passwords
   exist, and waits for the four rollouts.

A new service (notify, M7) needs `infra/vault` applied first: that creates its
namespace, service account and secrets, writes its operator manifests to
`deploy/k8s/overlays/vault-namespaces/notify`, and gives NATS the password hash it
references. Without it `make k8s-apply-eks` stops at the missing directory.

**After an `infra/vault` apply that adds keys, let the operator sync before the
deploy.** It re-reads Vault only hourly, so the Kubernetes Secrets lag behind Vault.
NATS does not start while its config names a password its Secret lacks (2026-10-19:
`nats-0` crash-looped on `NATS_PASSWORD_NOTIFY`); `make k8s-apply-eks` now checks that
first (`k8s-check-nats-secret`) and stops with the fix:

```bash
kubectl -n vault-secrets-operator-system rollout restart deploy vault-secrets-operator-controller-manager
make k8s-check-nats-secret          # in a minute: every password nats.conf references is there
```

Order matters because Supabase's pooler blocks a database user for a while after
repeated failed logins (`ECIRCUITBREAKER`). Starting the services next to migrate on
the first deploy cost a few minutes of crash loops. The services now also retry the
database and NATS with backoff (5 s doubling to 60 s, jittered) instead of exiting,
and wait up to 10 minutes (startup probe).

```bash
make k8s-validate && make k8s-apply-eks
kubectl -n ryft-migrate logs job/migrate                     # "role password set" ×4, "schema current"
for s in ingest scoring api notify nats migrate; do kubectl -n ryft-$s get vaultstaticsecret,secret ryft-secrets; done
kubectl -n ryft-api get ingress,certificate                  # certificate READY True (DNS-01, ~1–2 min)
kubectl -n ryft-ingest get ingress,certificate
dig +short api.ryftapp.de                                    # NLB addresses (ExternalDNS, from the api Ingress)
curl -sI https://api.ryftapp.de/v1/me                        # 401 without a token
```

If a pod is stuck in `CreateContainerConfigError`, its namespace has no `ryft-secrets`
yet. `kubectl -n ryft-<svc> describe vaultstaticsecret ryft-secrets` shows why: usually
the Vault login. Check it by hand with `terraform -chdir=infra/vault output login_check`.
Kubernetes auth needs HCP Vault to reach the EKS API (TokenReview), so
`endpoint_public_access_cidrs` must admit Vault's egress addresses.

The public host only routes `/v1/*`; `/healthz`, `/readyz` and `/metrics` stay internal.
Port 80 is not exposed at all, so clients must use `https://`.

**Production smoke test.** `make smoke-supabase` runs against the public host with the
real project. It never touches real accounts:

```bash
SUPABASE_URL=https://<ref>.supabase.co SUPABASE_ANON_KEY=<publishable key> \
SMOKE_EMAIL=<test user> SMOKE_PASSWORD=<…> SUPABASE_SECRET_KEY=sb_secret_… \
API_URL=https://api.ryftapp.de INGEST_URL=https://api.ryftapp.de make smoke-supabase
```

1. **Contract checks:** it signs in the dedicated test user (`SUPABASE.md` checklist)
   and runs the full contract checks with 10 synthetic days in that account.
2. **Account flows** (`scripts/check_accounts.py`, needs `SUPABASE_SECRET_KEY`): it
   creates two throwaway, confirmed users through the Supabase admin API and signs them
   in. It checks that `/v1/me` creates the row, that one user's sync stays invisible to
   the other, and the `apple-authorization` endpoint. It then deletes both through
   `DELETE /v1/me` and checks the tokens get `401` and the Supabase sign-ins are gone.
   It cleans up even when a check fails.

The email-confirmation link itself is tested by hand from the app. Don't run plain
`make smoke` against the public host: it is for apikey mode.

**Rescoring** after a scoring rule or constant changed (`SCORING.md`):
`scripts/rescore_all.sh [days]` (default 400) runs `scoring rescore` inside the scoring
pod. Each user's last *days* days are rescored, oldest first, with scoring's own role;
the log shows `user rescored … n of N`, then `rescore done`. Locally:
`RESCORE_LOCAL=1 scripts/rescore_all.sh 30`.

**Learned sleep baseline** (`SCORING.md` → Sleep): scoring estimates it every Sunday from
04:00 local on its own. To run it for every user now (after a deploy, or after changing
its rules): `kubectl -n ryft-scoring exec deploy/scoring -- /app learn-baselines`
(locally `podman compose exec -T scoring /app learn-baselines`). The log ends with
`learn-baselines done` and the counts `applied` (the baseline moved; that user's last
7 days were rescored), `kept`, `insufficient` and `failed`. Users who set their baseline
by hand keep it.

Certificates: cert-manager renews 30 days before expiry. Each Ingress has its own
certificate for the same host, because a Secret cannot be shared across namespaces. To
try issuance without touching Let's Encrypt's production rate limits, point both
Ingress annotations at `letsencrypt-staging` first.

**Rotation.** The operator re-reads each namespace's `kv/config` hourly and restarts
the workload on a change.

- **Supabase secret key:** create a new one in Supabase, put it in `terraform.tfvars`,
  run `terraform apply`, then revoke the old one.
- **NATS password:** `terraform apply -replace='random_password.nats["api"]'`. The
  operator updates both sides within the hour. To skip the wait, delete
  `ryft-secrets` in `ryft-nats`, then in the service's namespace, and the operator
  re-creates them.
- **Database role password:** Postgres must get the new password before the service
  does, or its new pods fail their logins and may trip the pooler's circuit breaker.
  So force the order instead of waiting for the hourly refresh (here for `api`):

  ```bash
  terraform -chdir=infra/vault apply -replace='random_password.db["api"]'
  kubectl -n ryft-migrate delete secret ryft-secrets      # the operator re-creates it from Vault
  kubectl -n ryft-migrate wait --for=create secret/ryft-secrets --timeout=2m
  kubectl -n ryft-migrate delete job migrate --ignore-not-found
  kubectl apply -k deploy/k8s/overlays/eks -l ryft.dev/stage=first
  kubectl -n ryft-migrate wait --for=condition=complete job/migrate --timeout=10m   # Postgres has the new password
  kubectl -n ryft-api delete secret ryft-secrets          # re-created; the operator restarts the Deployment
  kubectl -n ryft-api rollout status deploy/api
  ```

  Open connections survive a password change, so the old pods keep serving until the new
  ones are ready. If a `wait --for=create` times out, the operator did not re-create the
  Secret at once; it does at the next hourly refresh at the latest
  (`kubectl -n ryft-<svc> describe vaultstaticsecret ryft-secrets`).

## Deploy and roll back

Every release is one image SHA for every service (`newTag` in
`deploy/k8s/overlays/eks/kustomization.yaml`), so rolling back is pinning the previous
one.

1. **Pin:** CI pushed `ghcr.io/timkrebs/ryft/*:<sha>`; set every `newTag` to it and
   commit (`make k8s-check-images` checks they are pinned and well-formed).
2. **Apply:** `make k8s-apply-eks` (migrate first, then the services; it waits for the
   rollouts).
3. **Smoke:** `make smoke-prod` with the dedicated smoke user (`SUPABASE_URL`,
   `SUPABASE_ANON_KEY`, `SMOKE_EMAIL`, `SMOKE_PASSWORD`, and once `ADMIN_API_KEY`, which
   gives the smoke user a one-use invite code so it passes with `BETA_GATE` on): the edge
   for api and ingest, sign-in, `/v1/me` (consent posted if missing), one tiny sync, and the day read back
   once scoring has scored it with the model `GET /v1/model` serves. After a model bump,
   `scripts/rescore_all.sh`.
4. **On failure:** set `newTag` back to the previous SHA (`git log -p
   deploy/k8s/overlays/eks/kustomization.yaml`), `make k8s-apply-eks`, `make smoke-prod`.

**No down-migrations.** Migrations only add (tables, nullable or defaulted columns,
grants, backfills; never a drop or a rename), so the previous release runs on the newer
schema: it ignores what it does not know, and its migrate job skips every file it has
and does not mind newer rows in `schema_migrations`. A rollback is therefore never a
schema change.

**Rolling back past the dead-letter stream** (to a release before `ops: alerts, push
envs, rollback, DLQ`): that release's scoring sets stream `RYFT` back to `ryft.>`, which
overlaps `RYFT_DLQ`, and NATS refuses it, so scoring would not start. Drop the dead-letter
stream first, with the current release:

```bash
kubectl -n ryft-scoring exec deploy/scoring -- /app dlq          # keep a copy of what is in it
kubectl -n ryft-scoring exec deploy/scoring -- /app dlq drop
```

## Dead letters

An event that cannot be handled, unparseable or failed on its tenth delivery (notify:
fifteenth), is not dropped: it moves to stream `RYFT_DLQ` as `ryft.dlq.<subject>`
(`ryft.dlq.ingested`, …) with the subject, consumer, delivery count and error in its
headers, and stays 30 days (64 MiB at most, oldest first out; D84). The alert
`DeadLetters` fires on the first one. scoring's own NATS user reads and re-drives them:

```bash
kubectl -n ryft-scoring exec deploy/scoring -- /app dlq                   # one JSON line each: seq, time, subject, error, data
kubectl -n ryft-scoring exec deploy/scoring -- /app dlq redrive 7         # handle scoring's again (or: all); deleted when it works
kubectl -n ryft-scoring exec deploy/scoring -- /app dlq delete all        # e.g. notify's: a morning push hours late is wrong
```

Re-drive after fixing the cause (a deploy, a data fix). Scoring's events only name a user
and days, so `POST /v1/recompute` or `scripts/rescore_all.sh` repair the same thing if a
letter is gone. notify's are listed and deleted, never re-sent.

## Self-hosted (overlays/local-postgres)

In-cluster Postgres in `ryft-postgres`, the shared API key instead of Supabase Auth,
and nothing safe to expose. It uses the same five namespaces, roles, NATS users and
policies as EKS, but kustomize creates the namespaces and service accounts.
`scripts/local-secrets.sh` writes one env file per namespace with random passwords
(git-ignored, refuses to overwrite).

```bash
make k8s-apply-local          # generates the secrets once, then applies
kubectl -n ryft-migrate wait --for=condition=complete job/migrate --timeout=10m
grep API_KEY deploy/k8s/overlays/local-postgres/secrets/api.env   # the bearer
```

An install from before the per-namespace layout ran everything in namespace `ryft`.
`kubectl apply` does not remove it: once the data has moved (backup and restore below),
delete it with `kubectl delete namespace ryft`.

## Network policy

Every namespace starts with `default-deny` (no ingress, no egress) and `allow-dns`
(`base/common`). Each workload then allows exactly its own flows
(`base/<service>/networkpolicy.yaml`):

| Workload | In | Out |
| --- | --- | --- |
| ingest, api | 8080 from Traefik in `kube-system` (or ingress-nginx in `ingress-nginx`); 9090 (`/metrics`) from namespace `monitoring`, and on EKS from the VPC range (the host-network collector) | NATS (`ryft-nats`, 4222), TCP 443 + 5432 to public addresses (Supabase Auth, the pooler) |
| scoring | 9090 from `monitoring` (and the VPC range on EKS) | NATS (4222), TCP 5432 to public addresses |
| notify | 9090 from `monitoring` (and the VPC range on EKS) | NATS (4222), TCP 5432 (the pooler) and 443 (APNs: `api.push.apple.com`, `api.sandbox.push.apple.com`) to public addresses |
| web (`ryft-web`) | 8080 from Traefik | nothing |
| nats | 4222 from the `ingest`, `scoring`, `api` and `notify` pods, each in its own namespace | nothing |
| migrate | nothing | TCP 5432 to public addresses |
| postgres (`local-postgres`) | 5432 from the five client namespaces and the backup pods | nothing |

"Public addresses" means `0.0.0.0/0` minus RFC 1918, CGNAT and link-local ranges, so no
workload can reach anything inside the VPC or the cluster on those ports. NetworkPolicy
cannot name hosts, so the ports are the restriction for the internet. The
`local-postgres` overlay adds `allow-local-postgres` egress for the in-cluster
database. Kubelet probes come from the node and are admitted by the EKS VPC CNI (and
k3s, Calico, Cilium). Namespaces are matched by `kubernetes.io/metadata.name`, which the
API server sets and nobody can relabel.

Adjust the `from` of ingest/api for another Ingress controller, or add a `cloudflared`
peer if a Cloudflare tunnel targets the services directly.

### Edge rate limit

Before any token is checked, Traefik limits each client IP to 20 requests a second on
average, with bursts of 50 (`overlays/eks/ratelimit.yaml`, a `Middleware` in `ryft-api`,
`ryft-ingest` and `ryft-web`). Each of the two Traefik replicas counts on its own, so
the effective limit is up to twice that. Over it, Traefik answers `429` with a
plain-text body. The NLB preserves client addresses, which this needs (a target-group
attribute in `infra/aws/kubernetes`). Check it from one machine, expecting `429`s
after the first ~100:

```bash
for i in $(seq 1 150); do curl -s -o /dev/null -w '%{http_code}\n' https://api.ryftapp.de/v1/me; done | sort | uniq -c
```

The services' own per-user limit (D36) applies after the token, so the two complement
each other.

## Beta

Friends on TestFlight (D78–D83). Everything here uses the api's `ADMIN_API_KEY`:

```bash
ADMIN=$(terraform -chdir=infra/vault output -raw admin_api_key)    # locally: dev-admin-key-change-me-0123456789abcdef
API=https://api.ryftapp.de
```

**Consent.** `POST /v1/sync` answers `403 consent_required` until the account consented
to the current `PRIVACY_POLICY_VERSION` (configmaps of api and ingest, `2026-10-20`), and
scoring computes nothing for an account without consent. Nothing was backfilled, so the
operator's own account consents once too: with the app build that has the consent
screen, or by hand with its access token:

```bash
curl -s -X POST -H "Authorization: Bearer $TOKEN" $API/v1/me/consent -d '{"policy_version": "2026-10-20"}'
```

A new policy text: change `PRIVACY_POLICY_VERSION` in both configmaps (and the page),
deploy; every tester consents again before the next sync, `ryft_gate_refusals_total{code=
"consent_required"}` shows who has not yet.

**The gates and their modes** (D87). Two checks, each `off`, `warn` or `on`, set in
`infra/vault/terraform.tfvars` → `shared_secrets` (the user applies):

| Variable | Checks | Default | `on` | `warn` |
| --- | --- | --- | --- | --- |
| `BETA_GATE` | a redeemed code or an operator grant (api, ingest) | `off` | `403 invite_required` everywhere but onboarding | served, `X-RYFT-Gate: invite_required` |
| `CONSENT_ENFORCE` | a consent to the current policy (ingest, scoring) | `on` | `403 consent_required` on sync, nothing scored | synced and scored, `X-RYFT-Gate: consent_required` |

`warn` is for before the beta opens, while the app cannot pass a gate yet (it has no
invite or consent screen): the operator's own account keeps working, and every request
that would have been refused is counted (`ryft_gate_refusals_total{mode="warn"}`) and
flagged on its access line (`gate`). **Before the first external invite both are `on`,
and `make smoke-prod` proves it:** with `ADMIN_API_KEY` it takes the smoke user's consent
and access away for one request each, reports what each gate did, and gives them back;
`SMOKE_EXPECT_GATES=on make smoke-prod` fails unless both refused.

```bash
# infra/vault/terraform.tfvars:  shared_secrets = { BETA_GATE = "warn", CONSENT_ENFORCE = "warn" }   (later both "on")
(cd infra/vault && terraform plan -out=tfplan && terraform apply tfplan)
kubectl -n vault-secrets-operator-system rollout restart deploy vault-secrets-operator-controller-manager
# the operator rewrites ryft-secrets and restarts api, ingest and scoring; then:
for s in api ingest scoring; do kubectl -n ryft-$s logs -l app=$s --tail=-1 --since=10m | grep '"msg":"beta"'; done
ADMIN_API_KEY=$ADMIN make smoke-prod          # … gates: invite warn, consent warn
```

Accounts that existed at migration 0017 keep access. One account without a code gets it
from the operator (audited, D88):

```bash
curl -s -X POST   -H "Authorization: Bearer $ADMIN" $API/v1/admin/users/<id or first 8 digits>/access   # 204
curl -s -X DELETE -H "Authorization: Bearer $ADMIN" $API/v1/admin/users/<id>/access                     # takes it away
curl -s -H "Authorization: Bearer $ADMIN" "$API/v1/admin/audit?since=2026-10-21" | jq                 # who did what, when
```

```bash
# A code for one person (or max_uses for a group), optionally expiring:
curl -s -X POST -H "Authorization: Bearer $ADMIN" $API/v1/admin/invites \
  -d '{"note": "Anna", "max_uses": 1, "expires_at": "2026-12-31T23:59:59Z"}' | jq -r .code    # RYFT-7K3M-QX9P
curl -s -H "Authorization: Bearer $ADMIN" $API/v1/admin/invites | jq                           # uses so far
curl -s -X DELETE -H "Authorization: Bearer $ADMIN" $API/v1/admin/invites/RYFT-7K3M-QX9P
```

**Whose data is broken.** `scripts/beta_report.sh` prints one line per tester from
`GET /v1/admin/users`: short id, created, provider, beta access, consent version, app
version, last sync, sources, days scored / nights with stages / days with HRV in the
last 14 (UTC) days, calibrating, max-HR source, open feedback. Signs: `sources` without
`hr` (strain and recovery stay empty; the app shows `no-heart-rate-source`), `staged/14`
at 0 with `sleep` in the sources (a tracker writing only "asleep"), `scored/14` well under
the days since the first sync (syncs failing: `consent_required`, or the app's background
refresh). Emails only with `--emails` (`?emails=1`); every call is logged with the admin
key's fingerprint (`admin_key`).

```bash
ADMIN_API_KEY=$ADMIN scripts/beta_report.sh
ADMIN_API_KEY=$ADMIN scripts/beta_report.sh feedback 2026-10-20     # reports since a day
curl -s -X POST -H "Authorization: Bearer $ADMIN" $API/v1/admin/feedback/42/resolve    # no longer open
```

**Feedback** (`POST /v1/feedback`, 10 per tester a day) carries `request_ids`: search the
logs for them (`{namespace="ryft-api"} |= "<request id>"`, and the same id in ingest and
scoring) to see what the tester saw. `ryft_feedback_received_total` going up alerts the
operator (Monitoring).

## Feature flags

`GET /v1/config` serves the flags in table `feature_flags` (D69). Change them with the
admin routes and the api's `ADMIN_API_KEY` (generated by `infra/vault`):

```bash
ADMIN=$(terraform -chdir=infra/vault output -raw admin_api_key)    # locally: dev-admin-key-change-me-0123456789abcdef
API=https://api.ryftapp.de
curl -s -H "Authorization: Bearer $ADMIN" $API/v1/admin/flags | jq            # every flag
# On for two testers only (their user IDs: GET /v1/me → id):
curl -s -X PUT -H "Authorization: Bearer $ADMIN" $API/v1/admin/flags/today.redesign \
  -d '{"enabled": true, "rollout_pct": 0, "allow_user_ids": ["<uuid>", "<uuid>"]}'
# 10 % of everyone, then everyone:
curl -s -X PUT -H "Authorization: Bearer $ADMIN" $API/v1/admin/flags/today.redesign -d '{"enabled": true, "rollout_pct": 10}'
curl -s -X PUT -H "Authorization: Bearer $ADMIN" $API/v1/admin/flags/today.redesign -d '{"enabled": true, "rollout_pct": 100}'
# Kill switch (off for everyone, testers included):
curl -s -X PUT -H "Authorization: Bearer $ADMIN" $API/v1/admin/flags/today.redesign -d '{"enabled": false, "rollout_pct": 100}'
curl -s -X DELETE -H "Authorization: Bearer $ADMIN" $API/v1/admin/flags/some.old_flag      # 204
```

`PUT` replaces the whole flag (`enabled` and `rollout_pct` required, a missing
allow-list is empty) and answers `201` for a new key, `200` otherwise; the api logs
every change (`msg="feature flag set"`). The app caches its answer for up to six hours,
so a change reaches everyone within that. Rotate the key with
`terraform apply -replace='random_password.admin_key["api"]'` in `infra/vault`.

## Push (APNs)

notify sends with token-based APNs (D73). Until the key exists it runs and counts
`ryft_push_notifications_total{result="unconfigured"}`; tokens and preferences are
stored meanwhile. Once the Apple Developer Program membership is active:

1. Apple Developer → Certificates, IDs & Profiles → Keys → **+**, enable **Apple Push
   Notifications service (APNs)**, download `AuthKey_<key id>.p8` (once). The same key
   serves sandbox and production. The App ID `dev.timkrebs.ryft` needs the Push
   Notifications capability (the app side adds it in Xcode).
2. In `infra/vault/terraform.tfvars`, `service_secrets.notify = { APNS_KEY_ID, APNS_TEAM_ID,
   APNS_KEY_P8 }` (all three; the .p8 as PEM or base64), then plan and apply. The
   operator restarts notify; its log says `apns configured`.
3. Check: register a debug build (`env: sandbox`), then
   `kubectl -n ryft-notify logs deploy/notify | grep push` after the next morning sync,
   and `ryft_push_notifications_total{result="sent"}` in Grafana.

Revoking the key in Apple Developer makes APNs answer `403` (alert `APNsRejectsOurKey`).
A device token APNs reports gone is deleted (`ryft_push_tokens_pruned_total`). Raise
`push.enabled` (above) once sending works, so the app starts asking for permission.

## Scaling and disruptions

api and ingest run 2–4 replicas under a CPU HPA (70 % of the 50m request; needs
metrics-server), with a `PodDisruptionBudget` of `minAvailable: 1`, spread across nodes
when there are several. On a **single-node** cluster a drain blocks on the second pod,
because the first has nowhere to reschedule. Use `kubectl drain --disable-eviction`, or
`kubectl -n ryft-api delete pdb api; kubectl -n ryft-ingest delete pdb ingest` before
maintenance and re-apply afterwards. Pods that are not ready never count
(`unhealthyPodEvictionPolicy: AlwaysAllow`): during an outage, when no pod is ready, a
drain or a node group update still goes through. Their Deployments carry no `replicas`, so
re-applying never fights the HPA. scoring stays at one replica: it owns the 15-minute
timer and processes recompute ranges in order. NATS is a single-replica StatefulSet.

## Monitoring (Grafana Cloud)

The collector is Grafana's `k8s-monitoring` chart with the onboarding's preset, in
namespace `monitoring`: the collectors `alloy-daemonset` and `alloy-deployment`,
node-exporter, kube-state-metrics, Beyla, Kepler, OpenCost and k8s-manifest-tail, as the
onboarding deploys them (D64). The collector names matter: Fleet Management assigns
its Kubernetes pipelines by them. OpenCost reads with the same token and the stack's
Prometheus user (`PROM_USERNAME`, also in Vault). The Fleet
Management token lives in Vault like every other credential (D51), and the operator
restarts both collectors when it changes. It is never passed on a command line:

1. **Rotate the token** that was used during onboarding (it was on a command line and
   in a chat): Grafana Cloud → your stack → Access policies → the Kubernetes Monitoring
   policy → create a new token, then delete the old one.
2. **Vault:** put the new token into `infra/vault/terraform.tfvars` as
   `service_secrets.monitoring = { GC_TOKEN = "glc_…", PROM_USERNAME = "3085952" }`. Remove the hand-made secret
   (`vault kv metadata delete …` under `admin/ryft/…/grafana-cloud`). If you created
   the Vault namespace `admin/ryft/monitoring` by hand, import it instead of
   deleting it: `terraform import 'vault_namespace.service["monitoring"]' ryft/monitoring`.
   Do the same for an existing `monitoring` Kubernetes namespace:
   `terraform import 'kubernetes_namespace_v1.service["monitoring"]' monitoring`.
3. `terraform plan` and `apply` in `infra/vault`. This creates the Vault namespace, its
   auth role, `kv/config {GC_TOKEN}`, the namespace `monitoring` (Pod Security
   privileged) and `deploy/k8s/overlays/vault-namespaces/monitoring`.
4. `make monitoring-apply`: it applies the operator objects, waits for
   `monitoring/ryft-secrets`, then runs
   `helm upgrade --install grafana-cloud grafana/k8s-monitoring --version 4.5.3`.
5. **In Grafana Cloud:**
   - In the Fleet Management pipelines for pod logs, exclude namespaces matching
     `ryft-.*`; RYFT's logs go to CloudWatch.
   - Load the alert rules: `make alerts-apply` (OBSERVABILITY → Alerts), then a contact
     point (email and the Grafana mobile app) and a notification policy for
     `severity` `critical`, `warning` and `info`.
   - Remove collectors that no longer report from Fleet Management → Collectors (the
     single `alloy` collector before 2026-10-19).
   - Check that the cluster appears in Kubernetes Monitoring, that
     `ryft_http_requests_total` has series, and that `{namespace=~"ryft-.*"}` in Logs
     Explore is empty.

**What the collector can do:** it runs as root on the host network with the nodes'
log files, cgroups and storage mounted. Beyla reads all pod traffic through eBPF,
including RYFT's routes and durations, and the SDK injector's webhook may modify pods
that opt in by annotation (no RYFT pod does). Its configuration comes from Grafana
Cloud. Access to the Grafana stack is therefore access to the cluster's telemetry: keep
the stack's members to yourself.

## Terraform state

Every root keeps its state in its own **HCP Terraform** workspace (organization
`tim-krebs-org`, D56). HCP stores, locks and versions the state and records every run.
Plans and applies run on your machine (execution mode **Local**), with your AWS and
Vault credentials; HCP never holds cloud credentials.

| Root | Workspace |
| --- | --- |
| `infra/aws` | `ryft-prod-euc1-platform` |
| `infra/aws/dns` | `ryft-prod-euc1-dns` |
| `infra/aws/kubernetes` | `ryft-prod-euc1-kubernetes` |
| `infra/vault` | `ryft-prod-euc1-vault` |

**Moving the states there (once):**

1. In HCP Terraform, create the two missing workspaces (`-dns`, `-kubernetes`) as
   CLI-driven workspaces. On all four, set *Settings → General → Execution Mode* to
   **Local** and the Terraform version to **1.16.6**. Restrict team access: the vault
   workspace's state contains every RYFT secret.
2. Install exactly Terraform 1.16.6 (`tfenv install 1.16.6 && tfenv use 1.16.6`, or the
   binary from releases.hashicorp.com), then run `terraform login`.
3. `make tf-migrate-hcp`. For each root it:
   - checks the workspace exists and runs locally;
   - copies the last full local state to `~/.ryft-tfstate-rescue/<time>/` (that is
     `terraform.tfstate.backup` where the S3 attempt emptied `terraform.tfstate`);
   - moves the root's S3 backend cache (`.terraform/terraform.tfstate`, settings only)
     next to that copy and runs `terraform init`, so nothing comes over from S3;
   - pushes the state into the empty workspace and checks the resource count.

   A workspace that already holds state is left alone.
4. **`infra/vault` only:** the failed apply of 2026-10-19 created the Kubernetes
   namespace `monitoring`, which the old state does not know:
   `terraform import 'kubernetes_namespace_v1.service["monitoring"]' monitoring`.
5. `terraform plan` in every root. Nothing that already exists may show as *create*.
6. Delete the old local `terraform.tfstate*` and the rescue copies. They contain the
   same secrets in plaintext. Done 2026-10-19, also the `tfplan` files.
7. Retire the S3 bucket of the earlier attempt. Done 2026-10-19: the bootstrap root
   destroyed it and was then removed from the repository with `infra/backend.hcl`
   (D54).

If `terraform init` ever offers to *migrate* state from another backend, answer **no**
and use the steps above: the S3 bucket holds only a partial Vault state.

**CI** checks every root offline on every push: `fmt`, `init -backend=false`,
`validate`, `tflint` and the mocked `terraform test`, with Terraform 1.16.6. It has no
HCP token and no cloud credentials and never touches a workspace.

## Data protection (logs)

- **What is logged:** one access line per request (method, path, status, bytes, duration,
  route, request id, user id) and what the services decide (a sync's counts, a scored day
  with its scores, errors). **Never logged:** request or response bodies, query strings,
  tokens, the `Authorization` header, email addresses, feedback messages, invite notes.
  Paths carry dates and resource ids (`/v1/days/2026-10-19`, `/v1/workouts/<uuid>`).
  scoring's `scored day` lines carry a user's daily scores next to the user id: the logs
  are health data.
- **Where and how long:** stdout of each pod (on the node until the pod goes); CloudWatch
  Logs (Fluent Bit ships the `ryft-*` namespaces), **14 days**, encrypted with a key only
  `/ryft/*` groups may use (`infra/aws/kubernetes/logs.tf`, D52). By the user's choice
  (2026-10-19) the pod logs also reach **Grafana Cloud** (stack in eu-west-2, London):
  retention there is the stack plan's (the free tier keeps logs 14 days; check under
  Billing), and Grafana Labs is then a processor of health data, so the privacy policy
  names it. Excluding `ryft-.*` from pod-log collection in Fleet Management ends that.
- **Who can read them:** the AWS account's administrators (CloudWatch, `kubectl logs`)
  and the Grafana stack's members. Nobody else has either.

## Backups

**Supabase (EKS).** The database is Supabase's, and so are the backups: Database →
Backups. **The free plan keeps none and pauses a project after a week without
activity**, so the project moves to **Pro** before the first tester's data arrives: daily
backups kept 7 days; point-in-time recovery is an add-on (worth it once losing a day of
syncs matters more than its price; the app re-uploads only what HealthKit still holds).
There is no dump job in the cluster. Before restoring a backup:

1. In the SQL editor, run `SELECT * FROM deleted_users` and download the result as CSV.
   Accounts deleted after the backup was taken would otherwise come back.
2. Restore in the dashboard.
3. Insert the tombstones back: SQL editor → import the CSV into a temporary table,
   then `INSERT INTO deleted_users SELECT * FROM <tmp> ON CONFLICT (id) DO NOTHING`.
4. `make k8s-apply-eks` to run the migrate job again, which sets the role passwords in
   case the backup predates them. The api's deletion reconciler erases the restored
   accounts at start-up.

**Restore drill, monthly** (Pro): restore the latest backup into a new scratch project
(Database → Backups → *Restore to a new project*). Then:

1. Compare `SELECT count(*)` of `users`, `samples` and `daily_scores` with production.
2. Run the services against it and smoke them: the compose stack in Supabase mode with
   the scratch project's pooler URL (`DATABASE_URL`, its `postgres` user) and project ref,
   then `make smoke-supabase` with the scratch project's `SUPABASE_URL` and anon key and
   the smoke user (restored with the backup, auth included):

   ```bash
   AUTH_MODE=supabase SUPABASE_PROJECT_REF=<scratch ref> DATABASE_URL='postgres://postgres.<scratch ref>:…@aws-…pooler.supabase.com:5432/postgres?sslmode=require' make up
   SUPABASE_URL=https://<scratch ref>.supabase.co SUPABASE_ANON_KEY=… SMOKE_EMAIL=… SMOKE_PASSWORD=… make smoke-supabase
   ```
3. Note the date and how long the restore took in `STATUS.md`, then delete the scratch
   project and `make down`: it holds real health data.

**In-cluster Postgres (`local-postgres`).** `pg-backup` in `ryft-postgres` runs
`pg_dump --format=custom` nightly at 03:30 Europe/Berlin into the `pg-backups` PVC
(10 Gi) and deletes dumps older than 14 days. Files are named
`ryft-YYYYMMDDTHHMMSSZ.dump`; a dump is written as `.partial` and renamed when complete.

```bash
kubectl -n ryft-postgres create job --from=cronjob/pg-backup pg-backup-manual   # back up now
kubectl -n ryft-postgres logs job/pg-backup-manual                              # lists /backups
```

The PVC lives in the cluster, often on the same disk as Postgres. Copy dumps off it:
`kubectl -n ryft-postgres cp pg-restore:/backups/<file> ./<file>`, using the restore pod
below.

### Restore (local-postgres)

Verified against the compose stack: restoring into an empty database and over an
existing one both reproduce every row. Dumps hold the `public` schema only, so they also
restore into Supabase. Restoring a plain-Postgres database into Supabase needs the RLS
step from `SUPABASE.md`, and then the migrate job. Accounts deleted after the dump was
taken come back with it, so keep the current tombstones across the restore (steps 2b
and 3b).

```bash
# 1. stop writers (HPA does not scale a Deployment that is at 0)
for s in api ingest scoring; do kubectl -n ryft-$s scale deploy/$s --replicas=0; done

# 2. a pod with the backups mounted, allowed to reach Postgres (label app: pg-backup)
kubectl apply -f - <<'EOF'
apiVersion: v1
kind: Pod
metadata: { name: pg-restore, namespace: ryft-postgres, labels: { app: pg-backup } }
spec:
  restartPolicy: Never
  automountServiceAccountToken: false
  securityContext: { runAsNonRoot: true, runAsUser: 70, runAsGroup: 70, fsGroup: 70, seccompProfile: { type: RuntimeDefault } }
  containers:
    - name: restore
      image: postgres:17-alpine
      command: ["sleep", "3600"]
      securityContext: { allowPrivilegeEscalation: false, capabilities: { drop: [ALL] } }
      env:
        - name: DATABASE_URL
          valueFrom: { secretKeyRef: { name: ryft-secrets, key: DATABASE_URL } }
      volumeMounts: [{ name: backups, mountPath: /backups }]
  volumes:
    - name: backups
      persistentVolumeClaim: { claimName: pg-backups }
EOF
kubectl -n ryft-postgres wait --for=condition=Ready pod/pg-restore
kubectl -n ryft-postgres exec pg-restore -- ls -lh /backups

# 2b. save the current tombstones (deleted accounts)
kubectl -n ryft-postgres exec pg-restore -- sh -c 'psql "$DATABASE_URL" -c "\copy deleted_users TO /tmp/tombstones.csv CSV"'

# 3. restore (drops and recreates every object in the dump)
kubectl -n ryft-postgres exec pg-restore -- sh -c 'pg_restore --clean --if-exists --no-owner -d "$DATABASE_URL" /backups/ryft-20261018T013000Z.dump'

# 3b. put the tombstones back
kubectl -n ryft-postgres exec pg-restore -- sh -c 'psql "$DATABASE_URL" -v ON_ERROR_STOP=1 \
  -c "CREATE TEMP TABLE t (LIKE deleted_users)" -c "\copy t FROM /tmp/tombstones.csv CSV" \
  -c "INSERT INTO deleted_users SELECT * FROM t ON CONFLICT (id) DO UPDATE SET auth_deleted_at = COALESCE(deleted_users.auth_deleted_at, EXCLUDED.auth_deleted_at)"'

# 4. clean up; re-run migrate (grants and role passwords), restart; the HPAs take api/ingest back to 2
kubectl -n ryft-postgres delete pod pg-restore
make k8s-apply-local
for s in api ingest scoring; do kubectl -n ryft-$s scale deploy/$s --replicas=1; done
```

To restore a dump from your machine instead, run
`kubectl -n ryft-postgres cp ./ryft-….dump pg-restore:/backups/` before step 3. The PVC
must have room.

## Upgrading

From the scaffold: api and ingest no longer set `replicas` (the HPA owns it). Because the
old manifest did, the first `kubectl apply` drops the field and the Deployments briefly
fall back to 1 replica until the HPA scales them to 2 — harmless, but expect it.

Migrations run in the migrate job before the services (they wait for it; advisory lock,
so two migrate runs at once are safe).
New columns on `daily_scores` (readiness, sleep detail, strain detail, baselines) are
filled when a day is scored (`steps` and `active_kcal` too), and source
de-duplication (`SCORING.md`) changes strain and sleep for anyone with two devices. Rescore history once after upgrading to this
version:

```bash
curl -fsS -X POST https://<host>/v1/recompute -H "Authorization: Bearer $ACCESS_TOKEN" \
  -H 'Content-Type: application/json' \
  -d "{\"from\":\"$(date -v-90d +%F 2>/dev/null || date -d '-90 days' +%F)\",\"to\":\"$(date +%F)\"}"
```
