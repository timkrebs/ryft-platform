# RYFT — operations

How to deploy, where the secrets come from, what the network policy allows, and how to
back up and restore. Manifests are kustomize-only and applied by hand.

```text
deploy/k8s/
  base/<service>/          namespace-neutral manifests per workload (ingest, scoring, api,
                           notify, migrate, smoke, web) and base/common (default-deny + DNS)
  services/<service>/      puts one workload into its namespace ryft-<service>
  overlays/eks/            the five namespaces on EKS: Traefik + Let's Encrypt, gp3-encrypted,
                           pinned images; no Secrets, no Namespace objects (infra/vault owns them)
  overlays/vault-namespaces/<service>/   generated by infra/vault: the operator objects that
                           sync Secret ryft-secrets from the service's own mount kv-<service>
                           on the in-cluster Vault
  overlays/local-postgres/ self-hosted: the same five namespaces plus ryft-postgres, API-key
                           auth, one RabbitMQ node, Secrets from scripts/local-secrets.sh
deploy/rabbitmq/           the broker (RabbitMQ section below): operators/, cluster/,
                           topology/ (generated), clients/ (the services' certificates)
```

Render without applying: `kubectl kustomize deploy/k8s/overlays/eks`. Validate everything
offline: `make k8s-validate` (needs `kubeconform`).

## Namespaces and identities

Each workload runs in its own namespace, under its own service account, with its own
credentials and nothing else ([`ARCHITECTURE.md`](ARCHITECTURE.md#namespaces-and-trust)):

| Namespace | Workload | Vault mount (in the cluster) | Holds |
| --- | --- | --- | --- |
| `ryft-ingest` | Deployment `ingest` | `kv-ingest` | DB role `ryft_ingest`, RabbitMQ user `ingest`, project ref |
| `ryft-scoring` | Deployment `scoring` | `kv-scoring` | DB role `ryft_scoring`, RabbitMQ user `scoring` |
| `ryft-api` | Deployment `api` | `kv-api` | DB role `ryft_api`, RabbitMQ user `api`, project ref, Supabase secret key, `ADMIN_API_KEY` |
| `ryft-notify` | Deployment `notify` | `kv-notify` | DB role `ryft_notify`, RabbitMQ user `notify`, the APNs key (once there is one) |
| `ryft-rabbitmq` | RabbitmqCluster `rabbitmq` (three pods) | `kv-rabbitmq` | the four users' passwords (Secrets `amqp-user-<service>`, for the Topology Operator) |
| `ryft-smoke` | Job `smoke` (Argo CD's PostSync hook) | `kv-smoke` | the smoke user's sign-in |
| `ryft-migrate` | Job `migrate` | `kv-migrate` | the database owner, the four role passwords |

Each mount holds one secret `config` (the broker's also `amqp-user-<client>`), readable only
through the service's Kubernetes auth role and policy of the same name (D187, D207;
`infra/vault/k8s.tf`). Community Edition has no Vault namespaces: the mount, the role and
the policy are the isolation. `monitoring` and the import service have theirs the same way.

On EKS `infra/vault` creates the namespaces (Pod Security `restricted`), the service
accounts, the Vault side and the operator manifests; the overlay only deploys workloads.

Every Terraform root keeps its state in its HCP Terraform workspace (execution mode
Local): `terraform init` in a fresh checkout connects to it after `terraform login`.

Argo CD deploys the app (step 8; **Deploy and roll back**). Its waves keep the order
the break-glass `make k8s-apply-eks KUBE_CONTEXT=<context>` enforces by hand, which runs
these steps, waiting at each one. Every Makefile target and operator script that talks to
a cluster needs it named (`KUBE_CONTEXT=<context>`, one of `kubectl config get-contexts -o
name`; production's is `ryft-prod-euc1` if you kept the alias `aws eks update-kubeconfig
--alias` wrote) and refuses to start without it; kubectl's current context is never used
(`scripts/lib/kube.sh`), and the self-hosted targets refuse a context that looks like EKS
(its name, cluster, server or token helper: a heuristic, not a proof).

0. It checks that kubectl is logged in (`k8s-check-auth`): kubectl takes its EKS
   token from `aws eks get-token`, so expired AWS credentials fail every call with
   "the server has asked for the client to provide credentials". Refresh them and
   check with `aws sts get-caller-identity`.
1. It applies the operator objects for every namespace and waits until each
   `ryft-secrets` (and in `ryft-rabbitmq` each `amqp-user-<service>`) exists; it stops
   at the first one that fails.
2. RabbitMQ (`make k8s-rabbitmq KUBE_CONTEXT=<context>`): the operators, then `deploy/rabbitmq`, and waits until
   all three nodes are ready.
3. It deletes the finished migrate Job, since a Job's pod template is immutable, applies
   the first stage, the migrate Job (label `ryft.dev/stage=first`), and waits for it.
4. Only then it applies everything, so the services start after their role passwords
   exist, and waits for the four rollouts.

A new service (notify, M7) needs `infra/vault` applied first: that creates its
namespace, service account and secrets, writes its operator manifests to
`deploy/k8s/overlays/vault-namespaces/notify`, and gives the broker's namespace its
RabbitMQ password (a new user also needs its `User`, permissions and certificate in
`amqpbus/topology.go` and `deploy/rabbitmq/clients`). Without it the `vault-notify`
application cannot render (and `make k8s-apply-eks` stops at the missing directory).

**After an `infra/vault` apply that adds keys, let the operator sync before the
deploy.** It re-reads Vault only hourly, so the Kubernetes Secrets lag behind Vault
(2026-10-19, NATS then: it crash-looped on a password its Secret did not have yet):

```bash
kubectl -n vault-secrets-operator-system rollout restart deploy vault-secrets-operator-controller-manager
```

Order matters because Supabase's pooler blocks a database user for a while after
repeated failed logins (`ECIRCUITBREAKER`). Starting the services next to migrate on
the first deploy cost a few minutes of crash loops. The services now also retry the
database and RabbitMQ with backoff (5 s doubling to 60 s, jittered) instead of exiting,
and wait up to 10 minutes (startup probe).

```bash
make k8s-validate && make k8s-apply-eks KUBE_CONTEXT=<context>
kubectl -n ryft-migrate logs job/migrate                     # "role password set" ×4, "schema current"
for s in ingest scoring api notify migrate; do kubectl -n ryft-$s get vaultstaticsecret,secret ryft-secrets; done
kubectl -n ryft-rabbitmq get vaultstaticsecret,secret,rabbitmqcluster          # amqp-user-*, ALLREPLICASREADY
kubectl -n ryft-api get ingress,certificate                  # certificate READY True (DNS-01, ~1–2 min)
kubectl -n ryft-ingest get ingress,certificate
dig +short api.ryftapp.de                                    # NLB addresses (ExternalDNS, from the api Ingress)
curl -sI https://api.ryftapp.de/v1/me                        # 401 without a token
```

If a pod is stuck in `CreateContainerConfigError`, its namespace has no `ryft-secrets`
yet. `kubectl -n ryft-<svc> describe vaultstaticsecret ryft-secrets` shows why: usually
the Vault login. Check it by hand in the session shell (**Vault**: the `svc/vault-active`
port-forward and the CA file; the login needs no token):
`terraform -chdir=infra/vault output -json login_check | jq -r .<svc> | sh` prints the
role's policies (`[default <svc>]`), never the token. Vault reviews the service account's
token itself, as its own service account against `https://kubernetes.default.svc` (D187),
so the login does not go through the EKS public endpoint and does not depend on
`endpoint_public_access_cidrs`. When it fails, the cause is the role or its bound service
account, the audience (`vault`), the namespace's `vault-ca`, or a sealed Vault (no ready pod
behind `vault.vault.svc`: **Vault** → A pod is sealed).

The public host only routes `/v1/*`; `/healthz`, `/readyz` and `/metrics` stay internal.
Port 80 is not exposed at all, so clients must use `https://`.

**Production smoke test.** `make smoke-supabase` runs against the public host with the
real project. It never touches real accounts:

```bash
SUPABASE_URL=https://<ref>.supabase.co SUPABASE_ANON_KEY=<publishable key> \
SMOKE_EMAIL=<test user> SMOKE_PASSWORD=<…> SUPABASE_SECRET_KEY=sb_secret_… \
API_URL=https://api.ryftapp.de INGEST_URL=https://api.ryftapp.de make smoke-supabase
```

1. **Contract checks:** it signs in the dedicated test user (`SUPABASE.md` checklist)
   and runs the full contract checks with 10 synthetic days in that account.
2. **Account flows** (`scripts/check_accounts.py`, needs `SUPABASE_SECRET_KEY`): it
   creates two throwaway, confirmed users through the Supabase admin API and signs them
   in. It checks that `/v1/me` creates the row, that one user's sync stays invisible to
   the other, and the `apple-authorization` endpoint. It then deletes both through
   `DELETE /v1/me` and checks the tokens get `401` and the Supabase sign-ins are gone.
   It cleans up even when a check fails.

The email-confirmation link itself is tested by hand from the app. Don't run plain
`make smoke` against the public host: it is for apikey mode.

**Rescoring** after a scoring rule or constant changed (`SCORING.md`):
`KUBE_CONTEXT=<context> scripts/rescore_all.sh [days]` (1 to 400, default 400; or
`--context <context>`) runs `scoring rescore` inside the scoring pod of the cluster it
names; without a context it runs nothing. Each user's last *days* days are rescored,
oldest first, with scoring's own role; the log shows `user rescored … n of N`, then
`rescore done`. Locally: `RESCORE_LOCAL=1 scripts/rescore_all.sh 30`.

Days scored before their history (a backfill newest first, a late sample) need no
rescore by hand: scoring re-scores the days after a changed day itself, a retried
event included (log `rescored days after a history change`), and its 15-minute pass
picks up about 50 days a pass whose `baseline_days` (or one of its two counts) is
behind their stored history or whose baseline is missing (log `rescored days behind
their history`;
`ryft_days_rescored_total`, `OBSERVABILITY.md`). A user whose re-score there failed is
left until their next local day (the error is logged). Only users who synced in the
last 48 hours get the pass; the others get it with their next sync, or now with
`POST /v1/recompute` or `KUBE_CONTEXT=ryft-prod-euc1 scripts/rescore_all.sh`. A scoring letter replayed from
`dlq.scoring` (`scripts/dlq.sh replay`, RabbitMQ → Dead letters) arrives as a redelivery:
like a retry, it re-scores the days after its days and finishes what its failed attempts
began, so no recompute is needed after a replay (once scoring runs an image that reads
the marker; until then follow a replay with `POST /v1/recompute`).

**Learned sleep baseline** (`SCORING.md` → Sleep): scoring estimates it every Sunday from
04:00 local on its own. To run it for every user now (after a deploy, or after changing
its rules): `kubectl -n ryft-scoring exec deploy/scoring -- /app learn-baselines`
(locally `podman compose exec -T scoring /app learn-baselines`). The log ends with
`learn-baselines done` and the counts `applied` (the baseline moved; that user's last
7 days were rescored), `kept`, `insufficient` and `failed`. Users who set their baseline
by hand keep it.

Certificates: cert-manager renews 30 days before expiry. Each Ingress has its own
certificate for the same host, because a Secret cannot be shared across namespaces. To
try issuance without touching Let's Encrypt's production rate limits, point both
Ingress annotations at `letsencrypt-staging` first.

**Rotation.** The operator re-reads each namespace's `kv/config` hourly and restarts
the workload on a change.

- **Supabase secret key:** create a new one in Supabase, put it in `terraform.tfvars`,
  run `terraform apply`, then revoke the old one.
- **RabbitMQ password:** `terraform apply -replace='random_password.amqp["api"]'`. The
  operator updates both sides within the hour (OPERATIONS → RabbitMQ → Credentials);
  to skip the wait, restart the Vault Secrets Operator.
- **Database role password:** Postgres must get the new password before the service
  does, or its new pods fail their logins and may trip the pooler's circuit breaker.
  So force the order instead of waiting for the hourly refresh (here for `api`):

  ```bash
  terraform -chdir=infra/vault apply -replace='random_password.db["api"]'
  kubectl -n ryft-migrate delete secret ryft-secrets      # the operator re-creates it from Vault
  kubectl -n ryft-migrate wait --for=create secret/ryft-secrets --timeout=2m
  kubectl -n ryft-migrate delete job migrate --ignore-not-found
  kubectl apply -k deploy/k8s/overlays/eks -l ryft.dev/stage=first
  kubectl -n ryft-migrate wait --for=condition=complete job/migrate --timeout=10m   # Postgres has the new password
  kubectl -n ryft-api delete secret ryft-secrets          # re-created; the operator restarts the Deployment
  kubectl -n ryft-api rollout status deploy/api
  ```

  Open connections survive a password change, so the old pods keep serving until the new
  ones are ready. If a `wait --for=create` times out, the operator did not re-create the
  Secret at once; it does at the next hourly refresh at the latest
  (`kubectl -n ryft-<svc> describe vaultstaticsecret ryft-secrets`).

## Deploy and roll back

**One-way door (2026-10-31, D144/D145).** Once an app build sends `deleted` or a record `id` (the
changelog "Deletions and HealthKit ids"), ingest must not be re-pinned to an image from before
that change: the older ingest rejects unknown request fields with `400`, the app does not retry a
`400`, and uploads stall until you roll forward again. Roll forward or fix forward; for an
unrelated incident pin only the other groups back.

Git is the only way anything reaches `ryft-prod-euc1` (D94–D96). Argo CD syncs the
applications in `deploy/argocd/apps`; CI promotes images by a PR that pins
`deploy/k8s/overlays/eks`. Nobody runs `kubectl apply` against production, except
break-glass below.

**How a change reaches production:**

1. **Merge to main** (or push, as admin). CI runs every check, then builds an image for
   each **group** whose directory differs from its running pin in
   `deploy/k8s/overlays/eks` (D107): **services** (ingest, scoring, api, notify, migrate)
   from `backend/`, **web** (the apex site) from `web/`. Tags are
   `ghcr.io/timkrebs/ryft/<image>:<the commit's first 7 characters>`.
2. **promote** opens one PR "deploy: images <sha>" that pins the groups it built, each
   with its old pin and its commits since, and closes every older open `deploy/*` PR as
   superseded. It runs only when every group it needs was built: if one image job failed,
   nothing is pinned (fix the cause, then "Re-run failed jobs" on the **latest** run on
   main). The PR merges itself once its checks pass (`manifests` also asks ghcr.io for
   every pinned image). Close it to stop the deploy and `hold.sh add` the group (a closed
   deploy PR with the group still different from its pin makes the deploy watch fail every
   day). A change to manifests only (no new
   image) deploys on its own merge. The job runs in the GitHub environment `deploy`
   (below) and signs with the deploy App's key from there.
3. **Argo CD syncs.** It picks a merge up within two to six minutes (the repository is
   polled and cached; the rollback drill saw 2:20 and 6:08); a release, from the merge of the change to the new pods, takes about 15
   minutes, because the images are built and the deploy PR passes its checks first. Waves
   order the applications: wave 0 the Vault objects, wave 1 the RabbitMQ operators, wave 2
   the broker, wave 3 `ryft-platform`. Inside `ryft-platform` there are no sync waves
   (the services roll together, in no set order); only the hooks are ordered: **migrate
   first** (PreSync: a failed migration fails the sync and nothing rolls), the apply,
   wait until everything is healthy, **the smoke last** (PostSync, `ryft-smoke`: every
   `/readyz`, the smoke user's sign-in, one sync, the day rescored within 90 s).
4. **Watch:** `kubectl -n argocd get applications`, the UI, or the alerts
   (`ArgoSyncFailed`, `ArgoAppDegraded`, `ArgoAppOutOfSync`). From outside, `make
   smoke-prod` still checks the edge and probes the gates. After a model bump,
   `KUBE_CONTEXT=ryft-prod-euc1 scripts/rescore_all.sh`. Once a day the deploy watch (below) looks for a deploy that
   did not happen.

**Staging a backend change (D175).** An open promote PR holds nothing: it merges itself once its checks pass, and
when the next promote PR opens, promote closes every older open `deploy/*` PR as superseded (step 2). On 2026-11-05 the
promote PR #124 (the scoring and notify lifecycle change) was left unmerged; the next one, #130, closed it with
"Superseded by deploy: images dc1fcd4" (and merged when its checks passed, 3 minutes after it opened). So to make a change wait for a step of yours
(alert rules loaded, a soak after the previous stage), **hold the image group, not one promote PR**:

1. One stage per image group and per rollout: the five services images roll together (D107), so a services change that
   needs a soak is its own rollout; do not merge the next stage's change into that window.
2. Before the merge that builds the change, merge a PR with `./scripts/hold.sh add services "<reason>"` (the reason is public:
   an issue number and nothing else, see the rollback steps below). While the hold stands CI builds no services images and
   no promote PR opens for the group ("Proof that the hold works", below). The deploy watch fails a hold older than 7 days.
3. Merge the change. The group does not deploy. Do your steps now (for example `make alerts-apply` from an up-to-date main,
   then confirm in Grafana that the rules are listed).
4. Release the hold with `./scripts/hold.sh rm services`: two merges, the second being the promote PR (below, "Release a
   hold"). Watch the rollout as that change's PR asks. Rollback is the same hold mechanism (`pin_images.sh` and
   `hold.sh add` in one commit).

Closing a promote PR, or switching its auto-merge off, is not a hold: a newer promote PR is a new PR.

**What Argo CD may no longer do** (T12-f, D120). Its ClusterRoles are written in
`infra/aws/kubernetes/argocd.tf` (the chart's defaults give the controller `*` and the
server delete/get/patch on everything). **What is true after this change alone:** a compromised
controller can no longer hand itself write on the admission policies through RBAC (no `escalate`
on a ClusterRole, `bind` on one fixed name), the public server can write nothing cluster-wide, and neither holds Secrets,
`pods/exec` or `impersonate`. **What is not:** a compromised Argo CD can still reach cluster-admin
by other routes (`kube-system/aws-auth`, workloads in `cert-manager` and `kube-system`), and so can
still switch the admission layer off. That closes only when **P6 and P12** ("operators-cluster" and
"argo-scope") are **both** in Deny and this change is applied (P12 judges names, and the chart and
`admission.tf` refuse it in Deny otherwise); for `aws-auth` alone, also with EKS authentication mode `API`. It is not a sandbox: read
"What stays open" below before you rely on it. Each rule has a reason; what a
missing one looks like is under "A missing rule" below (a missing write fails the sync with
`forbidden`; a missing read is a comparison error; a missing cluster-wide list is silent):

The test for all this is an **allowlist** (`tests/addons.tftest.hcl`: verbs, kinds per API group,
non-resource URLs, `resourceNames` never empty, `escalate`/`bind` only on named Roles, the server
read-only), and `scripts/lib/admission_lib.sh` checks the rendered ClusterRoles the same way in the kind
run. A new kind or verb fails them until it is added on purpose.

The rules are not the only thing that decides what Argo CD may do, so more guards stand beside the
allowlist:

- `modules/argocd-values-guard`, wired into `helm_release.argocd` as a **precondition** (a violation is an
  error of `plan` and `apply`; a `check` block would only warn, and the apply would go on). It allows:
  `extraObjects` of the kinds NetworkPolicy and Middleware only, each in `argocd`, each with its one
  apiVersion; **no `{{` anywhere in the values** (the chart renders many values with `tpl`: a template
  expression in an `extraObjects` apiVersion renders a whole other object, one in an ingress annotation
  runs `lookup` with Terraform's credentials); **ASCII only, no control character or escape, no template delimiters,
  except newlines in the Lua health entries of `configs.cm`** (a line break in `ingressClassName`,
  `global.domain` or `global.image.tag` ends the value in the rendered YAML and starts another document;
  so do U+2028, U+2029 and U+0085, which `jsonencode` writes as escapes or raw; keys are covered too);
  `exec.enabled` false and `resource.respectRBAC` strict; no `controller.roleRules`; `createClusterRoles` not false
  (the chart then renders no ClusterRole and every check on the rules passes for want of an object); no
  `configs.rbac`, anonymous login or `server.disable.auth`; and a key allowlist **two levels deep**, plus
  the keys of `global.image`, `global.logging`, `global.networkPolicy` (create must stay true),
  `configs.cm` (three settings and the health customizations), `configs.params`, `configs.secret`,
  `server.ingress` and its annotations. Below that (the values of those keys, other charts' keys) it checks
  only for `{{`, non-ASCII characters and control characters or their escapes. Its dangerous variants are canned test cases in `tests/addons.tftest.hcl`:
  a variant nobody wrote down is not tested for.
- **Sync impersonation stays off.** If `application.sync.impersonation.enabled` were ever turned on, all controller writes would move to other usernames and P12 (which judges names) would match nothing: the guard keeps refusing it (it is not an allowed `configs.cm` key, `configs.params` key or `controller` value, and `tests/addons.tftest.hcl` pins that).
- **The release takes the guard's output.** The module returns the document it checked
  (`values_yaml = yamlencode(var.values)`); `helm_release.argocd` uses `values = [module...values_yaml]`,
  and a **postcondition** requires that to be the release's only values, with no `set`, `set_list`,
  `set_sensitive` or `postrender`. So a map renamed behind the guard's back, or a `merge` in the release,
  reaches Helm only if the postcondition is edited away. `scripts/tests/argocd_release_guard_test.sh`
  shows these fail (it edits a copy of the module: a `set`, a second document with a wildcard role, a
  renamed base map merged afterwards, a merge in the release, a guard violation). Limits: a postcondition
  is checked at plan time only when the release's inputs are known then, which is true today (nothing
  computed is in the values or the `set` arguments); with a computed input it fails only after the apply
  has started. **Review checklist: no computed value in the release's values or `set*`.** And a PR that
  changes the guard module together with the tests and the script's anchors is caught only by human
  review (`.github/CODEOWNERS`: everything is `@timkrebs`'s).
- The kind run: `argo-bindings` (the render holds only the chart's own role bindings, none to
  `cluster-admin`), `argo-extra-objects` (`helm template -s templates/extra-manifests.yaml` yields exactly as
  many documents as `extraObjects` lists, each a NetworkPolicy or Middleware in `argocd`) and
  **`argo-inventory`**: the whole render counted by (kind, namespace) must equal the table
  `ARGO_INVENTORY_EXPECTED` in `scripts/lib/admission_lib.sh` (48 objects: ConfigMap 7, ServiceAccount 5,
  RoleBinding 5, Role 5, NetworkPolicy 5, Service 4, Deployment 4, CRD 3, Middleware 2, ClusterRoleBinding
  2, ClusterRole 2, StatefulSet, Secret, Job and Ingress 1 each; all in `argocd` or cluster-scoped). It is
  the backstop for a value that the guard allows and that still renders another object: a DaemonSet or a
  ClusterRoleBinding adds a line. **What the guard does not check:** the values of allowed keys other than the ones pinned above
  (`admin.enabled`, the `router.middlewares` annotation value, `global.image.tag`, resource sizes) pass and are
  protected by review and, for what Argo CD may do, by the two ClusterRoles' allowlist. It does not look inside an object of an expected kind (a Deployment's
  image, an Ingress's rules); the drift and invariant checks cover the two ClusterRoles only. A chart bump
  or a component turned on changes the table on purpose, in the same PR.
- `argo-tf-bindings`: a **tripwire**, not a guard. It reads the module's `*.tf` for a `kubernetes_*role_binding*`
  resource or a RoleBinding manifest that names an argocd identity or one of the groups
  `system:serviceaccounts`, `system:authenticated`, `system:unauthenticated`, and for a
  `kubernetes_manifest`/`kubectl_manifest` whose manifest is not a literal (it cannot read
  `yamldecode(file(...))`; a human must). A binding built from locals or another module passes it.

**What stays open (stated plainly).** The admission layer is not protected by Argo CD's RBAC alone.

1. **The controller is still powerful outside `ryft-*`** (design gap, not a regression; P12 below).
   It has create, update, patch and delete on Deployments, Jobs, ConfigMaps, Services and
   ServiceAccounts in **every** namespace, and no admission policy matches Argo CD's writes outside
   `ryft-*` and `rabbitmq-system` (P2 covers only those; P3, P5, P9 only `ryft-*`; P7 only Argo CD's own
   kinds and Secrets in `argocd`). With a stolen controller token an attacker can, for example,
   - deploy a workload in `cert-manager` as the cert-manager ServiceAccount (it reads Secrets
     cluster-wide and holds Route53 rights through Pod Identity: a DNS-01 certificate for
     `api.ryftapp.de`);
   - deploy in `kube-system` as a controller-manager ServiceAccount;
   - patch `argocd-cm` or `argocd-rbac-cm` (anonymous admin on the public UI, D103) or the
     `argocd-server` Deployment;
   - **write `kube-system/aws-auth`.** The cluster runs authentication mode `API_AND_CONFIG_MAP` (the
     admission chart's `values.yaml` says so beside `clusterRoleWrites`), so a ConfigMap write there
     maps an IAM principal of the attacker's to `system:masters`: cluster-admin with no Pod needed,
     which then deletes the policy bindings (claim a: bindings are exempt from admission). This is
     the worst of the routes and needs only the controller's ConfigMap write.

   The controller's ConfigMap write cannot be narrowed here: the apps write ConfigMaps only in `ryft-*`
   and `rabbitmq-system`, but a ClusterRole rule cannot be scoped to namespaces, so the honest options are
   per-namespace RoleBindings (a separate decision: one Role and RoleBinding per namespace, kept in
   step with the apps, and the namespaces must exist first) or P6 and P12 both in Deny. The rule is unchanged: the render
   shows the apps need it. For `aws-auth` alone, EKS authentication mode `API` (access entries) removes
   the route.

   Neither the narrowed ClusterRoles nor P1 to P11 stop this. It closes only with **P6 and P12 both in Deny**
   (P12, "argo-scope": Argo CD's own identities may write namespaced objects only in `ryft-*` and
   `rabbitmq-system`, in `argocd` only `argoproj.io` objects and Events, and cluster-scoped objects only
   of the whitelisted kinds; it judges names only), and this change applied. Until then the
   controller token is, in effect, an admin of the workloads of every namespace, and through them of
   whatever those ServiceAccounts reach (Secrets included).
2. **A Role of an operator name in any namespace, until P6 is in Deny.** The `escalate` and `bind` on
   the four Role names are in a ClusterRole, so they match in **every** namespace: without P6 the
   controller can write a Role named `rabbitmq-cluster-operator-role` (any rules, Secrets and
   `pods/exec` included) in `kube-system` or `argocd` and bind itself to it. (`escalate` by name is
   checked with the name in the request URL, so it works for an update, a patch and a **server-side
   apply** create, which is what Argo CD does and what the kind run uses; a plain POST create
   carries no name and is refused, so a client-side `kubectl apply` of a new Role fails.) This is the vector the
   kind run's `claim-h-open` shows. P6 in Deny admits Roles and RoleBindings only in `rabbitmq-system`
   and the four named objects in `ryft-rabbitmq` (`p06-operators-cluster.yaml`). T12-f's first version
   also let the controller add write on VAP/VAPB to a ClusterRole and bind it; that route is now closed
   by RBAC alone (`claim-h-clusterrole`), because the controller holds no `escalate` on any
   ClusterRole and its one `bind` is on a role it cannot extend.
3. **What else P6 in Deny closes besides escalate/bind:** (a) creating a webhook configuration cannot be
   limited by name: a Mutating or ValidatingWebhookConfiguration with a `url` would receive every
   matched object, Secrets and Pods included, and could mutate Pods; P6 admits only the four names,
   served from `rabbitmq-system`, on `rabbitmq.com` only. (b) Creating a CRD cannot be limited by name
   either (updating one now can, to the operators' 14); P6 admits only CRDs of `rabbitmq.com` without a
   conversion webhook. Until P6 is in Deny both stay possible for a compromised controller.
4. **Secrets in `argocd`.** The chart's Role (get, list, watch on Secrets and ConfigMaps, full rights on
   Applications and AppProjects, all in `argocd`) stays the chart's: a compromised controller reads the
   admin hash and the repository credentials.
5. **Not changed by #47: the server's Role in `argocd`.** argo-cd 10.10.5 hard-codes it (no values
   setting): create, update, patch and delete on all Secrets, ConfigMaps, AppProjects and ApplicationSets
   (and Applications) in `argocd`. P7 refuses only Secrets labelled `secret-type`. So a leaked token of
   the public UI (D103) can rewrite `argocd-secret` (`admin.password`, `server.secretkey`), `argocd-cm`
   (`users.anonymous.enabled`) and `argocd-rbac-cm` (`policy.default: role:admin`) today, exactly as
   before. Only P6 and P12 in Deny (the server writes Applications and Events in `argocd` only) or a chart that
   stops granting it changes that.
6. **RBAC objects that outlive a stolen controller token (not narrowed here; P6 and P12 in Deny close the create and update route, not the rest).**
   The controller has create, update, patch and delete on `clusterroles`, `clusterrolebindings`, `roles`
   and `rolebindings` with **no `resourceNames`**, because Argo CD must create the operators' RBAC objects
   on a fresh cluster. Kubernetes' escalation check limits what a role it writes may hold (a subset of
   the controller's own rights, plus what it may `escalate`/`bind`), but not where it is bound. So a
   stolen controller token can write a ClusterRole holding a subset of the controller's rights (it can
   write ConfigMaps, Deployments and Jobs in every namespace, see 1) and bind it with a ClusterRoleBinding
   to `system:serviceaccounts` (every pod in the cluster) or `system:authenticated` (every authenticated
   caller). `system:unauthenticated` is probably not effective on EKS 1.36, where anonymous requests are, as
   far as we know, admitted to the health endpoints only: not verified here, so do not rely on it either way.
   That grant stays when the token is rotated or Argo CD is reinstalled, and it hands those rights to every
   pod or caller. **A second route needs no binding write at all:** a ClusterRole labelled
   `rbac.authorization.k8s.io/aggregate-to-edit`, `-admin` or `-view` adds its rules (a subset of the
   controller's) to the roles that are already bound to others; an `aggregationRule` of its own would need
   `escalate`, which stays closed, but the labelled rules need none. Also, `delete` of **any**
   ClusterRoleBinding or ClusterRole is open (including `system:*` ones that are not protected from
   deletion, and the bindings of other add-ons), and P6 matches only CREATE and UPDATE of the operators'
   own objects, not deletes or objects of other names. This is a design gap of the same kind as 1 (the chart's
   `*` allowed it and more); T12-f does not close it.

   *Evaluated, not implemented:* restrict `update`, `patch` and `delete` on the four RBAC kinds to
   `resourceNames` (the operators' ClusterRoles `messaging-topology-metrics-auth-role`,
   `-metrics-reader`, `rabbitmq-cluster-service-binding-role`, the ClusterRoleBinding
   `messaging-topology-metrics-auth-rolebinding`, the four Roles and their four RoleBindings: 12 names in
   all, from `kubectl kustomize deploy/rabbitmq/operators`), and leave `create` open (Kubernetes cannot
   name an object by `create`).
   That closes the rewrite and delete of every other object, but **not the route above**: a *created*
   ClusterRole and ClusterRoleBinding of any other name remain possible, so it narrows, it does not close.
   It was not applied here, and that is a **scoping choice**, not a proof of unsafety: the narrowing would
   have to be shown against Argo CD's own flows (the operators' sync with its RBAC objects, escalate/bind,
   server-side apply of existing objects by name), which only the `full` mode of the kind harness
   exercises (`admission-e2e` workflow, dispatched by hand; the pull request's `admission` job runs `ci`
   mode). This PR stays a draft until a full-mode run passes anyway; the narrowing is better its own change
   with its own run, since it does not close the route. What closes the create and update route is
   **P6 and P12 together in Deny** (P6 limits the ClusterRoles and bindings that Argo CD's identities
   create or update, their subjects and rules, to the operators' names; P12 keeps those identities to the
   whitelisted kinds; P12 alone does not close it). **What stays open even then:** the aggregation-label
   route, `delete` of RBAC objects (P6 matches CREATE and UPDATE only; P12 "does not cover" it), and prune
   by name.

*Evaluated, not implemented:* move the `escalate`/`bind` rule out of the cluster-wide ClusterRole into
**namespaced Roles in `rabbitmq-system` and `ryft-rabbitmq`**, shipped as `extraObjects` of the Argo CD

**A failed sync:** `argocd app get ryft-platform` names the operation's failing step.
PreSync: `kubectl -n ryft-migrate logs job/migrate`; a refused apply: the object's
message; PostSync: `kubectl -n ryft-smoke logs job/smoke` (the step and the user it
failed for). Argo CD retries a failed sync twice (1 and 2 minutes later); after that it
waits for the next commit, or `argocd app sync ryft-platform`. The release itself is in
when only the smoke failed: decide between a fix and a rollback.

**A migration that hits the lock timeout.** The migrator sets `lock_timeout` to 5 s in
every migration's transaction (`internal/db`, `lockTimeout`; a migration may set its own
`SET LOCAL`, which wins; 0027 does, also 5 s). A migration that cannot get its lock in
that time fails with `apply 00NN_name.sql: hit the lock timeout ...` (SQLSTATE 55P03).
Its transaction rolls back: `schema_migrations` and the schema stay as they were, the
earlier migrations of the run stay applied. The migrate Job exits 1 (the Job retries up
to its `backoffLimit`, with the same outcome while the blocker lives), the PreSync hook
fails, the sync fails before anything rolls and Argo CD retries it twice; the running
pods are untouched and keep serving. The wait for the migration lock itself (a second
migrator, e.g. an overlapping sync) is not cut by this timeout; it ends with the Job's
10 minute context. The services never migrate, they only wait for the schema
(`WaitMigrated`). `statement_timeout` is not set: a migration that runs long (a backfill)
is not killed, but it holds its locks while it runs.

Find the blocker (as the database owner, in the Supabase SQL editor or `psql`):

```sql
-- sessions holding or waiting for locks on the table the migration names
SELECT a.pid, a.state, a.xact_start, now() - a.xact_start AS open_for, a.wait_event_type,
       l.mode, l.granted, left(a.query, 120) AS query
FROM pg_locks l JOIN pg_stat_activity a USING (pid)
WHERE l.relation = 'public.daily_scores'::regclass       -- the migration's table
ORDER BY a.xact_start;
-- long-open transactions (the migrator has given up by now, so nobody is blocked any more)
SELECT pid, backend_type, state, wait_event, xact_start, now() - xact_start AS open_for,
       left(query, 100) AS query
FROM pg_stat_activity
WHERE xact_start < now() - interval '5 seconds' AND pid <> pg_backend_pid()
ORDER BY xact_start;
```

Usually the blocker is a long transaction (`state = 'idle in transaction'`, or a long
read). Let it finish, or end it if it is safe. `idle in transaction`: only
`SELECT pg_terminate_backend(pid)` helps; `pg_cancel_backend(pid)` returns true but the
session keeps its lock. `pg_cancel_backend` ends a running query (`state = 'active'`)
only. Never kill an autovacuum worker whose query says "to prevent wraparound"; it can
be the blocker, and the migration waits for it or goes first.

A failed run is not free: each attempt queues every query on the target table for up to
5 s. With `backoffLimit` 4 (5 pods per Job) and three syncs that is up to about 15 short
stalls over about 10 minutes. No alert fires, but latency spikes; so rerun once the
blocker is gone, not blindly: `argocd app sync ryft-platform` (the hook Job is
recreated), or at a quiet time. Nothing needs undoing.

`Seed` (built-in exercises and plans, run by the same Job after the migrations) also runs
under `locked()` and gets the same 5 s timeout. Its error is the raw `55P03` ("canceling
statement due to lock timeout") without the `apply ...` wrapper, from the `migrate` log
line `seed`; the same rerun applies.

The migrate Job has `ttlSecondsAfterFinished: 3600`: an hour after it finished its Pod
and logs are gone. What the hooks did stays in the operation state of the application:

```bash
kubectl -n argocd get app ryft-platform -o jsonpath='{.status.operationState.phase}{"\n"}{range .status.operationState.syncResult.resources[?(@.hookType)]}{.kind}/{.name} {.hookType} {.hookPhase}{"\n"}{end}'
# Succeeded / Job/migrate PreSync Succeeded / Job/smoke PostSync Succeeded
```

**A selective sync skips the hooks** (user only): `argocd app sync ryft-platform
--resource apps:Deployment:web` runs no PreSync and no PostSync, and is not recorded in the
history (Argo CD's selective sync documentation: "Hooks are not run."). Use it only when
migrate is the blocker and the change is safe without it; the smoke has not vouched for
the result, so run `make smoke-prod` afterwards.

**A wave that does not get healthy holds every later change:** the root's sync waits for
it, so even a fix to another application is not delivered. `argocd app terminate-op
ryft-root`, then `argocd app sync ryft-root` (seen in the kind test with a broker that
could not start).

**Which groups would move?** Compare with what runs, not with the last push:

```bash
./scripts/deploy_targets.sh                     # services=… web=… and why; read-only, needs the full history
gh pr list --search 'head:deploy/'              # open deploy PRs
gh run list --workflow ci --branch main --limit 5
```

**Roll back** one group: the old pin(s) **and a hold** in the same commit. Without the
hold the next push to main builds the rolled-back code again and pins it within about 15
minutes (D107). Argo CD does not roll back by itself (D95). Migrations stay (below), so
the previous release runs on the newer schema; how far back that works is under
"Lockouts and rolling back across releases".

**Configuration is part of the rollout** (F1). api, ingest, scoring and notify read
`ryft-config-<hash>`, generated from `deploy/k8s/base/<service>/config.env` (migrate's
`ryft-config` stays plain). Any edit renames the ConfigMap, so the Deployment rolls with the
images that are pinned; Argo CD deletes the old ConfigMap only after the sync is healthy
(`PruneLast`), and a failed rollout leaves it for the old pods. Roll back in git, never with
`kubectl rollout undo` or by scaling an old ReplicaSet: it may name a pruned ConfigMap
(`CreateContainerConfigError`) and self-heal reverts it anyway. Which commit to revert:

- a **configuration** problem (a `config.env` value such as `LOG_LEVEL`, or a hand-made change
  of `overlays/eks`): revert the merge that changed it. The old content gives the old name, so
  the pods roll back. Not for `PRIVACY_POLICY_VERSION`: a policy PR cannot be reverted (the
  versions list is append-only and the check wants the newest page); see "Withdrawing a
  version" under Beta → Consent, where a new version is the way.
- an **image** problem: the pins and a hold as above (`pin_images.sh <old> <group>` and
  `hold.sh add <group> "<reason>"`), not a revert of the deploy PR's merge when it pinned
  both groups. Leave the pin commits of the other group alone.

**A web rollback moves the policy in force too.** `pin_images.sh <old> web` sets the version
in force (api and ingest) to what the site at `<old>` serves: base's `config.env` there, or the
newest privacy page for a commit from before `config.env` existed (the foreign `f437747`: the
first listed version). If that differs from today's, api and ingest roll with web and the
testers who consented to the newer version consent again (`consent_required` rises). The
`manifests` job (`check_policy_in_force.sh`) refuses a web pin whose commit does not serve the
version in force, so pin and version always go back together. A draft version on main blocks
every deploy PR (services too), because the deploy PR would put a draft into force: publish the
text, or hold web (`./scripts/hold.sh add web "<reason>"`).

**Before you start** (a planned rollback or a drill; in an incident the first three may be
red, which is why you are rolling back, the rest still holds):

- Nothing pending: `./scripts/deploy_targets.sh` prints `services=false web=false
  held=false`, and the overlay has no `# hold:` line.
- No deploy PR is open (`gh pr list --state open --search 'head:deploy/'`,
  `git ls-remote --heads origin 'deploy/*'`), the last `ci` run on main is green and none
  is in progress, `GH_REPO=timkrebs/ryft-platform ./scripts/deploy_watch.sh` reports OK.
- Argo CD: `kubectl -n argocd get applications` all Synced and Healthy.
- The images you roll back to exist: `./scripts/check_registry.sh
  ghcr.io/timkrebs/ryft/{ingest,scoring,api,notify,migrate}:<old>` for the services, and
  `./scripts/check_registry.sh ghcr.io/timkrebs/ryft/web:<old>` for the site (`web:<old>` is
  its own tag: the services' SHA is no proof that it exists).
- Nothing else merges while the hold stands (a merge that touches the group's directory
  would be built after the release, not before, but a second deploy PR confuses the proof).
- Know the way back (the undo below) before you merge.

**Abort and way back:**

| Where | Abort if | Way back |
| --- | --- | --- |
| Before the merge | a local check or CI is red, no approval | Close the PR, delete the branch. |
| PreSync | migrate fails or hangs | Nothing rolled; Argo retries twice; then the undo. |
| Rollout | a pod crash-loops or stays unready for 3 minutes, or api or ingest has fewer than one ready | The old ReplicaSet keeps serving; the undo. |
| PostSync / verify | the smoke fails, `/v1/me` is not 401, dead letters grow (`KUBE_CONTEXT=<context> scripts/dlq.sh list`), `ArgoSyncFailed` | The undo. |
| Hold window | a deploy PR appears | Close it, then the undo; find out why promote ran. |

1. Find the last "deploy: images" merge that moved the group, and the pins before it.
   `git log -- <overlay>` lists the web-only deploys too (they leave the five service
   lines alone), so read what each merge changed. Name the branch anything but
   `deploy/<7 hex>`: CI treats those as the App's own and refuses their change of a held
   pin.
   ```bash
   git fetch origin && git switch -c fix/rollback-services origin/main     # or fix/rollback-web
   f=deploy/k8s/overlays/eks/kustomization.yaml
   git log --oneline -8 -- $f                                              # the deploy merges
   git show <merge> -- $f | grep -E '^[-+] +newTag'                        # five lines a side: services; one: web
   git show <merge>^:$f | grep -A1 -E 'ryft/(ingest|scoring|api|notify|migrate)$'   # the old tags (services)
   git show <merge>^:$f | grep -A1 'ryft/web$'                             # the old tag (web)
   ```
2. Set the pins and hold the group. `pin_images.sh` sets all five services tags at once
   (never edit them by hand: one forgotten tag is a mixed release) and prints the pin you
   roll back from; `hold.sh` refuses a services hold while the five disagree.
   ```bash
   ./scripts/pin_images.sh <old> services       # or: web   (the site may also go to "f437747", see Apex site)
   ./scripts/hold.sh add services "bad migration, see #57"      # or: web "broken AASA, see #57"
   ```
   A **web** rollback also sets the version in force to what the site at `<old>` serves, and
   `manifests` refuses the pair when the older site would bring back a draft text: if the
   version in force was published in place (the same version label, `status: draft` then
   `published`), rolling web back past the commit that published it, or to `f437747`, fails
   `check_policy_in_force.sh` ("would bring the draft text back"). Pick an `<old>` at or after
   the publishing commit, or hold web at the current pin.
   `hold.sh` writes exactly `# hold: <services|web> <YYYY-MM-DD UTC> <reason>` above the
   group's first image (the **ingest** entry for the services, **web** for the site), is
   idempotent, and runs `deploy_targets.sh --check` (any other line that starts like a
   hold fails `manifests`: a mistyped hold would otherwise be ignored). **The reason is
   public** (the overlay, deploy PR bodies, run summaries): printable ASCII, one line, an
   issue number and nothing else, no names, ids, e-mail addresses or health details;
   `hold.sh` refuses `@` and "fixes/closes/resolves" before `#N`, `GH-N` or an issue URL (the
   merge would close the issue); `deploy_targets.sh --check` applies the same rules to every
   hold line in the overlay, so a hand-edited line fails `manifests` too. `--check` also reads the
   whole overlay as an allowlist: only the six plain image entries, a single `images:` key and
   the known top-level keys; anything else fails.
   When the deploy PR moved both groups and only one is bad, change only that one; do not
   `git revert` the whole merge. GitHub's Revert button works too (its `Revert "…"` title
   passes `pr-title`), but you still add the hold.
3. Commit as `deploy: roll back services to <old>`, `gh pr create --fill`, then merge.
   `gh pr merge --squash --auto` merges as soon as the required checks pass; main has no
   required reviews, so no human sits in between. When someone must approve, merge by
   hand (no `--auto`) after the review. Pushing as admin to skip the checks (D96) is for
   the user only; an agent never does.
4. Argo CD picks the merge up within two to six minutes (drill: 2:20 and 6:08) and rolls the group back like
   any release. For a **services** rollback the hooks are the OLD release's: PreSync
   migrate and PostSync smoke run the `migrate:<old>` image (limits below). A web
   rollback leaves migrate and the smoke on the services pin.
5. **Proof that the hold works:** the run on main of the rollback merge itself is the
   first proof. Its `changes` job and summary print `services held since 2026-10-23 (…)`,
   `images` and `web-image` are skipped, and promote ends with `promote: no group differs
   from its running pin (services: held since 2026-10-23 …; web: …): no deploy`. No
   `deploy/<sha>` branch or PR appears. `held=true` is what lets promote run when nothing
   else is pending; it then closes older open deploy PRs, so one cannot undo the rollback.

**Undo a rollback** (the old release was fine after all): one commit on a branch that is
not `deploy/<7 hex>` that sets the pins back to what you rolled back from and runs
`./scripts/hold.sh rm <group>`. Merge it; Argo CD rolls forward. If the group's directory
moved past the pin you roll back to in the meantime, the merge also targets it: CI builds
and deploys a new SHA instead of the one you rolled back from.

**A hold stops promote for that group only.** While it stands, every run on main prints
`web held (…)` in the `changes` job and its summary, and the next deploy PR shows
`held: <reason>`; the group deploys nothing, not even a fix. `manifests` fails a deploy
PR that moves a held group's `newTag`. Your own PRs may still move a held pin (a second
rollback). If a red `web-image` (Trivy, GHCR) blocks a backend hotfix, hold web
(`./scripts/hold.sh add web "ci red"`) and merge the hotfix. The deploy watch fails a hold
older than seven days: a hold is a rollback in progress, not a state.

**Release a hold** once the fix is on main (or the bad code reverted). It takes **two
merges**, and the cluster stays on the rolled-back pin until the second is through:

1. Before opening the PR, see what its merge will target: `./scripts/hold.sh rm services`
   on a branch, then `./scripts/deploy_targets.sh` (`services=true` and why).
2. Merge the PR that deletes the `# hold:` line. CI on main finds `backend/` different
   from the rolled-back pin, builds new images at the **new** SHA, and promote opens a
   deploy PR that merges itself. Plan for about 12 to 15 minutes. The final pin is that
   new SHA, not the one you rolled back from.
3. If the group's directory already equals the pinned tree (the cause was not code, e.g. the
   `SUPPORT_EMAIL` variable), nothing is targeted: `gh workflow run ci --ref main -f
   force=web` (or `services`, `all`). A hold always wins over `force`.

```bash
curl -s -o /dev/null -w '%{http_code}\n' https://api.ryftapp.de/v1/me     # 401 (alive, wants a token)
```

The consumers: `kubectl -n ryft-scoring logs deploy/scoring | grep -E 'amqp (connected|consuming)'`
(likewise notify), or `ryft_amqp_connected` in Grafana. The pods' `/metrics` cannot be

**Disruptions:** api, ingest and `web` (two replicas, `maxUnavailable: 1`) have a
PodDisruptionBudget, so a node drain takes one site pod at a time.

**Re-run promote:** "Re-run failed jobs" on the latest run on main. An older run's
promote exits with "not main's tip" and does nothing; use `gh workflow run ci --ref main
-f force=<group>` instead. promote touches only the App's own `deploy/<sha>` PRs, and does
not reopen one you closed. A stalled deploy PR (red checks) is closed by the next push or
by hand.

**If migrate blocks the rollback** (a failed PreSync, e.g. the Supabase lockout below),
the rollback PR rolls nothing: web shares the `ryft-platform` application with migrate.
Follow "Lockouts" first. A broken manifest change is reverted like code.

**Break-glass** (Argo CD itself is down): pause it if it is half up, then `make

services, without the PostSync smoke; checks the registry first). Afterwards make git
hold exactly what you applied, and resume.

### A deploy: what the old pod logs

A service started through `internal/app` (scoring and notify since the PR that moved them;
api and ingest follow) logs its shutdown. On every deploy, every old pod of such a service
writes, in this order (CloudWatch, log group `/ryft/ryft-prod-euc1/containers`, fields under
`data.`): `shutting down` (`reason` `signal`), one `shutdown step` per step in this order
(`consumers`, `http`, `jobs`, `relay`, `broker`, `pool`; `dur_ms` each; `drain` first when a
drain delay is set, and `metrics` last only when its stop fails), and `shut down` with `exit`
0. A pod that logs `shutting down` but never `shut down` was either killed (SIGKILL after the
30 s grace, exit 137) or ended by the watchdog (a `shutdown overdue` line, then exit 1, or 2
after a panic): the last `shutdown step` line, or the `step` of `shutdown overdue`, says which
step it was in. The bounds add up to under 26 s (`internal/app/app.go`); past 26 s the
watchdog exits the process itself. Exit codes: 0 clean; 1 a start failed, a task failed or a
step overran its bound; 2 a task panicked (recovered, then a normal shutdown); 137 killed.
A SIGTERM while the service still waits for the database or the broker is a clean stop: it
logs `start interrupted by the signal` (info, `step` `db` or `events`), then `shutting down`
and `shut down`, and exits 0 (it is not a `db` error line).

`/readyz` answers 503 `draining` from the start of the shutdown; the liveness probe's
`/healthz` stays 200 until the listener closes. scoring and notify have no Service traffic,
so nobody sees it.

Not changed by this: an event a consumer is handling when SIGTERM arrives is still cut
(`handle event failed, will retry`, then `amqp: could not retry, rejecting for redelivery`,
one delivery of the queue's 10 used). The delivery in hand finishes only after the amqpbus
drain PR (A4); until then those two lines on a scoring or notify deploy are expected, and are
what that PR is measured against. The last query below also matches `delivery requeued at
shutdown`; that line does not exist before A4.

```text
# the shutdown timeline of one deploy
fields @timestamp, data.service, data.msg, data.reason, data.step, data.dur_ms, data.exit, data.err
| filter data.msg in ["shutting down","shutdown step","shut down","shutdown overdue"]
| sort @timestamp asc

# pods that began shutdown but never finished (SIGKILL): expect no rows
fields @logStream, data.msg
| filter data.msg in ["shutting down","shut down"]
| stats sum(strcontains(data.msg,"shutting down")) as began, sum(strcontains(data.msg,"shut down")) as done by @logStream
| filter began > 0 and done = 0

# slow or failed steps
fields @timestamp, data.service, data.step, data.dur_ms, data.err
| filter data.msg = "shutdown step" and (data.dur_ms > 5000 or ispresent(data.err))
| sort data.dur_ms desc

# the consumer side of a scoring or notify deploy
fields @timestamp, data.service, data.msg, data.queue, data.attempt, data.err
| filter data.service in ["scoring","notify"] and (data.msg like /could not (retry|dead-letter|defer)/ or data.msg = "handle event failed, will retry" or data.msg = "delivery requeued at shutdown")
| sort @timestamp desc
```

The exit code of a pod that a rollout replaced never reaches Grafana (kube-state-metrics
drops deleted pods): a bad exit on a deploy is visible in these queries only. Grafana sees
a container that restarted inside a living pod (ServiceExited, next section).

### A service exited (ServiceExited)

`ServiceExited` (critical) fires when a container of api, ingest, scoring or notify has
restarted in the last 15 minutes. Zero restarts is normal for these four, so any restart
pages; the exit code is not part of the rule. The services handle SIGTERM and exit 0 on a
clean stop, so a container the kubelet killed for a failed liveness or startup probe (a hang,
a deadlock) can end with exit 0, and kube-state-metrics may not send the exit code series. A
restart is also the trace of what a metric cannot show: a goroutine panic ends the process
before a scrape sees `ryft_goroutine_panics_total` rise, and a failed start leaves no counter.

1. Which pod and why: `kubectl --context ryft-prod-euc1 -n ryft-<service> describe pod <pod>`
   (read-only): *Last State: Terminated*, its *Exit Code* and *Reason* (`OOMKilled`), and the
   events (`Unhealthy` and `Killing` mean a probe failed: a hang, not a crash).
2. The previous container's log: `kubectl --context ryft-prod-euc1 -n ryft-<service> logs
   <pod> --previous`, or CloudWatch (`filter data.service = "<service>" and data.level =
   "ERROR"`, newest first).
3. By exit code (from step 1):
   - **2**: a recovered panic. The `msg="panic"` line names the `task` and has the stack.
     It is a bug: reproduce it with a test, fix it, and mind that the pod restarted and the
     work resumes by itself (events are redelivered, D100; timers run again).
   - **1**: read the last error line before `shutting down`: `config`/`beta config`/
     `apns config` (a setting: fix the secret or `config.env` in git), `db` or `events`
     (the dependency was down at start: DatabaseDown, AMQPDisconnected), `serve` (the HTTP
     port would not bind), `consume`/`job` (a task gave up), or a `shutdown step` with `err`
     (a step overran its bound; `shutdown overdue` means the watchdog ended it).
   - **137**: killed. `OOMKilled`: the memory limit (Scaling and disruptions). Else the
     kubelet's SIGKILL after the grace period: no `shut down` line; the last `shutdown step`
     says where it was.
   - **0 or 143** with `Unhealthy`/`Killing` events: a probe killed a container that was
     still running but not answering `/healthz` (the process exited cleanly on the kubelet's
     SIGTERM). Look for what hung: the last lines before the restart, goroutine or
     connection-pool exhaustion, a dependency that stopped answering.
4. A crash loop is also PodRestarting (more than three restarts in 30 minutes).

If the alert never fires although a pod restarted, check in Grafana Explore that
`kube_pod_container_status_restarts_total{namespace="ryft-scoring"}` exists for the pod
(Fleet Management's allow-list decides what kube-state-metrics sends). The exit code series
`kube_pod_container_status_last_terminated_exitcode` is not needed by the rule.

### A panic (Panics)

`Panics` (critical) fires when a handler (`ryft_http_panics_total`), an event handler
(`ryft_event_handler_panics_total`) or a service's own goroutine (`ryft_goroutine_panics_total`)
panicked in the last 15 minutes. Find the line, which has the stack (the one place a stack is
logged, Data protection (logs)):

```text
fields @timestamp, data.service, data.task, data.check, data.route, data.panic, data.stack
| filter data.msg = "panic"
| sort @timestamp desc
```

`task` or `check` is set for a goroutine panic, `route` for a handler's. After a goroutine
panic the pod has restarted (exit 2, ServiceExited fires too): read the previous container's
log, `kubectl --context ryft-prod-euc1 -n ryft-<service> logs <pod> --previous | grep
'"msg":"panic"'`. A handler panic answered `500` and the pod runs on; an event handler's
message is retried and, at the last delivery, dead-lettered (DeadLetters). Reproduce with a
test, then fix. The alert can miss a first panic that follows a collector outage of about an
hour, or a second one within about an hour of a pod restart (a counter born at 1 looks like
an old series there); the CloudWatch query does not.

### The deploy watch

`.github/workflows/deploy-watch.yml` runs `scripts/deploy_watch.sh` every day at 05:17 UTC
(and on `gh workflow run deploy-watch`) with a read-only token. It reuses
`deploy_targets.sh`, changes nothing and fails with its findings in the run summary:

| Finding | Meaning | What to do |
| --- | --- | --- |
| `<group> has been held for N days` (`HOLD_MAX_DAYS`, 7) | A rollback never finished. | Ship the fix and release the hold (above), or renew it on purpose: `hold.sh rm`, then `hold.sh add` in a PR. |
| `<group> is held since <date>, which is N day(s) in the future` | A typo in the date would keep the age check from ever firing. | Fix the date in the overlay (UTC `YYYY-MM-DD`; `hold.sh` writes today's). |
| `#N (deploy/<sha>) has been open for N min` (`DEPLOY_PR_MAX_HOURS`, 2) | The deploy PR should have merged itself. | Open it: red checks (fix or re-run), no auto-merge, a branch rule. Close it **and hold the group** to stop the deploy. |
| `<group> differs from its pin, main's tip is N h old and no deploy PR is open` | promote failed (a missing key is this: with no `RYFT_DEPLOY_APP_KEY` in the environment and none in the repository, `create-github-app-token` fails and the job is red, not skipped), was skipped (only `RYFT_DEPLOY_APP_CLIENT_ID` unset skips it), or its PR was closed on purpose. | The latest `ci` run on main: re-run failed jobs, or `gh workflow run ci --ref main -f force=<group>`; to keep a stopped deploy stopped, hold the group. |
| `scripts/deploy_targets.sh failed` | A hold that does not parse, or a byte in the overlay that is not printable ASCII (a CR, U+2028, U+2029, U+0085: line breaks to YAML). A missing or disagreeing pin is not this: it targets the group. | Fix the overlay first. |
| `could not list the open pull requests` / `a creation time I cannot read` | The token lacks `pull-requests: read`, or GitHub's answer changed. | The workflow's `permissions`; the script. |

A warning (not a failure) names a PR from a `deploy/<sha>` branch that is not by the
App: the App was renamed (set `DEPLOY_APP_SLUG` in the workflow) or a person used the
reserved name. It is not counted as a deploy PR. Run it on an up-to-date main: it reads
the checkout, which a scheduled run is. Exit 2 means the watch itself could not run (a
shallow clone, a bad setting).

A failed scheduled run is mailed to whoever last changed the `cron` line of the workflow
(GitHub's rule for scheduled workflows), not to the repository owner by default, and only
if that account's Actions notifications (Settings → Notifications → Actions) are on. Do
not let a bot be the last to edit that line. A scheduled workflow in a public repository
is switched off after 60 days without repository activity; a failed run is the only
signal, so also look at the Actions tab now and then.

### The `deploy` environment and the App key

The `promote` job runs in the GitHub environment `deploy`, restricted to the branch
`main` and not bypassable by administrators, and the deploy App's private key
`RYFT_DEPLOY_APP_KEY` lives there. Only a job on `main` that names the environment can
read it: a workflow edited in a pull request, or run from another branch, cannot. The
environment has no required reviewers (the promote is unattended). CI's `manifests` job
(`scripts/check_workflows.sh`, which parses the workflows with `yq`) fails if any other job
names an environment or reads the key (in any spelling: flow style, quoted keys, any case
of the secret's name), if a workflow uses `pull_request_target` or `workflow_run`, calls an

`secrets: inherit` or reads `secrets` other than as `secrets.<NAME>`, or names one of the
test hooks of the scripts, or a YAML merge key. CI's `bytes` job (no path filter, on every run; `ci-ok` and the image jobs need it) fails on a hidden line break,
control or other invisible character (format, private use, odd spaces), bidi control or BOM
in ANY tracked file, by content and not by extension (kustomize also reads `Kustomization`
and any file a `resources:` entry names), on the file names `Kustomization`,

1. In GitHub → Settings → Developer settings → GitHub Apps → the deploy App → Private
   keys: **Generate a private key**. The browser saves `ryft-deploy.<date>.private-key.pem`.
2. Find it: one line must print.

   ```bash
   key=$(ls ~/Downloads/ryft-deploy.*.private-key.pem); echo "$key"
   ```

3. Create the environment with the branch policy `main`:

   ```bash
   gh api -X PUT repos/timkrebs/ryft-platform/environments/deploy --input - <<'JSON'

   ```
   **Then confirm "admin bypass off" in the browser:** Settings → Environments → `deploy` →
   "Allow administrators to bypass configured protection rules" must be **unchecked**
   (untick it and Save if not). `can_admins_bypass` is not in GitHub's REST schema, so the
   `PUT` above may be ignored and the `bypass` field of the `GET` may print `null` or
   `true`: the checkbox is the proof. Do not go on to step 4 before it is off.
4. Put the new key in the environment and check that it is there:
   ```bash
   gh secret set RYFT_DEPLOY_APP_KEY --env deploy -R timkrebs/ryft-platform < "$key"
   gh secret list --env deploy -R timkrebs/ryft-platform
   ```
5. Merge the change that adds `environment: deploy` to `promote`. **Then delete the
   repository-level secret at once**, do not wait for a promote: from the merge on, the
   environment's secret wins and the repository copy is never read, and until it is gone
   any workflow run in this repository can read it:
   ```bash
   gh secret delete RYFT_DEPLOY_APP_KEY -R timkrebs/ryft-platform
   gh secret list -R timkrebs/ryft-platform          # no RYFT_DEPLOY_APP_KEY any more
   ```
6. In the App's settings → Private keys delete the old key(s): exactly one key is left,
   the new one.
7. `rm -- "$key"`, remove any older `~/Downloads/ryft-deploy.*.private-key.pem`, empty the
   Trash.
8. The first promote after the merge (a real deploy, or `gh workflow run ci --ref main -f
   force=web`, which pins the site once) is the proof that the environment's key works. If
   it fails at `create-github-app-token`, the secret in the environment is wrong: repeat
   step 4 and "Re-run failed jobs" on the latest run on main; nothing was deployed.

**Prove the branch policy once** (optional, user only): a pull request that names the
environment is refused.
```bash
git switch -c ci/env-proof origin/main
printf 'name: env-proof\non: pull_request\npermissions: {}\njobs:\n  proof:\n    runs-on: ubuntu-latest\n    environment: deploy\n    steps:\n      - run: "true"\n' > .github/workflows/env-proof.yml
git add .github/workflows/env-proof.yml && git commit -m "ci: environment proof (do not merge)" && git push -u origin ci/env-proof
gh pr create --draft --fill && gh pr checks     # proof: failed, "not allowed to deploy to deploy" (and manifests: only promote may name it)
gh pr close --delete-branch                    # then
```

**Order matters:**
- Delete the repository copy before the merge (step 5 before the merge) and the old
  `promote` still reads it: it fails at `create-github-app-token` with no private key.
  Nothing deploys and nothing breaks; merge, set the secret, re-run the failed job.
- Merge before the environment exists: GitHub creates `deploy` on the first run with no
  branch policy. The job works (it falls back to the repository's secret), but the key is
  not yet protected.
- Delete the repository copy before step 4: the first promote fails the same way.
- Never delete it: the environment protects nothing while a copy any workflow can read
  exists.
- A policy that names the wrong branch refuses the job outright (red, nothing deploys).

### What a kustomization or an Argo CD app may contain

Both are read by an allowlist, not by a list of forbidden things: kustomize reads `Resources:`
and the U+017F spelling `reſources:` like `resources:`, and decodes `!!binary`, so no list of
bad spellings is complete. The schema is `scripts/lib/yamlpolicy.py`:

- exact, case-sensitive keys. A kustomization: `apiVersion`, `kind`, `namespace`, `resources`,
  `patches` (`path`, `patch`, `target`), `images` (`name`, `newTag`), `labels`,
  `configMapGenerator` / `secretGenerator` (`envs`, `literals`, `options.labels`),
  `generatorOptions`. An app: one `spec.source` (`repoURL`, `targetRevision`, `path`), never
  `sources`, `kustomize`, `helm`, `plugin` or `directory`;
- the YAML tags `!!map !!seq !!str !!int !!bool !!null` only; no `<<`, `!!binary`, anchor or alias;
  one document per file (a trailing `---` is a second one); regular files, no symlink in the tree;
- an inline `patch:` is a literal block (`|` or `|-`), and no key or string may DECODE to a line break
  or invisible character (a double-quoted `\L` or `\x85` would);
- every field that names a file is typed `Path(...)` in the schema and is checked by what it names
  (`scripts/check_kustomize_refs.sh`): plain relative paths below `deploy/`, no symlink, and in
  `resources:` no name that kustomize could read as a remote URL (a segment with a dot, such as
  `github.com/org/repo`, is refused even when a directory of that name exists: kustomize clones first);
- an app's path is below `deploy/`, one application per path; the project is one of `ryft`,
  `ryft-operators` (bound to `deploy/rabbitmq/operators`) and `ryft-root` (`root.yaml` only);
  every path is rendered (git limited to `file://`) and the render keeps a SMALL set of production
  invariants (`scripts/lib/renderpolicy.py`): no `argoproj.io` object; for the `ryft` project only
  our six images with 7-hex tags (plus a digest-pinned rabbitmq, compared by pattern); no
  `API_KEY`, `ALLOW_INSECURE_APIKEY_AUTH` or `USER_ID` and `AUTH_MODE=supabase` in ConfigMaps,
  Secrets (decoded) and container env, no `valueFrom` for them, no `envFrom[].prefix`; default-deny
  intact in every `ryft-*` namespace with a workload; no NetworkPolicy rule that allows every peer
  (empty, `from: []` / `to: []`, ports only).

**Not checked** (the follow-up is an admission policy, see `docs/STATUS.md`): pod security
(privileged, `host*`, `hostPath`), Namespace objects and Pod Security labels, which image runs in
which namespace, `command` / `args`, the broker image beyond its pattern, NetworkPolicy shapes
beyond the above (`ipBlock`, `namespaceSelector`), workloads without `metadata.namespace`, Vault
Secrets Operator objects (the `VaultConnection` address, transformation templates), the power of
the operators project's cluster roles, and `project.yaml` itself (the check reads it from the
pull request). Do not read a green check as "production-safe".

`make k8s-validate` (CI's `manifests` job) runs these checks. The byte check
(`scripts/check_bytes.sh`, CI's `bytes` job) refuses tracked symlinks, reads every file under
`deploy/` and `.github/` as text whatever its extension, and has no exemption by path: characters
that render as nothing are written as `\u` escapes in sources. CI's `yq` is the release
binary from `scripts/install_yq.sh` (version and sha256 in that file; `manifests` and `smoke` both run it).

**To add a key**, change the schema in `scripts/lib/yamlpolicy.py` and the test in
`scripts/tests/check_kustomize_refs_test.sh` in the same PR as its first use; a new path-carrying key
is a `Path(kind)` there, so its references are followed automatically.

### Admission policies: the kind run (D120, D151, D152, T12-d)

The policies of `infra/aws/kubernetes/charts/admission-policy` are tried against a real API server
in kind before they reach `ryft-prod-euc1`: in CI on every change, and by hand before an apply and on
every upgrade. `make admission-celtest` (offline CEL) stays the first line; the kind run answers what
only an API server can: that the policies compile (`status.typeChecking`), what the real components
send (Argo CD's controller, the operators, their webhooks), and the design's claims (table below).

**CI: the `admission` job** (required in `ci-ok` when it ran). It runs on a change to `deploy/**`,
`infra/aws/kubernetes/**`, `ci.yml`, the Makefile or the scripts of the job, on a push to main, and by
hand. It is skipped for a promote PR **and for its merge to main** (D151: `changes` asks
`scripts/promote_only.sh`, the base branch's copy, whether the diff is only the EKS overlay's pins,
holds and privacy-version literals; any doubt, and a base without the script, runs the job). It is
`scripts/admission_e2e.sh --mode ci`, about 5 minutes:

1. On a pull request: `scripts/check_chart_bump.sh` fails when the chart's `templates/` or
   `values.yaml` changed and the `version:` in `Chart.yaml` did not go up (the Helm provider upgrades a
   release only when the version moves).
2. The CEL harness, once, with `CELTEST_EMIT`: its cases must pass and the fixtures it writes must equal
   `admission-e2e/fixtures/generated` (regenerate and commit after a policy change). The fixtures do not
   depend on the overlay's pins (the short SHA of an image is written as `0000000`), so a deploy PR does
   not make them stale.
3. kind 1.36 (the node image pinned by digest in the script) and kind, kubectl, helm and yq pinned by
   sha256 (`scripts/install_*.sh`; the versions are in the summary), the CRDs of VSO 1.6.0, cert-manager,
   Traefik, RabbitMQ and Argo CD (argo-cd chart 10.10.5, the versions of `infra/aws/kubernetes/main.tf`),
   the namespaces with infra/vault's and `argocd.tf`'s labels.
4. Argo CD's chart rendered with `argocd.tf`'s values (Terraform evaluates `local.argocd_values`
   offline), its two ClusterRoles compared with the rules of the values and checked against T12-f's list.
5. The chart in Audit (the committed values) and in Deny (every binding, `brokerEgressPublic: false`).
   After each install the API server must hold exactly the policies and bindings `helm template`
   renders with the same values (11 and 12 today; nothing is accepted on an empty answer), every policy
   must be type-checked without warnings, and a canary fixture must be answered as the variant says
   (polled for 30 s). Then every Application's render (and the projects and the root) dry-run applied
   server-side as Argo CD's controller (every app must give at least one object); one refused fixture
   per rule (Deny), the same fixtures passing with the rule's message as a warning (Audit); claims a, b, c,
   d and the negative test of claim h.

**By hand: `make admission-e2e REPO=<path>`** (or Actions -> `admission-e2e` -> Run workflow, with the
branch or commit as `ref`, dispatched from that branch). About 25 minutes, 6 GB of memory. It creates its
own kind cluster, runs the CI part, then the real stack (below), and deletes the cluster. Run it:

- before Step 0 (applying T12-f) on the combined tree of the Argo CD RBAC and the namespace-scoped
  operators (a throwaway merge of both branches, checked out beside this repository);
- on every operator, argo-cd chart, Traefik/VSO/cert-manager chart or EKS minor upgrade, on the tree
  that carries it.

```bash
git fetch origin infra/argocd-rbac deploy/operators-namespace-scoped
git worktree add /tmp/tree-rbac origin/infra/argocd-rbac            # a PR's tree: a git checkout
make admission-e2e REPO=/tmp/tree-rbac                              # ~25 min; summary in admission-e2e-summary.md
make admission-e2e REPO=/tmp/tree-rbac MODE=ci                      # only what CI runs
```

**The tree under test is code, not data.** `REPO` is rendered by kustomize, its `argocd.tf` is evaluated
by Terraform, and Argo CD in the cluster syncs it. So: an untrusted tree is run in the workflow (a runner
with no credential of yours and read-only contents) or on a machine without production credentials, not
on a laptop whose kubectl points at production. What the scripts do to limit the damage (a second line,
not a sandbox):

- only files git tracks under `deploy/` and `infra/aws/kubernetes/` are read (`scripts/lib/tracked_copy.sh`
  copies them to a temporary directory; `REPO` must be a git checkout): a git-ignored `tfplan`, `.tfvars`,
  `.terraform` or `deploy/k8s/secrets.yaml` is never rendered, evaluated or served to the cluster; a
  tracked symbolic link is refused;
- Terraform runs under `env -i` with a throwaway `HOME` and no AWS, HCP Terraform or Kubernetes
  credential, with this checkout's mock providers (the tree's `*.tftest.hcl`, `*.tftest.json`,
  `*.tfmock.*` and tfvars are deleted). `scripts/lib/tf_scan.py` is a **tripwire**, not a refusal to rely
  on: it reads the `*.tf` files with comments removed and strings blanked and stops at `provisioner`,
  `alias` (an aliased provider is not mocked, so its `exec`, `credential_process` or `postrender` would
  run), `exec`, `config_path`, `shared_config_files`, `shared_credentials_files`, `credential_process`,
  `postrender`, `local-exec`, `data "external"`, `data "http"`, `data "local_file"` (also
  `local_sensitive_file`, `terraform_remote_state`), the functions that read a local file (`file`,
  `templatefile`, `filebase64*`, `filemd5`, `filesha*`, `fileset`, `fileexists`, `pathexpand`, `abspath`,
  `path.cwd`, `path.root`, any `provider::` or `core::` function: this checkout's own module uses `file()`,
  `fileset()` and `fileexists()`, so a file is exempt from this one check only when it is byte-identical
  to this checkout's), a `\u` escape in a string and any
  `*.tf.json`, also in the modules `terraform init` downloads (only a `providers.tf` byte-identical to
  this checkout's, which holds the real `exec`, is skipped), and at a lock file naming a provider other
  than aws, helm, kubernetes and random. HCL is a language: a clever tree gets past a lexer, and
  `env -i` does not stop a program from reading `~/.aws` or `~/.kube` by absolute path. What contains it
  is a runner or a machine with no credentials, or, optionally, `TF_VALUES_CONTAINER=<terraform image
  pinned by digest>` (docker or podman): `init` then runs in a container that mounts only the work
  directory and `terraform test` in it with `--network none`;
- a `REPO` that is not this checkout must have its HEAD commit on an `origin/*` branch of this checkout
  (`scripts/check_e2e_ref.sh`, the workflow's check; `git fetch origin` first) and unmodified tracked
  files under `deploy/` and `infra/aws/kubernetes/`, or `make admission-e2e` refuses; the files are then
  copied from that commit (`git archive HEAD`), not from the working tree, which `git status` can be
  made to misreport. `origin/pr/*` and `origin/pull/*` never count, and a `remote.origin.fetch` other than
  the default `+refs/heads/*:refs/remotes/origin/*` refuses (a refspec can put fork pull requests under
  `origin/*`). `FORCE=1` runs it anyway with a warning, for a machine that has no production credentials;
- for such a tree Terraform needs `TF_VALUES_CONTAINER=<terraform image pinned by digest>` (the container
  sees only the work directory, so its file functions read the tree's own files and nothing else), or
  `FORCE=1`, which keeps the loud warning and still refuses a changed file that uses the file functions.
  In GitHub Actions both guards are skipped with a notice in the log (the runner holds none of your
  credentials; the workflow ran `check_e2e_ref.sh` on the ref);
- every value the tree supplies (an Application's name and path, a Secret's labels, an image name) is
  checked before it reaches a command line, and `kc`, `kca` and `hc` refuse any argument that would
  choose another cluster or user (`--kubeconfig`, `--context`, `--server`, `--token`, `--as`, `--kube-*`,
  ...);
- the guard (`scripts/lib/kind_guard.sh`, tested by `scripts/tests/kind_guard_test.sh`) refuses anything
  but a kubeconfig whose server is exactly `https://127.0.0.1:<port>` (or `[::1]`), with the one context
  `kind-*`, no `proxy-url`, no exec or auth-provider user, not in `~/.kube` (links resolved, the file
  included); with `--kubeconfig` it also compares the file with `kind get kubeconfig`; `HELM_KUBE*`
  variables are unset.

It needs `kind` and Docker or Podman, `kubectl`, `helm`, `yq` (mikefarah v4), `jq`, `git`, `go` and
`terraform` (the provider plugins are downloaded or come from `TF_PLUGIN_CACHE_DIR`; `TF_PLUGIN_DIR=<dir>`
installs them from a directory). It installs nothing, and if kind cannot start it stops with a message.
The script makes a kind cluster with `--kubeconfig <temp>/kind.kubeconfig`, exports `KUBECONFIG` to that
file and passes `--kubeconfig` and `--context` on every `kubectl` and `helm` call; it never reads or
writes `~/.kube/config`. `--keep` keeps the cluster and prints its kubeconfig; `--kubeconfig <file>`
reuses a kind cluster of yours (the release and the claim-a objects are removed first). After a failure,
a timeout or an interruption the temporary directory with every step's log (`log/`) is kept and its path
printed; the cluster is deleted in every case.

The full mode, after the CI part: cert-manager and the internal CA; Argo CD from `argocd.tf`'s values;
the tree served to Argo CD from inside the cluster; the policies in Audit; the first sync of every
app (waves: Vault secrets, operators, broker, services; hooks); the policies in Deny (a binding stays
in Audit while the tree lacks what it needs: `operators-cluster` without T12-g, `netpol` without T12-k)
and a manual `argocd app sync` of every app through argocd-server; the hooks again; the broker's
`rollout restart` (D98); `argocd app sync --async` then `terminate-op` (and what argocd-server writes
as the sync's revision, claim k); the operators' logs (no `forbidden`, since the stage began), the
topology Ready, `kubectl auth can-i` for both operator service accounts; claim i (`respectRBAC: strict`
with no cluster-wide Secrets) and claim m (kube-state-metrics, disproved). Validation failures the API
server logged during each stage (the audit log of the kind node, grepped there) are listed; one is
explained only if it has the policy, requester, resource and message of what the tree has not fixed yet
(the two vendored operator ClusterRoles until T12-g; the broker's open 443 egress until T12-k), and only
while the tree lacks that. Anything else is a failure. A cluster this run created always has the audit
log: its absence is a failure (with `--kubeconfig` the check is skipped, and says so).

**Stubbed** (the summary says so as well): Vault and VSO (the CRDs are real, a loop marks the
`VaultStaticSecret`s synced and writes dummy Secrets), the service images (busybox images built as
`localhost/ryft-stub/...`, loaded into kind and tagged inside the node as
`ghcr.io/timkrebs/ryft/<name>:<pin>`, because the policies judge names; no `ghcr.io/timkrebs/ryft` tag is
ever created in your local image store; the Job specs of the hooks are the real ones, the migrate job just
sleeps 15 s so `terminate-op` has something to terminate), the git remote (Argo CD reads the tree from
`git.gitsrv.svc` and the served Applications and project name that URL; P7's `argocd.repoURL` follows),
Ingress addresses, and the broker's size (1 replica, default StorageClass). **Not tried:** a node drain,
three workers, Traefik, the Vault auth, the real images, claims f, j and l (D151).

**What a failure means**

- `crds-*`, `argo-render`, `argo-values`: a pinned chart or Helm repository changed or is unreachable;
  `argocd.tf` no longer evaluates offline (read `tf_values` in the log), or the module holds something
  `tf_values.sh` refuses.
- `argo-rbac-drift-*`: the chart renders other rules than `argocd.tf` gives it (an argo-cd bump changed
  `clusterRoleRules`): fix `argocd.tf`. `argo-rbac-invariants`: a rule T12-f forbids is back.
- `claim-h-clusterrole` fails: with the narrowed RBAC and no policy the controller could rewrite a
  ClusterRole to carry write on the admission policies, i.e. it holds `escalate` on a ClusterRole, or `bind`
  on one other than `messaging-topology-metrics-auth-role`, or the permissions of one of those, again:
  fix `argocd.tf`. `claim-h-open` fails: the controller could not write a Role of an operator name
  in `kube-system` and bind itself (escalate/bind by `resourceNames` on roles do not do what the docs
  assume, or the hole is closed): re-read T12-f. `claim-h-guarded` fails: P6 does not stop the Role
  vector; **do not set P6 or P7 to Deny** until it does.
- `claim-a` fails: the API server runs admission on policy objects (or the canary policy never became
  live); the break-glass is not safe, stop. `claim-b` / `claim-c`: P6 does not see webhook
  configurations / P8 does not see `pods/exec`; the design leaned on both. `claim-d`: the audit
  annotation is not on dry runs, so §5's CloudWatch query cannot split them.
- `chart-install-*`: the API server refused a policy or binding (a CEL compile error, often an EKS minor),
  or reports other policies and bindings than the chart renders, or none. `typechecking`: a policy has
  type-check warnings; a warning is a rule that may never fire or may error under `failurePolicy: Fail`.
  `enforced-*`: the bindings are not answering within 30 s of the install.
- `dryrun-*`: a render of this tree is refused or flagged, or an app renders nothing. Fix the manifest; if
  the manifest is right the chart is wrong (that is how P10 and P11 were found wrong). `errors` are no
  admission decisions: Argo CD's RBAC lacks a kind (T12-f), a CRD or namespace is missing.
- `fixtures-*`: the API server and the harness disagree, or a policy changed without
  `CELTEST_EMIT=<dir> admission-celtest/run.sh` (copy the output to
  `admission-e2e/fixtures/generated`; CI diffs it). The message shows which rule answered instead.
- `full-*`: `full-sync-*` an app did not reach Synced/Healthy (the summary names the failing
  operation: a refusal by a policy reads "denied request" in it; with `respectRBAC: strict` a root that
  stays Progressing for minutes while its children are Healthy means the controller lacks
  `applications.argoproj.io` get, list and watch cluster-wide: the kind is dropped from its cache without a
  log line, and the root only catches up at its periodic reconcile, about 3 minutes; see `claim-i-list`); `full-findings-*` a validation failure that no stage explains: a policy refuses something
  production does (fix the chart before Deny); `full-broker-restart` P2's exemption of the D98 restart does
  not hold; `full-terminate-op` P10 or P7 blocks the operations of OPERATIONS -> Deploy;
  `full-operator-logs-*` / `full-operators-can-i` a scoped Role lacks a verb (T12-g) or the operators still
  read Secrets elsewhere; `full-stub-refused` the tree has a Secret label or name that is not valid.

**The design's claims, as the kind run answers them** (kind 1.36.4, argo-cd chart 10.10.5; the run says so
again each time; the table is in the design too):

| Claim | Result |
| --- | --- |
| a: nothing guards policy and binding objects | holds: a Deny policy matching both kinds (proven live by refusing a canary ConfigMap) fired for neither a further policy and binding nor their deletion; the API server admits the chart's 11 policies and 12 bindings |
| b: P6 sees webhook configurations | holds |
| c: P8 matches CONNECT on `pods/exec` | holds (refused outside `ryft-rabbitmq`, admitted for the Cluster Operator inside it) |
| d: dry runs carry `validation_failure` | holds (audit level Metadata; `requestURI` has `dryRun=All`) |
| g: P7's whole-`spec` equality type-checks | holds (`status.typeChecking` empty; the project as committed passes, a widened one is refused) |
| h: escalate/bind by `resourceNames` | the negative test, run again for the rules without `escalate` on any ClusterRole (and `bind` on one name only): the ClusterRole route (rewrite a ClusterRole of an operator name to carry VAP/VAPB write, bind it) is refused by RBAC itself (`claim-h-clusterrole`); the Role route (a Role of an operator name in `kube-system` with Secrets and `pods/exec`, bound to the controller) succeeds without the policies (`claim-h-open`) and is refused with P6 in Deny (`claim-h-guarded`). ### Lockouts and rolling back across releases

**The database refuses every connection** (`ECIRCUITBREAKER: too many authentication
failures` in every service's log, pods unready): Supabase's pooler blocks the project for
the cluster's NAT address (`63.188.104.25`, `3.120.13.212`) for 120 s after 10 failed
logins in 150 s, and repeated failures get the address banned on the database host.
**Do not re-run deploys** (`make k8s-apply-eks`, or syncs by hand): before D93 every
migrate run rewrote the role passwords and caused the next round of failures. Wait two minutes; find the failing
login (`kubectl -n ryft-<svc> logs -l app=<svc> --tail=-1 --since=15m | grep -v
ECIRCUITBREAKER | grep -i 'password\|28P01'`), and look at Supabase → Database →
Settings → Network Bans (or `supabase network-bans get --project-ref <ref>`) and remove
bans on those addresses. The pods reconnect on their own (incident of 2026-10-20 20:43,
`STATUS.md`).

**No down-migrations.** Migrations only add (tables, nullable or defaulted columns,
grants, backfills; never a drop or a rename), so the previous release runs on the newer
schema: it ignores what it does not know, and its migrate job skips every file it has
and does not mind newer rows in `schema_migrations`. A rollback is therefore never a
schema change.

**Rolling back past the RabbitMQ cutover** (D102): images from `fd36a9a` on carry both
brokers and follow `EVENTS_BACKEND`/`EVENTS_CONSUME`, which `overlays/eks/events.yaml`
sets to RabbitMQ, so they run without NATS. Images before `fd36a9a` know only NATS:
rolling back that far means restoring NATS first (revert the R4 commit, `infra/vault`
with the `nats` service again).

**Rolling back past the gate modes** (to a release before `beta: gate modes and admin
access grant`, e.g. `21eb0fa`) with `BETA_GATE = "warn"` in `infra/vault`: that release
knows only `on` and `off` and api and ingest do not start ("BETA_GATE must be on or
off"). Set it to `off` or `on` first (apply, restart the operator), then roll back.
`CONSENT_ENFORCE` it ignores: consent is then enforced again.

**Rolling back past the `smoke` subcommand** (`361e34a`): a rollback runs the hooks of
the OLD release, PreSync migrate and PostSync smoke from the `migrate:<pin>` image of the
rolled-back pin. A pin before `361e34a` has no `smoke` subcommand, so the PostSync hook
fails and the sync is reported failed although the pods rolled (the rollout itself is in).
Prefer a fix forward to a rollback that far.

**Dead letters** (`dlq.scoring`, `dlq.notify`, 14 days): an event that did not decode, or
failed six attempts (5 s, 30 s, 5 min apart). `scripts/dlq.sh` port-forwards to the
management API itself, on the cluster you name (`KUBE_CONTEXT=<context>` or `--context
<context>`; it never uses kubectl's current context, `scripts/lib/kube.sh`). Name it per
command, as below; do not `export` it, or the next script in that shell runs against it too:

```bash
KUBE_CONTEXT=ryft-prod-euc1 scripts/dlq.sh list                  # per queue, one line per letter: subject, attempts, error
KUBE_CONTEXT=ryft-prod-euc1 scripts/dlq.sh show dlq.scoring 5    # in full (n: 1 to 1000, or all)
KUBE_CONTEXT=ryft-prod-euc1 scripts/dlq.sh replay dlq.scoring 1  # after fixing the cause: back on ryft.events with its key, as a redelivery
KUBE_CONTEXT=ryft-prod-euc1 scripts/dlq.sh purge dlq.notify      # notify's: a push hours late is wrong (replay refuses without --force)
KUBE_CONTEXT=ryft-prod-euc1 scripts/dlq.sh put-back <dir>        # letters a failed replay kept in <dir>, back into their DLQ
```

(`ryft-prod-euc1`: the name from `kubectl config get-contexts -o name`, if your alias differs.)
`list` and `show` read at most 1000 letters a queue, so a DLQ with more shows 1000.

**Before a replay**, all of these:

1. The cause is fixed and **scoring runs the image that fixed it** (and reads the marker: check the
   pin in `overlays/eks` and that no hold keeps the services back). A deploy or rollout is not in
   progress: a restart interrupts a handling, and a surge runs two consumers for 10 to 30 s.
2. scoring's `ryft_amqp_connected` is 1, there is no `RabbitMQAlarm`, and the queue itself
   (`scoring`) is near empty, so the replay is not behind a backlog.
3. If the letters came from a crash, `kubectl --context ryft-prod-euc1 -n ryft-scoring get pods` shows no
   restart climbing and no `OOMKilled`: a letter that crashed the pod will crash it again.
4. `list` shows the letters you expect (count, subjects, the same error); `show` a few. **The first
   replay after this change is rolled out starts with `show` (or `purge`)**: a letter dead-lettered
   by an image from before D150 carries Ryft-Subject = the type its publisher set, which
   the script cannot tell from a real one (a letter of type `session.completed` published under
   the key `ingested` was filed under `session.completed`). The 14-day TTL empties these by itself.
5. Start with `replay dlq.scoring 1`, watch it succeed (below), then the rest.

**While it runs.** A replayed letter that fails again needs six handlings (at 0, +5 s, +30 s,
then +5 min three times), so about 16 minutes pass before it is back in the DLQ, and each
handling is a full catch-up re-score of the user's days after the letter's days: up to six re-scores
per failing letter, and fifty failing letters is 300. Hence one letter first.

- **Do not call it done** until `list` is empty 20 minutes later. `ryft_events_handled_total{result="retry"}`
  rising means a replayed letter is failing again; `failed` is it going back.
- Alerts: `RabbitMQDeadLetters` resolves as soon as the letters are taken off and fires again
  about 20 minutes later (16 minutes of attempts, then its 5 minutes) if they come back;
  `DeadLetters` counts dead-letterings over 1 hour, so after a successful replay it keeps firing
  for up to an hour on the dead-letterings that came before. The first dead letter after a
  scoring pod restarted is invisible to `DeadLetters` (its counter starts at 1, and `increase()`
  does not count the first sample); `RabbitMQDeadLetters` sees it.

A replay publishes each letter to `ryft.events` with its key, marked `x-ryft-replayed:
true` and without the `Ryft-*`, `x-death`, `x-delivery-count` and `x-ryft-attempt` headers. Its
consumer handles it as a redelivery (`events.Redelivered`), so a scoring letter re-scores the 30
days after its days and finishes a re-score its attempts left half-done (D112); it is
counted in `ryft_nats_redeliveries_total`, and scoring logs `handling a replayed dead letter` with
the key and message id. A scoring image from before the marker
ignores it: until scoring runs an image with it, follow a replay with `POST /v1/recompute` of its
days. It gets all six attempts again; if it fails them, it is back in the DLQ and `list`
shows it with `"replayed_before": true` (replaying it again before the cause is fixed
only repeats that).

**Which letters are replayed** (D150). Only the keys the queue's consumer is bound for
(`dlq.scoring`: `ingested`, `session.completed`; `dlq.notify`: `scored`, `session.scored`,
`refresh`), and a letter's key is read from where the publisher cannot write it:

- A letter the consumer filed carries `Ryft-Subject`, the routing key it arrived with; its type
  must equal that key.
- A letter **the broker dead-lettered** (its delivery limit, or the consumer's own copy into the
  DLQ failed: an `x-death` entry for the consumer's queue, `list` says `"dead_lettered_by_broker":
  true`) has no `Ryft-*` the consumer wrote, so any it carries is ignored. The entries for the
  consumer's queue must agree, and then its key is:
  - for an entry from exchange `ryft.events`, that entry's routing key (the publisher's, limited
    by topic permissions); the letter's type must be empty or equal it;
  - for an entry from `ryft.requeue` with routing keys `[<consumer>]` (the letter had been retried:
    a retry's copy has the queue's name as routing key), the letter's **type**, when that is a key
    the consumer is bound for: the consumer wrote it and checked it against the routing key on the
    first delivery, and only consumers may publish into the retry tiers.

  Anything else (an entry from another exchange or with other routing keys, entries that disagree, a
  retry's copy whose type is empty, not a key or not text, a type that says otherwise) is refused as
  "dead-lettered by the broker: check by hand", with what is wrong named.

Any other letter (a forged type: the broker's administrator would otherwise send it where its
publisher may not) goes back into its DLQ as it was and is named on stderr, as is a letter the
broker does not route; the script then exits 1. amqpbus drops `x-death`, `x-ryft-attempt` and
`Ryft-*` from a first delivery from `ryft.events` (a publisher sets any header, and a forged attempt
count would skip the retries), so a letter the consumer files never carries a forged account of
where it died.

**A letter that is refused and must go through** (`show` it first, and be sure of its key): publish
it by hand through the management API (UI or `POST /api/exchanges/ryft/ryft.events/publish`) with
`routing_key` the key, the same payload and `message_id`, `type` the key, `delivery_mode` 2 and the
header `x-ryft-replayed: true` (boolean). Leave out every other header the letter carries: `Ryft-*`,
`x-death`, `x-first-death-*`, `x-last-death-*`, `x-delivery-count`, `x-acquired-count` and
`x-ryft-attempt`. The original stays in the DLQ (`purge` deletes every letter of the queue, so purge only
when the rest are dealt with; otherwise the 14-day TTL removes it).

**Nothing is lost.** Taking letters off and republishing them are separate calls, so a
dropped port-forward can strand letters half-way: the script puts back what is left on
its way out, and if even that fails it keeps them in a directory it names (mode 700,
without the credentials), with `source.txt` saying which cluster (or broker URL) they came from.
Put them back with `KUBE_CONTEXT=… scripts/dlq.sh put-back <dir>` once the cluster answers
again: it refuses a directory from another cluster or broker, or one without a `source.txt`, and
afterwards removes what it wrote there (`source.txt` and the like) and the directory, with `rmdir`,
when that leaves it empty; it never removes the current directory, a `taken.json` or anything of yours.
Give the broker's login as `RABBITMQ_USER` and `RABBITMQ_PASSWORD`, not inside `RABBITMQ_MGMT_URL`
(the URL is recorded, minus everything before its last `@`). A second Ctrl-C, a TERM or a dropped session (SIGHUP)
does not stop that way out, and it names the directory before it starts; after a dropped session
the message may not have reached you, so look for a `dlq.*` directory in `$TMPDIR` (or
`/tmp`) with a `pending/` in it, and put back what it holds. A `dlq.*` directory with a
`taken.json` is different: the take's answer could not be read, and the letters are only in that
file, and the directory has a `source.txt` from the start of the take. Read it, then either publish
what matters by hand (as above), or split it into one `*.back.json` per letter in that directory
(`{"routing_key": "<consumer: scoring or notify>", "properties": {…the letter's properties…},
"payload": …, "payload_encoding": …}`) and run `put-back` on it; then delete the directory; `taken.json` holds message
bodies, which name users and days. A kept directory must not outlive the DLQ's 14 days: after that
the letters would be older than any copy of them, and the replay's premise (the cause fixed) is stale.
The take itself may run for
half an hour (its letters are gone from the queue before the answer arrives); every other
call gives up after two minutes. A letter can then be in its DLQ twice (put back after a publish
whose answer was lost); handlers are idempotent (D100). Every argument is checked first,
and without a named context the script reaches no cluster; credentials go to `curl` in a
config file, never on its command line, and `curl -q` never reads `~/.curlrc`.

Re-drive after fixing the cause (a deploy, a data fix). scoring's letters only name a
user and days, so `POST /v1/recompute` or `KUBE_CONTEXT=ryft-prod-euc1 scripts/rescore_all.sh` repair the same if a
letter is gone; notify's are listed and purged, never re-sent late.

**The outbox** (D101): events waiting for the broker are rows of `outbox` in Postgres
(SQL editor, as the owner):

```sql
SELECT publisher, count(*), min(created_at) FROM outbox WHERE published_at IS NULL GROUP BY 1;
SELECT id, publisher, routing_key, attempts, last_error FROM outbox WHERE published_at IS NULL AND attempts >= 50;
UPDATE outbox SET attempts = 0 WHERE id = 1234;   -- a stuck row, once its cause is fixed: the relay sends it again
```

Waiting rows mean the relay cannot reach the broker or the broker refuses (a full queue,
an alarm); they go by themselves once it accepts. A stuck row (50 failed sends) is
usually a key no queue is bound for: a topology change missed.

**Changing the topology:** edit `backend/internal/events/amqpbus/topology.go`, run
`go run ./cmd/rabbitmq-topology` in `backend/`, commit both files; Argo CD applies it. A
queue's arguments cannot change (the Topology Operator refuses): tune with its policy.
Queues and the vhost have `deletionPolicy: retain`, so removing one from the topology
leaves it in the broker; delete it in the UI once it is empty.

**A node drain** (a node group rotation): the PDB lets one RabbitMQ pod go at a time, and
the pod waits up to 10 minutes to hand over its quorum queues. Two of three nodes keep
every queue working; with one left, publishes are refused (the outbox keeps them) and
consumers stop until a second node is back.

**Alarms:** the memory watermark is 60 % of what the operator gives RabbitMQ of the
1 GiB limit (80 %): about 0.52 GB a node (`rabbitmq-diagnostics -q status`; a node uses
about 130 MiB idle); the disk alarm
at 1 GB free of 10 GiB. Either blocks every publisher until it clears
(`RabbitMQAlarm`); first look at the queue depths (a consumer that stopped consuming).

**The operators' reach** (T12-g, D97): both operators run in `rabbitmq-system` but watch
and write `ryft-rabbitmq` only (`OPERATOR_SCOPE_NAMESPACE=ryft-rabbitmq` on both
Deployments), and neither holds a cluster-wide `secrets` or `pods` right. Their former
ClusterRoles are replaced by Roles in `ryft-rabbitmq` (`scoped-rbac.yaml` beside each

controller). The leader election stays in `rabbitmq-system`. The Argo CD project

**Before the sync, a baseline:** save both operators' logs
(`kubectl -n rabbitmq-system logs deploy/rabbitmq-cluster-operator > before-cro.log`, the same for

## Self-hosted (overlays/local-postgres)

## Network policy

Every namespace starts with `default-deny` (no ingress, no egress) and `allow-dns`
(`base/common`). Each workload then allows exactly its own flows
(`base/<service>/networkpolicy.yaml`):

| Workload | In | Out |
| --- | --- | --- |
| ingest, api | 8080 from Traefik in `kube-system` (and from the PostSync smoke pod in `ryft-smoke`); 9090 (`/metrics`) from namespace `monitoring`, and on EKS from the VPC range (the host-network collector) | RabbitMQ (`ryft-rabbitmq`, 5671), TCP 443 + 5432 to public addresses (Supabase Auth, the pooler) |
| scoring | 9090 from `monitoring` (and the VPC range on EKS); 8080 from the PostSync smoke pod in `ryft-smoke` (readiness) | RabbitMQ (5671), TCP 5432 to public addresses |
| notify | 9090 from `monitoring` (and the VPC range on EKS); 8080 from the PostSync smoke pod in `ryft-smoke` (readiness) | RabbitMQ (5671), TCP 5432 (the pooler) and 443 (APNs: `api.push.apple.com`, `api.sandbox.push.apple.com`) to public addresses |
| web (`ryft-web`) | 8080 from Traefik in `kube-system` | nothing |
| rabbitmq | 5671 from the `ingest`, `scoring`, `api` and `notify` pods, each in its own namespace; 15671 from the Topology Operator; 15692 (metrics) from the VPC range; the Erlang ports from its own nodes | its own nodes, the Kubernetes API (peer discovery) |
| migrate | nothing | TCP 5432 to public addresses |
| postgres (`local-postgres`) | 5432 from the five client namespaces and the backup pods | nothing |

"Public addresses" means `0.0.0.0/0` minus RFC 1918, CGNAT and link-local ranges, so no
workload can reach anything inside the VPC or the cluster on those ports. NetworkPolicy
cannot name hosts, so the ports are the restriction for the internet. The
`local-postgres` overlay adds `allow-local-postgres` egress for the in-cluster
database. Kubelet probes come from the node and are admitted by the EKS VPC CNI (and
k3s, Calico, Cilium). Namespaces are matched by `kubernetes.io/metadata.name`, which the
API server sets and nobody can relabel.

Adjust the `from` of ingest/api for another Ingress controller, or add a `cloudflared`
peer if a Cloudflare tunnel targets the services directly.

### Edge rate limit

Before any token is checked, Traefik limits each client IP to 20 requests a second on
average, with bursts of 50 (`overlays/eks/ratelimit.yaml`, a `Middleware` in `ryft-api`,
`ryft-ingest` and `ryft-web`). Each of the two Traefik replicas counts on its own, so
the effective limit is up to twice that. Over it, Traefik answers `429` with a
plain-text body. The NLB preserves client addresses, which this needs (a target-group
attribute in `infra/aws/kubernetes`). Check it from one machine, expecting `429`s
after the first ~100:

```bash
for i in $(seq 1 150); do curl -s -o /dev/null -w '%{http_code}\n' https://api.ryftapp.de/v1/me; done | sort | uniq -c
```

The services' own per-user limit (D36) applies after the token, so the two complement
each other.

**A new policy text** (only on the user's decision: everyone consents again) is **one
PR and no restart**: `web/content/legal/{en,de}/privacy/<version>.mdx` (the old versions
stay), `<version>` appended to `web/content/legal/privacy-versions.json`, and
`PRIVACY_POLICY_VERSION` in `deploy/k8s/base/api/config.env`,
`deploy/k8s/base/ingest/config.env` and `docker-compose.yml`. The base value is the version
that is *published*. The version in force on EKS is a pin in
`overlays/eks/kustomization.yaml` (two `ryft-config` literals, api and ingest) that CI's
promote moves to the base's value in the same deploy PR that pins the web image carrying the
page. So the page, web, api and ingest go live in one Argo CD sync: the merge itself changes
nothing on EKS, and there is no interim restart. A service's ConfigMap is generated as
`ryft-config-<hash>`, so a changed value renames it and rolls exactly the pods that read it.
`manifests` runs `node web/scripts/check-policy-version.mjs --strict` (published version,
pages, compose) and `scripts/check_policy_in_force.sh` (api and ingest agree, the pinned web
commit serves the version at `/privacy`, newest page in both languages). If web is held or its build fails, the old version stays in force
with the old site. The deploy PR body shows `privacy policy in force: A → B`.

What to watch after the deploy PR merges (read-only):

The roll is a rolling update of a minute or two in which old pods still serve the old
version: `ryft_consents_total{action="stale"}` and `consent_required` refusals bump briefly
and recover. The PostSync smoke consents through api and syncs through ingest, so it proves
the two agree. Argo CD deletes the old `ryft-config-<old>` only after the sync is healthy
(`PruneLast`); until then the old hash is still listed. Rolling a ReplicaSet back by hand is
not a rollback path (its ConfigMap may be pruned, and self-heal reverts it): revert in git.

Withdrawing a version. A policy PR itself cannot be reverted as a whole (the versions list is
append-only), and the check requires the in-force version to be the NEWEST page of the pinned
web commit (that is what `/privacy` serves). So setting the in-force pin back alone fails the
check, and would be undone by the next web deploy anyway. A withdrawal is durable only as a
NEW version (the corrected text, appended) or with web held and pinned back (`pin_images.sh`
and `hold.sh add`, in one commit), never as the pin alone. If a sync fails in the middle (web
stuck while api and ingest are already on the new version, or the reverse), move web and the
in-force pin back together in one commit; the check refuses a pair that disagrees.
On a pull request `check_policy_in_force.sh` also refuses a version that becomes the one in
force, or the published one in `config.env`, unless its page in both languages says exactly
`status: published` (read as the site reads it; a tag, flow frontmatter or a block scalar
refuse even when published). Anything else is a draft for this check. Going back to a version
listed before the one in force now is allowed. So a policy PR stays red until `status:
published` is set in that same PR, and a draft version on main blocks every deploy PR, services
too, until it is published or web is held. A text that is published cannot be un-published in
place: the check also refuses a PR that sets a published page back to a draft, and a web pin
that would serve the draft again under the same version (a rollback past the commit that
published it, or to `f437747`, which carries 2026-10-20 as a draft). Publish a new version
instead.

### Admin sign-in

`/v1/admin/*` takes two bearers (docs/API.md → Admin routes): the key above (scripts, smoke;
compared first, in constant time, independent of Supabase), or the Supabase access token of
an operator, for the operator's web page. A token is accepted only when **all** of these
hold: `app_metadata.role` is `"admin"` (never the top-level `role`, never `user_metadata`,
which the user can write), the user has a row in `admin_accounts` and no tombstone, and the
token is `aal2` with a TOTP at most 12 hours old. Everything else is one identical `401`
(the reason is only in the log: `admin auth rejected`, `reason` and the access line's `code`).
One exception, plainly: a token whose key id the api does not know, while the signing keys were
fetched less than a minute ago, answers `503` (`jwks_refresh_limited`, `Retry-After: 5`), not `401`.
Anyone can send such a token, so a `503` on an admin route can be provoked and is not by itself an
outage: it means the api could not complete a key fetch (or the allow-list check) for that token,
which includes a fetch that ran past its 1 s. It is kept on purpose (D184: a `401` there was
considered and rejected). A client that hangs up no longer counts as a failed fetch (D184), so it
cannot turn later answers into `jwks_unavailable`. A real operator without a fresh second factor gets `403 mfa_required` (and an audit row);
an operator's token on merge, flag writes, user detail or resync-hint gets `403` (key-only routes,
audited). The token's answers for the users list and the feedback are a projection without the
health-derived, device and diagnostic fields (API.md); the key gets the whole answers.

**What changes on deploy, and for whom.** The token path admits nobody until an `admin_accounts`
row exists *and* the account has the role, and CORS is off while `ADMIN_WEB_ORIGINS` is empty.
For key callers (scripts, `make smoke-prod`) three small things change: more than 10 requests a
second from one address now get `429`, the `401` text is `admin key or admin sign-in required`,
and the scheme `bearer` in lower case is accepted. Granting access is two statements in the
SQL editor, as the owner, by id; they are one trust domain (the Supabase project owner), and the
row exists so that revoking takes effect at once, not so that two parties must agree. **Before the
first row, run `make alerts-apply`** (the user's step; it needs `GRAFANA_PROM_URL`,
`GRAFANA_PROM_USER` and `GRAFANA_RULES_TOKEN`): alert rules reach Grafana only through that manual
apply, and `AdminWebUsed` is how a use you did not make is noticed (the lost-phone detection), so
the token path must not be opened before it is loaded.

```sql
update auth.users set raw_app_meta_data = coalesce(raw_app_meta_data, '{}'::jsonb) || '{"role":"admin"}'::jsonb where id = '<admin uuid>';
insert into public.admin_accounts (user_id, note) values ('<admin uuid>', 'operator') on conflict do nothing;
```

A role set this way appears only in tokens issued after the update: sign in again on the page.
The api only reads `admin_accounts`; it is operator configuration, not user data (account
deletion does not touch it; a deleted account's tombstone refuses the row). Which pages may
read the answers: `ADMIN_WEB_ORIGINS` in `deploy/k8s/base/api/config.env` (a comma-separated
list of exact origins, e.g. `https://ryftapp.de`; empty means no browser page can, scripts are
unaffected; a malformed value stops the api at start-up, before it waits for the database, and a
test parses the committed line). Every `/v1/admin/*` request is limited per client address (10 a
second, bursts of 20, per pod; the address is the rightmost `X-Forwarded-For` entry, Traefik's;
never logged; the map is bounded only by evicting a bucket idle for 10 minutes and needs a cap
before IPv6 clients arrive), and every admin log line carries `admin_actor` (`key:3fa1c2d9` or `user:1b2c3d4e`,
the first 8 hex digits). The audit (`GET /v1/admin/audit`) names the actor: `actor.kind` `user` or `key`.

user detail and resync-hint stay with the key and the scripts. A lost phone: the runbook below (**not verified**: no run of

## Two accounts for one person

**How it happens:** someone signs in with email and later with Apple (or the other way
round). Supabase links the two only when Apple hands over the same verified email; with
"Hide My Email" it is a relay address, and a second account appears. The app syncs into
whichever is signed in, so the data splits.

**How to see it:** `scripts/beta_report.sh` → `dup` (accounts that synced from the same
device id in the last 30 days); `scripts/user.sh <id>` names them under "possible
duplicate", with provider, last sync and days scored. The app is told too
(`GET /v1/me` → `account_hint`, API.md).

**How to merge** (D90): the smaller account into the one with the history. The plan
first, then the merge, which moves everything in one transaction, rescores the kept
account over the moved days, and deletes the other one like `DELETE /v1/me` (Supabase
sign-in and Apple grant included):

```bash
scripts/user.sh <from> --merge-into <to> --dry-run      # per table: moved, dropped (to's row kept), and why
scripts/user.sh <from> --merge-into <to>                # shows the plan again, asks for MERGE
```

Where both accounts have the same row (a sample, a device id, a session id, a journal
day, a custom exercise's slug), the kept account's wins and the other's is counted as
dropped. A consent and beta access are copied only when the kept account has none.
Merging the account with more scored days into the smaller one is refused (`409`) unless
`--force`. A second run answers `404` (from is gone). **After the merge, fold the target's
workouts**: both accounts may have held copies of one workout under different ids
(`fold-workouts -user <to>`, "Fold duplicate workouts" below; dry-run first). Afterwards, the person signs in the
way the kept account uses; if both identities should open it, they link Apple to the
email account in the app (Supabase **manual linking**, `SUPABASE.md`).

**Imported training history and a merge.** The app derives the training import's ids from the
account's id (API.md → `POST /v1/train/import` → For the app). The merge moves imported
sessions and plans with the ids they have; an import of the same file into the kept account
would derive other ids and store that history a second time. So after a merge the person must
not import the same file again: tell them when you merge. A server-held import namespace that
the merge carries over is an open point (D141).

## Fold duplicate workouts

What it does: `ingest fold-workouts` removes the extra copies of one workout that were
uploaded before the app sent deletions (D-c, `docs/work/2026-10-31-data-quality/design.md`).
Two workouts of one user are one when they have the same `source` and `activity` and both
their starts and their ends are within 120 s and they overlap by at least half of the
shorter one. Per group it keeps the most recently
uploaded id (`created_at`, ties to the higher id) and **deletes the rest**. `ryft-session`
workouts are never touched, and users without a current consent are skipped (counted in the
summary). A Train session on a removed copy stays; scoring attaches it to the kept workout
when the day is rescored. The days of the removed rows (and the day after, and the day
before when a session was attached) are queued and one `ingested` event per user goes
through the outbox, so the running ingest relays it and scoring rescores them. New syncs
fold on their own; this is for what is already stored.

**It cannot be undone** by this tool. The recovery path is Supabase's own backup (7 days;
`Backups`). A copy folded under that rule (120 s at both ends, at least half overlap) is near-identical
to it, so what is lost is a duplicate row, not a workout. There is deliberately no export
step: health rows on a laptop would outlive the retention, and the ids of a dry run can
differ from the real run's if a sync lands between them.

Flags only; any other argument exits 2 without doing anything. A real run needs either
`-user <uuid>` (one account) or `-all` (every account); `-dry-run` over everyone needs
neither.

```bash
# 1. Dry run for one account, then for everyone. Reads only; no lock, no queue, no event.
kubectl --context ryft-prod-euc1 -n ryft-ingest exec deploy/ingest -- /app fold-workouts -user <uuid> -dry-run
kubectl --context ryft-prod-euc1 -n ryft-ingest exec deploy/ingest -- /app fold-workouts -dry-run
```

It prints one line per group, `user=<uuid> day=<yyyy-mm-dd> kept=<id> folded=<id>,<id>`
(ids and a day, no health values), and a summary (`would fold N workouts in G groups, U of
T users, S skipped without consent, F failed`). The lines name a user who worked out on a
day: keep them out of tickets and chat. Check the reporter's account against what you
expect before going on (6 on 2026-10-20).

```bash
# 2. For real: one transaction per user, under the user's apply lock. It prints the same
#    list, now of what it deleted.
kubectl --context ryft-prod-euc1 -n ryft-ingest exec deploy/ingest -- /app fold-workouts -user <uuid>
kubectl --context ryft-prod-euc1 -n ryft-ingest exec deploy/ingest -- /app fold-workouts -all
```

The summary now reads `folded N workouts ...`. A second run prints `folded 0 workouts in 0
groups`. The exit status is non-zero when any user failed (that user's transaction rolled
back; run it again) or when the command was interrupted. Locally:
`podman compose exec -T ingest /app fold-workouts -dry-run`. Counters:
`ryft_workouts_folded_total{reason="same_source"}` (the one-off process does not serve
metrics, so only the syncs' folds show up there) and
`ryft_workouts_fold_skipped_total{reason="too_many"}` (a sync whose scope held more than
5 000 workouts folded nothing; run `fold-workouts -user <uuid>` for that account).
`scripts/rescore_all.sh` is not needed: the queued days are rescored by the running
scoring service.

## The coverage gate went red

`coverage-gate` (the `test` job of a pull request, D148) says "internal/ coverage fell from X% on main to Y%".
The job summary lists every package; compare it with the `coverage` artifact of the latest push run on main to see
which package lost. Usual causes: code added without a test (add the test), a test that needs Postgres or RabbitMQ
that skipped (look for a service container that did not start, then re-run the job), or main moved: the baseline
is main's tip, so rebase first. A drop that is really intended (code deleted together with its well-tested
siblings) is accepted by raising `MAX_DROP` in the PR's own `ci.yml` for that PR, with the reason in the
description; there is no other override. A warning "main's coverage is unknown" is not a failure: the gate passed
without a baseline (artifact outage or expired); re-run once the artifact is back. Locally: `make coverage`.

## Training import

`POST /v1/train/import` (D124-D133, API.md) stores plans and finished sessions that the
app parsed from another training app's export, each item in its own transaction, then
queues the days with one `ingested` event (`reason` `import`) for scoring, then
recomputes the records. Imported sessions send no `SESSION_SCORED` or `PR` push and move no
enrolment. The switch is the flag `train.import` (dark by default: testers by the allow-list,
Feature flags); the app hides the import while it is off, and the endpoint checks it too
(`403 import_not_enabled`), so the kill switch does not wait for the app's cached config.
A resend never overwrites what the user changed in the app since (`newer_on_server`, D141).

`KUBE_CONTEXT=ryft-prod-euc1 scripts/trace.sh <request id>` shows the access line and the import's one line
(`msg="train import"`: `result`, the items sent and their statuses, the days queued;
never a title, a value, an id list or the source app), then scoring's lines for the same id.

| Sign | Means | Do |
| --- | --- | --- |
| `429`, `code=import_in_progress` | another import of the account holds the lease (`users.import_lease_until`, 70 s, D132) | nothing: the app waits `Retry-After` (10 s) and resends the same request. A pod that died mid-import blocks that account for up to 70 s; the lease expires on its own, do not clear it by hand |
| `503`, `result=timeout` or `error` | the 50 s ran out (the items stop at 40 s), or the database failed; what was stored stays stored and was finished | nothing: the app resends, the stored items come back `unchanged`. Many in a row: `ryft_db_up`, `ryft_train_import_seconds` |
| `403`, `code=consent_required` | no consent to the current privacy policy (the import is an upload of health data, D129); on this route `CONSENT_ENFORCE=warn` refuses too (D141) | as for a sync (Beta) |
| `403`, `code=import_not_enabled` | the flag `train.import` is off for the account (`ryft_train_imports_total{result="disabled"}`) | intended for anyone not allow-listed; a tester: add the id to the allow-list (Feature flags) |
| `429` without a `code` | the import's own rate budget: bursts of 5, then one every 5 s (`ryft_rate_limited_total{class="import"}`) | nothing: the app waits `Retry-After` |
| `200` with `rejected` items | items the app must change; the `code` and `message` (ids and field names) are in the response only | the app's report; `ryft_train_import_items_total{status="rejected"}` |
| `days_touched` stay pending | scoring is behind | as for a sync (above) |
| sessions older than 400 days without strain | by design: stored for history and records, never scored (D128) | nothing |

## Feature flags

`GET /v1/config` serves the flags in table `feature_flags` (D69). Change them with the
admin routes and the api's `ADMIN_API_KEY` (generated by `infra/vault`):

```bash
ADMIN=$(terraform -chdir=infra/vault output -raw admin_api_key)    # locally: dev-admin-key-change-me-0123456789abcdef
API=https://api.ryftapp.de
curl -s -H "Authorization: Bearer $ADMIN" $API/v1/admin/flags | jq            # every flag
# On for two testers only (their user IDs: GET /v1/me → id):
curl -s -X PUT -H "Authorization: Bearer $ADMIN" $API/v1/admin/flags/today.redesign \
  -d '{"enabled": true, "rollout_pct": 0, "allow_user_ids": ["<uuid>", "<uuid>"]}'
# 10 % of everyone, then everyone:
curl -s -X PUT -H "Authorization: Bearer $ADMIN" $API/v1/admin/flags/today.redesign -d '{"enabled": true, "rollout_pct": 10}'
curl -s -X PUT -H "Authorization: Bearer $ADMIN" $API/v1/admin/flags/today.redesign -d '{"enabled": true, "rollout_pct": 100}'
# Kill switch (off for everyone, testers included):
curl -s -X PUT -H "Authorization: Bearer $ADMIN" $API/v1/admin/flags/today.redesign -d '{"enabled": false, "rollout_pct": 100}'
curl -s -X DELETE -H "Authorization: Bearer $ADMIN" $API/v1/admin/flags/some.old_flag      # 204
```

`PUT` replaces the whole flag (`enabled` and `rollout_pct` required, a missing
allow-list is empty) and answers `201` for a new key, `200` otherwise; the api logs
every change (`msg="feature flag set"`). The app caches its answer for up to six hours,
so a change reaches everyone within that. Rotate the key with
`terraform apply -replace='random_password.admin_key["api"]'` in `infra/vault`.

## Scaling and disruptions

api and ingest run 2–4 replicas under a CPU HPA (70 % of the 50m request; needs
metrics-server), with a `PodDisruptionBudget` of `minAvailable: 1`, spread across nodes
when there are several. On a **single-node** cluster a drain blocks on the second pod,
because the first has nowhere to reschedule. Use `kubectl drain --disable-eviction`, or
`kubectl -n ryft-api delete pdb api; kubectl -n ryft-ingest delete pdb ingest` before
maintenance and re-apply afterwards. web (the apex site, two replicas) has a
`PodDisruptionBudget` of `maxUnavailable: 1`: a drain or node group update takes one site pod
at a time (it is not in local-postgres). Pods that are not ready never count
(`unhealthyPodEvictionPolicy: AlwaysAllow`): during an outage, when no pod is ready, a
drain or a node group update still goes through. Their Deployments carry no `replicas`, so
re-applying never fights the HPA. scoring stays at one replica: it owns the 15-minute
timer and processes recompute ranges in order. RabbitMQ has its own PDB (one node at a
time, OPERATIONS → RabbitMQ → A node drain).

### Vault metrics (once)

The in-cluster Vault is scraped by `alloy-deployment` (jobs `ryft/vault` and

process start and sets it back only on unseal, so when every pod restarts and stays sealed the

hour after a restart goes quiet.

### Vault alerts

Group `ryft-vault` (OBSERVABILITY → Alerts → Vault). The Vault CLI below runs in the session
shell (Vault: the port-forward, `~/.config/ryft/vault-ca.pem`) with the admin token of a
generate-root session (D209, Vault → Login); `vault status` and `vault operator unseal` need
no token. The
rules that would fire before the init are gated on "this Vault has been initialised": a server
pod labelled `vault-initialized=true` in the last hour, or a snapshot that has succeeded once.
The label means "unsealed at least once since this process started" (Vault resets it to `false`
at every start; the source and its status are in OBSERVABILITY → Alerts → Vault, **to verify
in the kind drill**), so after a restart of every pod that stays sealed only the snapshot half
holds: the hand-run first snapshot (Vault metrics (once)) is what keeps these alerts alive then.

**Known gap:** with the StatefulSet itself gone (deleted, or not yet recreated after a restore),
`VaultUnavailable` and the server and kubelet branches of `VaultScrapeDown` are silent by design
(they need its series); only `PodRestarting` and the snapshot alerts remain.
The procedures for the states themselves are Vault's sections (#151); these entries say which
one and what the alert adds.

- **VaultSealed** (warning, one pod). Vault → **A pod is sealed**. Which pod:
  `kubectl --context ryft-prod-euc1 -n vault get pods -L vault-active,vault-sealed`. `474` in the
  probe events is a standby without the active node: Vault → **The leader is gone** (probe
  codes).
  - **shamir** (the default, D208): expected after every restart (a drain, an eviction, an OOM
    kill, a roll); it does not clear by itself. Unseal it by hand, three shares, one pod at a
    time: the next only once this one is `1/1` and autopilot Healthy. Until then no node
    maintenance (the PDB blocks a second drain).
  - **awskms**: a fault, the pod should have unsealed itself. A pod that started before its
    Pod Identity association gets no credentials until it is recreated
    (`aws eks list-pod-identity-associations --cluster-name ryft-prod-euc1 --namespace vault --region eu-central-1`).
- **VaultSealedQuorum** (critical, two or more pods). Vault → **Quorum loss**.
  - **shamir**: unseal each pod by hand (Vault → **A pod is sealed**), one at a time; the
    second unsealed pod brings the leader back (if one pod stayed unsealed, that is your first
    unseal). Nothing reads or writes Vault until then; the workloads keep their synced Secrets.
  - **awskms**: several sealed at once point at the shared cause, the unseal key or its role:
    `aws kms describe-key --key-id alias/ryft-prod-euc1-vault-unseal --region eu-central-1`
    (`Enabled`, not `PendingDeletion`) and CloudTrail's `Decrypt` by `ryft-prod-euc1-vault-unseal`.
- **VaultUnavailable** (critical, no server ready for 10 minutes, whatever the reason).
  `kubectl --context ryft-prod-euc1 -n vault get pods -o wide` and `describe` the pods: sealed
  (Running, `0/1`; shamir: unseal by hand, Vault → **A pod is sealed** / **Quorum loss**), Pending (no node in the
  volume's zone), a crash loop (`logs --previous`). VSO keeps the Secrets it synced; nothing
  renews or rotates until a server is back.
- **VaultNoActiveNode** (critical). Vault → **The leader is gone**, and with two voters down
  **Quorum loss**. Each node's view, no token needed:
  `for i in 0 1 2; do kubectl --context ryft-prod-euc1 -n vault exec vault-$i -- vault status; done`.
  It stays quiet while every server scrape fails (that is VaultScrapeDown: blind, not
  leaderless).
- **VaultRaftPeersBelow3** (warning). `vault operator raft autopilot state` names the unhealthy
  voter; `kubectl --context ryft-prod-euc1 -n vault get pods -o wide` its node and zone. A
  Pending pod waits for a node in its zone. A volume lost for good: Vault → **A lost volume**.
- **VaultAuditFailing** (critical). A node failed to write an audit entry in the last 10
  minutes: requests go unrecorded, and with both devices failing Vault refuses them.
  `vault audit list -detailed` (both devices, `log_raw=false`); the audit volume:
  `kubectl --context ryft-prod-euc1 -n vault exec <pod> -- df -h /vault/audit`. A full volume
  is VaultVolumeFilling's case, below; a broken `stdout` device shows in the pod's log.
- **VaultVolumeFilling** (warning). Which claim: `data-vault-N` (Raft; BoltDB grows with
  history) or `audit-vault-N` (the audit file only grows). Expand **the PVC only**
  (gp3-encrypted allows expansion; ask first, it is a change):
  `kubectl --context ryft-prod-euc1 -n vault patch pvc <claim> -p '{"spec":{"resources":{"requests":{"storage":"<new size>"}}}}'`,
  then watch `kubectl --context ryft-prod-euc1 -n vault get pvc <claim>` reach the new size.
  **Leave vault.tf as it is:** a StatefulSet's `volumeClaimTemplates` are immutable, so a new
  `dataStorage`/`auditStorage` there fails the apply. If a template change is ever needed (a
  new size for future pods, a new storage class): delete the StatefulSet without its pods
  (`kubectl --context ryft-prod-euc1 -n vault delete statefulset vault --cascade=orphan`; the
  pods keep running and serving), apply `infra/aws/kubernetes` with the new template (the
  release recreates the StatefulSet, which adopts the pods), then roll as Vault → Day 2. Ask
  first; with every pod `1/1` and autopilot Healthy before.
- **VaultUpdatePending** (info, after 24 h). Vault → **Day 2** (applying a template change,
  `OnDelete`). Until it is done no node maintenance: a drain would roll the pod unplanned (D204).
- **VaultScrapeDown** (warning). `ryft/vault-state` missing: the collector
  (`kubectl --context ryft-prod-euc1 -n monitoring get pods`, its log), or the monitoring values
  not applied (right after `make alerts-apply`: the rules went in before
  `make monitoring-apply`; this half is not gated, apply the monitoring and it resolves).
  `ryft/vault` failing for a pod: `vault_collector_peer` still false (Vault
  metrics (once), step 2), TLS in the collector's log (`x509`: the `vault-ca` Secret in
  `monitoring`, step 1), or a timeout (the vault-server NetworkPolicy's collector rule:
  `kubectl --context ryft-prod-euc1 -n vault get networkpolicy vault-server -o yaml`).
  `kubelet volume stats`: Fleet's kubelet pipeline sends none for `vault` (step 4).
- **PodRestarting** for a vault pod: the previous container's log
  (`kubectl --context ryft-prod-euc1 -n vault logs <pod> --previous`); an OOM kill is the
  512 Mi limit in vault.tf. Under shamir every restart leaves the pod sealed: `VaultSealed`
  follows, unseal it (Vault → **A pod is sealed**).

## Admission policy signals

The admission policies (D120, `docs/work/2026-10-23-admission/design.md`) write what they
decide into two places: the API servers' counters and the audit log. Alerts watch them
(OBSERVABILITY → Admission). The data path is `deploy/monitoring/k8s-monitoring.yaml`: Alloy
scrapes each API server endpoint (job `ryft/kube-apiserver-admission`; three metric
families, Pod Security refusals only), and kube-state-metrics' own collector exports the
chart's bindings (job `ryft/admission-bindings`). What each binding was committed as
comes from `deploy/grafana/alerts/admission-intended.yaml`, generated from
`infra/aws/kubernetes/admission-values.yaml`.

**Turn it on (once, before Phase 1; yours, nothing here is applied by Git):**

```bash
make monitoring-apply KUBE_CONTEXT=ryft-prod-euc1   # helm upgrade of grafana-cloud; only kube-state-metrics rolls (its collectors list), Alloy reloads its ConfigMap
make alerts-apply          # both rule files: ryft (groups ryft, ryft-pipeline, ryft-ops, ryft-admission) and ryft-admission (the committed actions)
```

Apply the monitoring values first: until the scrapes report, `AdmissionSignalsMissing` fires
(that is its job). Then check in Grafana Explore (the Prometheus data source):

- `up{job=~"ryft/kube-apiserver-admission|ryft/admission-bindings"}` is 1: one series for
  each API server endpoint (EKS runs at least two) and one for kube-state-metrics. If the
  API server targets are missing, the collector pod's log says why (`kubectl -n monitoring
  logs deploy/grafana-cloud-alloy-deployment | grep -i apiserver`).
- If remote_write answers 401 or 403: check that the access policy of `GC_TOKEN` has
  `metrics:write`. The Fleet pipelines write with the same token, so a token that cannot
  write breaks them too; do not widen a shared token for this.
- `pod_security_evaluations_total{decision="deny"}` and
  `apiserver_validating_admission_policy_check_total` have series only after the first
  refusal or finding: absent is normal, there is no series for a clean pass.
  `kube_validatingadmissionpolicybinding_info` has 17 `ryft-*` series once the chart is enabled,
  `kube_validatingadmissionpolicybinding_validation_action` one per live action, and
  `ryft:admission_binding_intended` 17 whether or not the chart is enabled.
- The binding alerts are quiet until bindings exist; the counter alerts are quiet until a
  `ryft-*` policy finds something.

**A step change** (a reviewed PR edits `actions:` in `admission-values.yaml`): regenerate
`scripts/admission_intended.sh` in the same PR (`make alerts-check` fails otherwise; the
generator also fails when the keys of `actions:` differ from the chart's). After the merge,
do the Terraform apply first, then `make alerts-apply`. In between, the live actions are
ahead of the committed ones, which shows as `AdmissionBindingDrift` with its two-hour wait
(a deny that went live) and clears when the rules load; the other order would raise
`AdmissionBindingNotDenying` after ten minutes. A one-plan `-var` override of
`admission_actions` is not mirrored in the rules: expect Drift or NotDenying for it until it
is committed in the values file.

**Reading a finding.** Every alert names a `policy` (the policy object, e.g.
`ryft-workloads`) and a `policy_binding` (e.g. `ryft-workloads-pods`); P-numbers and steps
are labels on the bindings:

```bash
kubectl get validatingadmissionpolicybindings \
  -L admission.ryft.dev/policy,admission.ryft.dev/step,admission.ryft.dev/intended-action,admission.ryft.dev/break-glass
kubectl get validatingadmissionpolicybinding <binding> -o jsonpath='{.spec.validationActions}'
```

The audit log has the objects. CloudWatch Logs Insights, log group
`/aws/eks/ryft-prod-euc1/cluster` (confirm the field names once in the console), a day of
findings counted by distinct object and split by dry runs from real writes (an Argo CD diff
or `kubectl --dry-run=server` is a dry run and writes nothing; a real write is the one
that matters):

```bash
aws logs start-query --region eu-central-1 --log-group-name /aws/eks/ryft-prod-euc1/cluster \
  --start-time $(( $(date +%s) - 86400 )) --end-time "$(date +%s)" \
  --query-string 'filter @logStream like /kube-apiserver-audit/
    | filter ispresent(`annotations.validation.policy.admission.k8s.io/validation_failure`) or ispresent(`annotations.pod-security.kubernetes.io/audit-violations`)
    | fields strcontains(requestURI, "dryRun") as dryRun
    | stats count(*) as evaluations, count_distinct(objectRef.name) as objects by dryRun, user.username, objectRef.namespace, objectRef.resource'
aws logs get-query-results --region eu-central-1 --query-id <queryId>
```

`evaluations` counts audit events (a controller that retries counts every try); `objects`
is the number of different objects, the one to read. For one object's message, keep the two
`filter` lines and end the query with plain named fields instead of `stats`:

```
fields @timestamp, user.username, verb, objectRef.resource, objectRef.namespace, objectRef.name, requestURI, `annotations.validation.policy.admission.k8s.io/validation_failure`
| sort @timestamp desc | limit 20
```

Do not display `@message`: an audit event can carry the request body (a Secret's data).

**AdmissionPolicyViolation** (info). A binding in Warn+Audit flagged a request that was
admitted, or Pod Security's warn or audit mode did. In Phase 1 this is the whole point:
read the day's query, and for each `user.username` and `objectRef` decide whether the
object or the policy is wrong. Findings that repeat on every Argo CD refresh (P6 on the two
vendored operator ClusterRoles until T12-g has synced) keep it firing; that is expected, not
an incident. A binding's findings must be gone before it goes to Deny. Once a binding
denies, its refusals are AdmissionPolicyDenied's and this alert leaves that binding alone.

**AdmissionPolicyDenied** (warning). A Deny+Audit binding refused a request: an Argo CD
sync of a changed manifest, or a `kubectl`. The requester got the policy's message.
```bash
argocd app get <name> | head -40                                  # the refused object and the message
kubectl -n argocd get application <name> -o jsonpath='{.status.conditions}'
```
Fix the object in Git (the usual case: the message says what the policy wants). If the
policy is wrong, either set that binding back to audit through `admission-values.yaml`
(a reviewed PR, the regenerated rules, then your `terraform apply`), or, when a deploy is
blocked now, the fast path under **Break-glass** below. With server-side diff the app also
turns OutOfSync (`ArgoAppOutOfSync`); this alert names the policy minutes earlier.

**AdmissionPodDenied** (critical). A Pod, or what looks like one, was refused: by
`ryft-workloads-pods` or `ryft-workloads-pods-vault` (P2), `ryft-operator-reach` (P8) or `ryft-auth-env` (P5), the design's
step C class plus P5, or by Pod Security's enforce mode (live today, with or without the
chart). The check counter has no resource label, so a P5 or P8 refusal of a Secret or a Role
pages too. A Pod refused now means a node loss, a rollout or a scale-up cannot re-create it:
treat it as an outage in waiting.
```bash
kubectl get events -A --field-selector reason=FailedCreate --sort-by=.lastTimestamp | tail -20
kubectl get validatingadmissionpolicybindings -o custom-columns='NAME:.metadata.name,ACTIONS:.spec.validationActions'
```
The ReplicaSet's or StatefulSet's `FailedCreate` event carries the message; a Pod Security
refusal (`source: Pod Security`) names the namespace's level. If workloads are down and the
cause is not a quick fix in Git, drop the binding to Warn+Audit first (Break-glass, fast
path), then fix.

**AdmissionPolicyError** (critical when the binding refuses, warning under Warn+Audit). A
policy's CEL could not be evaluated (`error_type` is `compile_error`, `invalid_error` or
`out_of_budget`). Under a Deny binding with `failurePolicy: Fail` the request was refused;
under Warn+Audit it was admitted and the policy judged nothing. The cause is the
expression meeting an object shape it did not expect, so the fix is the chart, not the
object: for the critical one bring the binding to audit through the Break-glass fast path to
restore writes, then correct the expression (`admission-celtest` reproduces it) and apply.

**AdmissionBindingMissing** (critical). Fewer than 17 `ryft-*` bindings exist for 10 minutes
while bindings existed within the last day. A binding that is gone means its policy judges
nothing (silently open). Compare with what is live, and check that the metric is not the
blind one:
```bash
kubectl get validatingadmissionpolicybindings -o name | sort
kubectl -n monitoring get pods -l app.kubernetes.io/name=kube-state-metrics
```
Helm does not see out-of-band changes (a deleted binding is not a diff to it), so a plain
apply restores nothing. The restore is the replace under **Restore** below. All 12 gone with
the chart switched off on purpose (back to Phase 0) raises this for up to a day: silence it
in Grafana Alerting.

**AdmissionBindingNotDenying** (warning, after 10 minutes). A binding committed as deny has
no `Deny` while other bindings still do: a fast-path patch that was never undone, or a hand
edit. That binding is not protecting anything.
```bash
kubectl get validatingadmissionpolicybindings \
  -o custom-columns='NAME:.metadata.name,ACTIONS:.spec.validationActions'
```
Restore (below). If the rules were loaded before a step's Terraform apply (or the other way
round), it fires until both have happened.

**AdmissionBindingDrift** (warning, after 2 hours). The other mismatches between the live
actions and the committed ones: a deny binding without Audit, an audit binding with Deny
or without Warn or Audit. Same look, same restore.

**AdmissionBreakGlass** (warning, after 4 hours). No `ryft-*` binding has `Deny` while at
least one is committed as deny: the chart's break-glass (`admission_break_glass=true`) is on,
or every binding was patched. Nothing is refused. Planned maintenance ends with the same
apply and `admission_break_glass=false`:
```bash
terraform -chdir=infra/aws/kubernetes plan -target=helm_release.admission_policy -out=admission.tfplan -var='admission_break_glass=false'
terraform -chdir=infra/aws/kubernetes apply admission.tfplan
```

**AdmissionSignalsMissing / AdmissionScrapeDown** (warning). The API-server scrape or the
bindings scrape reports nothing for 15 minutes, or `up` is 0. The alerts above are blind
meanwhile. Not gated, so they also fire before the monitoring values are applied.
```bash
kubectl -n monitoring get pods
kubectl -n monitoring logs deploy/grafana-cloud-alloy-deployment --tail=100 | grep -i -E "apiserver|admission|remote_write"
```

**Break-glass** (fast path, yours only; the design's section 3 has the rest). Per
binding, takes effect at once; pause Argo CD first for an Argo-synced object:
```bash
kubectl patch validatingadmissionpolicybinding <binding> --type=merge -p '{"spec":{"validationActions":["Warn","Audit"]}}'
```
Expect `AdmissionBindingNotDenying` after 10 minutes if you forget; when every binding is
patched, `AdmissionBreakGlass` after 4 hours.

**Restore** (undo a patch, recreate a lost binding). Helm does not see out-of-band changes,
so a plain apply changes nothing; replace the release:
```bash
terraform -chdir=infra/aws/kubernetes plan -target=helm_release.admission_policy -replace='helm_release.admission_policy[0]' -out=admission.tfplan
terraform -chdir=infra/aws/kubernetes apply admission.tfplan
```
A replace uninstalls the release and installs it again: every policy and binding is gone for
a moment, so the cluster is unprotected (and with `Fail` policies and no bindings, nothing is
refused) until the install finishes. Do it in a quiet minute, not mid-incident. A release stuck
in `pending-upgrade`: `helm -n kube-system history admission-policy`, then `rollback`.

**Not built: who writes the admission objects.** The signals above say what the policies
decide; none says who changed a policy or binding (they are exempt from admission, RBAC
guards them). A CloudWatch metric filter and alarm on the audit stream would, in
`infra/aws` (your Terraform and your apply; this is a design note, not code in the repo).
Config to start from, with the principal a placeholder to fill from one audit event of
your own apply:
```hcl

  log_group_name = "/aws/eks/ryft-prod-euc1/cluster"

}

  namespace           = "RYFT/Admission"
  metric_name         = "AdmissionObjectWrites"
  statistic           = "Sum"
  period              = 300
  evaluation_periods  = 1
  threshold           = 0
  comparison_operator = "GreaterThanThreshold"
  treat_missing_data  = "notBreaching"

```
Restrict to the audit stream if the filter matches too much (the group also holds the
API server and authenticator logs, which are not JSON audit events and never match).

## Vault

One Vault (D207): **Vault Community Edition in the cluster** (namespace `vault`, three Raft
pods, `infra/aws/kubernetes/vault.tf`). HCP Vault Dedicated is gone (2026-11-10), and with it
the Vault namespaces, the dual write and the cutovers. `infra/vault` writes this Vault on every
apply (`infra/vault/README.md`), and every generated VaultConnection reads
`https://vault.vault.svc:8200`.

**The seal is Shamir by default** (D208, `vault_seal = "shamir"` in `infra/aws/kubernetes`).
The init splits the unseal key into five shares, and any three unseal a pod. **Every Vault pod
that starts stays sealed until you unseal it by hand**: after a node drain, an eviction, a
crash or a template roll (**A pod is sealed**). `vault_seal = "awskms"` is D189's auto-unseal,
one variable away (**The seal: Shamir or awskms**).

The Vault has no Ingress and no LoadBalancer. Every operator command below goes through
`kubectl port-forward` on your machine, with the CA from the Secret `vault/vault-ca` (only
`ca.crt`, never `vault-tls`, which holds the server's key). Every `kubectl` line names
`--context ryft-prod-euc1`: that is production.

**One session shell.** It exports `VAULT_ADDR` and `VAULT_CACERT` for the vault CLI, and
after the login `VAULT_TOKEN` (the admin token) and `TF_VAR_vault_k8s_token` (the terraform
token). infra/vault's Vault provider takes its address, CA file, TLS verification and token
from its own configuration, so those exports do not steer it. It still reads
`VAULT_NAMESPACE`, `VAULT_TLS_SERVER_NAME`, `VAULT_CAPATH`, `VAULT_CACERT_BYTES`, the
client-certificate variables and `VAULT_MAX_RETRIES` from the environment: the `unset` line
below clears them. No `TF_LOG` at `DEBUG` or above while a token is set.

**Where these commands run.** In a standalone terminal (Terminal.app or iTerm) with session
restore and scrollback saving off. Not in the VS Code integrated terminal (it restores
scrollback), not in tmux or screen with logging, and never through an agent's or assistant's
shell: init output, unseal keys, root and admin tokens pass through it.

```bash
# The session shell (each time). History off: unseal keys and tokens pass through it.
unset HISTFILE VAULT_TOKEN VAULT_NAMESPACE VAULT_SKIP_VERIFY VAULT_TLS_SERVER_NAME VAULT_CAPATH VAULT_CACERT_BYTES VAULT_CLIENT_CERT VAULT_CLIENT_KEY VAULT_MAX_RETRIES TF_VAR_vault_k8s_token TF_LOG
umask 077 && mkdir -p ~/.config/ryft
kubectl --context ryft-prod-euc1 -n vault get secret vault-ca -o jsonpath='{.data.ca\.crt}' | base64 -d > ~/.config/ryft/vault-ca.pem
openssl x509 -in ~/.config/ryft/vault-ca.pem -noout -subject -enddate   # the ryft-vault CA
export VAULT_ADDR=https://127.0.0.1:8200 VAULT_CACERT="$HOME/.config/ryft/vault-ca.pem"
kubectl --context ryft-prod-euc1 -n vault port-forward svc/vault-active 8200:8200 >/dev/null &   # once a pod is active (after the bootstrap's step 3)
```

### Bootstrap

Once, from a clean checkout of `main` (`git status` empty), with the Shamir seal (the
default; for `awskms` see **The seal: Shamir or awskms** first). Precondition: the Vault
add-on is applied with `vault_collector_peer = false`, and
`kubectl --context ryft-prod-euc1 -n vault get pods -o wide` shows `vault-0`, `vault-1` and
`vault-2` `Running`, `0/1` ready, in three zones. Uninitialised means not ready, by design
(D196). Nothing below goes into a chat, a PR or a log. Start the session shell above, but
without the `svc/vault-active` port-forward: before step 3 no pod is ready, so the Service
has no endpoint. Have the 1Password break-glass vault open and the two paper sheets at hand
(**Unseal keys**): the drill in step 10 needs every share before one leaves the house.

**1. All three uninitialised (G3).**
```bash
kubectl --context ryft-prod-euc1 -n vault port-forward pod/vault-0 8200:8200 >/dev/null &
kubectl --context ryft-prod-euc1 -n vault port-forward pod/vault-1 8201:8200 >/dev/null &
kubectl --context ryft-prod-euc1 -n vault port-forward pod/vault-2 8202:8200 >/dev/null &
for p in 8200 8201 8202; do vault status -address="https://127.0.0.1:$p" | grep -E 'Seal Type|Initialized|Sealed'; done
# each: Seal Type shamir, Initialized false, Sealed true
```
Any `Initialized true`: stop (G3). Wipe it. Delete the pods and their claims
(`kubectl --context ryft-prod-euc1 -n vault delete pvc data-vault-0 audit-vault-0 …` for all
three, then the pods), then the retained EBS volumes in the EC2 console. Before anything
else, find out who reached the pods: the EKS audit log for `pods/portforward` and
`pods/exec` in `vault`. `Seal Type awskms`: the add-on was applied with `vault_seal =
"awskms"`; stop and decide (**The seal: Shamir or awskms**) before an init.

**2. Init on vault-0.** Under Shamir these are the **unseal** keys: three of the five unseal
a pod, make a root token and rekey (**Unseal keys**).
```bash

```
Put each share where **Unseal keys** says, one at a time: the three for 1Password into
their own items (copy one, paste it, `pbcopy </dev/null`, the next), the two for paper
straight from the screen, never through the clipboard. Put the initial root token into its
own 1Password item too (so a closed terminal cannot strand the bootstrap; step 9 revokes it
and deletes the item), and into this shell (next line). Then clear the terminal and its
scrollback (⌘K).
```bash
read -rs VAULT_TOKEN && export VAULT_TOKEN      # paste the initial root token: not echoed, not in history
pbcopy </dev/null
```
The default is no PGP (D203). With hardware keys: `-pgp-keys=k1.asc,…,k5.asc
-root-token-pgp-key=k1.asc` instead.

**3. Unseal vault-0, then the joins.** Each `vault operator unseal` without an argument
prompts for one share, hidden: never put a share on the command line. Three prompts per pod,
any three shares.
```bash
vault operator unseal -address=https://127.0.0.1:8200        # three times: vault-0
vault status -address=https://127.0.0.1:8200                 # Initialized true, Sealed false, HA Mode active
```
`vault-1` and `vault-2` find the leader by `retry_join`, but under Shamir a node joins only
once it is unsealed with **the same shares** (that is how it proves it belongs to the
cluster). Unseal each, three prompts each:
```bash
vault operator unseal -address=https://127.0.0.1:8201        # three times: vault-1
vault operator unseal -address=https://127.0.0.1:8202        # three times: vault-2
vault operator raft list-peers -address=https://127.0.0.1:8200   # vault-0 leader, vault-1 and vault-2 follower, all Voter true
vault operator raft autopilot state -address=https://127.0.0.1:8200   # Healthy true, Failure Tolerance 1
kubectl --context ryft-prod-euc1 -n vault get pods -L vault-active   # all 1/1, one vault-active=true
```
A joining node that still says `Sealed true` after three shares, or is missing from
`list-peers`: **to verify** in kind is whether 2.2.1 wants the shares before or after its
`retry_join` reached the leader; wait a minute and unseal again. Never init vault-1 or
vault-2 (G3: a second init is a second cluster).

**4. Audit, before anything is written** (addendum 1.10, D198). There are two devices,
and Vault keeps serving while one of them records. The options are explicit, so a changed
default cannot switch raw logging on. A fresh Vault audits three request headers
(`correlation-id`, `x-correlation-id`, `user-agent`); they go, so that no request header
reaches the audit lines.
```bash
vault audit enable file file_path=/vault/audit/audit.log log_raw=false hmac_accessor=true format=json
vault audit enable -path=stdout file file_path=stdout log_raw=false hmac_accessor=true format=json
vault audit list -detailed                      # file/ and stdout/, log_raw false on both
vault delete sys/config/auditing/request-headers/correlation-id
vault delete sys/config/auditing/request-headers/x-correlation-id
vault delete sys/config/auditing/request-headers/user-agent
vault read sys/config/auditing/request-headers  # headers map[]
```
`stdout` goes to the node's container log, and from there by alloy-daemonset (namespace
`vault` only) to Grafana Cloud Logs for 14 days (D197). `log_raw=true` on either device
would hand every credential to a third party. If it ever happens, rotate everything
(Data protection (logs) → Vault). **To verify** in kind: that 2.2.1 still enables audit
devices over the API with these options, and that the three headers stay deleted after a
pod restart (step 5 shows it: run the `read` again then).

**5. A restart needs you** (the drill for every later one, **A pod is sealed**).
```bash
kubectl --context ryft-prod-euc1 -n vault delete pod vault-2       # its port-forward (8202) ends here
kubectl --context ryft-prod-euc1 -n vault wait --for=jsonpath='{.status.phase}'=Running pod/vault-2 --timeout=5m
kubectl --context ryft-prod-euc1 -n vault get pod vault-2          # 0/1: sealed, and not in the Raft quorum
vault operator raft autopilot state             # Failure Tolerance 0 while it is sealed
kubectl --context ryft-prod-euc1 -n vault port-forward pod/vault-2 8202:8200 >/dev/null &
vault operator unseal -address=https://127.0.0.1:8202        # three times
kubectl --context ryft-prod-euc1 -n vault wait --for=condition=Ready pod/vault-2 --timeout=5m
vault operator raft autopilot state             # Healthy true, Failure Tolerance 1 again
vault read sys/config/auditing/request-headers  # still headers map[]
```

**6. The policies and the token roles from git** (reviewed in `infra/vault/bootstrap/`,
checked at every plan by `bootstrap.tf` and held to an allowlist by `tests/vault.tftest.hcl`):
```bash
vault policy write admin     infra/vault/bootstrap/admin.hcl
vault policy write terraform infra/vault/bootstrap/terraform.hcl
vault write auth/token/roles/admin     @infra/vault/bootstrap/token-role-admin.json
vault write auth/token/roles/terraform @infra/vault/bootstrap/token-role-terraform.json
vault read auth/token/roles/admin               # allowed_policies [admin], orphan true, renewable false, explicit max 1h, bound cidrs [127.0.0.1/32]
```
Never attach a policy to an entity or a group (`identity/*`): `admin` comes from the token
role `admin` only, and every admin token is minted by a root token of a generate-root
session (**Login**), so revoking that token is the whole revocation.

**7. The first admin token** (D209), from the initial root token. An orphan: revoking the
root token in step 9 leaves it.
```bash
ADMIN="$(vault token create -role=admin -display-name=admin -field=token)"
VAULT_TOKEN="$ADMIN" vault token lookup | grep -E 'display_name|policies|ttl|renewable|bound_cidrs|orphan'   # token-admin, [admin default], ~1h, false, [127.0.0.1], true
```
*The loopback binding.* Both token roles bind their tokens to `127.0.0.1/32`, the address a
port-forward is believed to arrive from inside the pod.
- **Why it should hold.** The listener is `[::]:8200` with no `x_forwarded_for`, so Vault sees
  the peer address of the connection. containerd's port-forward is believed to dial
  `localhost` over tcp4 first, so that peer is `127.0.0.1`. A forwarded request after a
  step-down (to `svc/vault-active`, a new pod) still arrives from `127.0.0.1`. If it arrives
  as `::1` instead, both bindings fail. Each of these is **to verify** in kind.
- **How a mismatch shows.** The lookup above says `permission denied` or
  `request originated from invalid CIDR`. Later, the same can happen after a containerd or
  Kubernetes upgrade: the next session's admin token is refused the same way.
- **The fix** is one reviewed change to both role files: drop `token_bound_cidrs`, or set
  the address Vault reports. `tests/vault.tftest.hcl` pins the binding
  (`the_admin_policy_and_the_token_roles_hold_the_reviewed_shape`), so its asserts change in
  the same commit; then `vault write auth/token/roles/<name> @…` with a root token.
- **A wrong CIDR cannot lock you out.** The root token of step 2 (and later of a
  generate-root session) is not bound: repair with it, then mint the admin token again.

**8. What the terraform token can and cannot do.** It is admin-equivalent for its hour, not a
sandbox (`bootstrap/terraform.hcl.tftpl` has the reasoning). It reads every credential, and it
rewrites the policy of any role it manages (each service's, and `snapshot` of the snapshot
job's `vault-snapshot`), which a Kubernetes token for that role's service account then turns
into those rights. What it cannot do: write any other policy (`admin`, `terraform` or `default`
in any spelling), give a role any but its own policy, namespace and service account, re-type the auth mount or point it outside the cluster,
switch audit HMAC off on a tune, touch audit, seal, Raft, generate-root, an OIDC login,
identities or tokens, renew itself, outlive the admin token it is a child of, or be used
anywhere but through the port-forward. Mint one from the admin token and check:
```bash
TFTOK="$(VAULT_TOKEN="$ADMIN" vault token create -role=terraform -display-name=terraform -field=token)"
for p in sys/mounts/kv-api sys/mounts/kv-api/tune kv-api/data/config auth/kubernetes/role/api sys/policies/acl/api \
         sys/mounts/auth/kubernetes sys/mounts/auth/kubernetes/tune \
         sys/policies/acl/ADMIN sys/policies/acl/Terraform sys/policies/acl/Default "sys/policies/acl/admin " \
         sys/policies/acl/admin sys/policies/acl/Snapshot sys/policies/acl/other auth/kubernetes/role/other sys/mounts/kv-other \
         sys/audit/file sys/config/auditing/request-headers auth/oidc/config auth/oidc/role/admin \
         sys/storage/raft/snapshot sys/generate-root/attempt identity/entity auth/token/create; do
  printf '%-40s %s\n' "$p" "$(VAULT_TOKEN="$ADMIN" vault token capabilities "$TFTOK" "$p")"
done
# the first seven: their capabilities (sys/mounts/auth/kubernetes read only); every one after them: deny
VAULT_TOKEN="$ADMIN" vault token lookup "$TFTOK" | grep -E 'policies|renewable|ttl|bound_cidrs'   # [default terraform], false, ~1h, [127.0.0.1]
VAULT_TOKEN="$TFTOK" vault write auth/kubernetes/role/api token_policies=admin bound_service_account_names=api bound_service_account_namespaces=ryft-api   # must say: permission denied
```

### Login (a generate-root session)

There is no standing login (D209: no OIDC, no userpass, no kept root token). A session is:
three unseal shares make a root token, the root token makes one admin token (1 hour, an
orphan, `127.0.0.1` only) and is revoked at once, and the admin token makes the terraform
token when Terraform runs. In the session shell, with the `svc/vault-active` port-forward:
```bash
unset VAULT_TOKEN
vault operator generate-root -status            # Started false. If true: see below, never continue that attempt
OTP="$(vault operator generate-root -generate-otp)"
vault operator generate-root -init -otp="$OTP"  # prints the Nonce
vault operator generate-root -nonce=<nonce>     # three times: one share per prompt, hidden; the third prints the Encoded Token
read -rs ENC                                    # paste the Encoded Token: not echoed (useless without the OTP, but kept off the screen)
export VAULT_TOKEN="$(printf %s "$ENC" | vault operator generate-root -decode=- -otp="$OTP")"; unset ENC OTP
ADMIN="$(vault token create -role=admin -display-name=admin -field=token)"
vault token revoke -self                        # the root token, now
export VAULT_TOKEN="$ADMIN"; unset ADMIN; pbcopy </dev/null
vault token lookup | grep -E 'policies|ttl|bound_cidrs'   # [admin default], ~1h, [127.0.0.1]
```
The session ends with `vault token revoke -self` (the admin token, and with it any terraform
token it made) and `unset VAULT_TOKEN TF_VAR_vault_k8s_token`. It ends by itself after an
hour. **To verify** in kind: that 2.2.1 reads the encoded token from stdin with `-decode=-`
(otherwise paste it as `-decode=<encoded token>`: it is useless without the OTP).

- **An attempt is already in progress** (`-status` says Started true, or `-init` refuses):
  never type a share into it. Its OTP is someone else's, so your shares would make *their*
  root token. `vault operator generate-root -cancel`, start your own, and treat it as an
  incident: `sys/generate-root/attempt` is unauthenticated, so anyone with a path to 8200
  could have started it. Find out who (the audit stream, the EKS audit log for
  `pods/portforward` in `vault`).
- **A leader change during the attempt** (the port-forward ends) loses it: restart the
  port-forward, `-cancel`, start again.
- Every session is a root token in the audit stream (`auth_display_name="root"`), followed by
  one admin token: that is the expected pattern, and anything else is an incident.

**Alternatives** (each a decision recorded under D209 before it is used):
1. **A root token kept in 1Password.** Skip step 9's revocation, keep the initial root token
   in its 1Password item, and start a session with `read -rs VAULT_TOKEN` from it, then the
   admin token as above. Simpler and it never expires, but it is one standing credential that
   is everything, usable without any share; a leak is invisible until it is used.
2. **OIDC with a personal Google account, later.** The bootstrap files `oidc-*.json` are the
   Google Workspace version (`hd = ryftapp.de`) and are written nowhere. A personal account has
   no `hd` claim: a reviewed change of the files and their tests first
   (`infra/vault/README.md` → `bootstrap/`), then the login is additive; the generate-root
   session stays the break-glass path.

### Unseal keys

Under Shamir the five shares are the unseal key. Any three unseal a pod, make a root token
(**Login**) and rekey, so three shares plus a port-forward are full control of every RYFT
credential. They are also the only way to open the Raft data: every pod restart needs three,
and every snapshot opens only with the shares of the cluster that took it (**Disaster
recovery**). Fewer than three left: the next restarted pod stays sealed, and no snapshot
opens. Terraform state still rebuilds every value Terraform knows (a fresh Vault, then
`infra/vault` from state: hours, no credential lost; the data key is in state too).

**Custody** (D208, amends D203). One person holds them. D203 kept every place below the
threshold (two in 1Password, two and one on paper): with auto-unseal the shares were needed
only for break-glass, but under Shamir they are needed at every pod restart and at every
login, and that layout would make each of those a trip to a paper sheet. So:

- **Three in 1Password**, each in its own item of the break-glass vault (`RYFT Vault unseal
  1/5` …). The routine path: a restart or a login needs nothing but 1Password.
- **Two on paper**, one at home and one off site: the loss backup. One deleted or corrupted
  1Password item still leaves three (two items and a sheet).
- **The trade-off.** The 1Password account alone (its password, Secret Key and second factor)
  now holds a threshold: with cluster access it unseals and makes a root token. And losing the
  whole 1Password account leaves two shares, below the threshold: the Vault can then not be
  unsealed after its next restart, and the way back is a fresh Vault from Terraform state.
  D203's layout avoids both at the price of paper for every restart; it stays the choice if
  restarts are rare enough.
- **What one custodian protects against:** the loss or theft of one place (a sheet alone is
  below the threshold), and an attacker with cluster access but no shares (a restarted pod
  stays sealed for them, and generate-root needs three shares). **Not against:** the
  custodian's own 1Password account compromised together with cluster access; the custodian
  absent (nobody else can unseal: a restart while you are away leaves that pod sealed, a
  second one takes Vault down, and the workloads run on their synced Secrets until you are
  back); coercion; one person's mistake with no second pair of eyes. One custodian with a
  Shamir split is a backup scheme, not dual control.

Which share is where, and the off-site place, are recorded in the 1Password break-glass
vault, not in this public repository. Never record key material, a photo of it, or the map
anywhere else.

| Init date | Shares / threshold | Layout | PGP | Last verification |
| --- | --- | --- | --- | --- |
| (after the bootstrap) | 5 / 3 | 3 × 1Password, 2 × paper | no | (after the bootstrap) |

**Drill: yearly, and after every rekey.** Run a generate-root session (**Login**) twice, with
two different sets of three shares that together use all five. Revoke each root token at once.
Each run proves its shares and the audit path. Once the log rules exist (`VaultRootTokenUsed`,
group `ryft-vault-logs`, D199: a follow-up to PR 4, which needs `lokitool`), it must fire both
times; until then, find the two root logins in the `stdout` audit stream
(`{namespace="vault", stream="audit"} | json | auth_display_name="root"` once Vault's log
pipeline is on, OBSERVABILITY → Vault's logs). Update *Last verification*. Run it where all
shares are (the off-site sheet comes home for the drill, or the drill goes to it).

**A place is lost or exposed:** rekey the same day with three remaining shares, then
redistribute all five:
```bash
vault operator rekey -init -key-shares=5 -key-threshold=3
vault operator rekey -nonce=<nonce>             # three times, one share per prompt; the last prints the five new shares
```
The snapshots taken before the rekey still open with the **old** shares (30 days, then 7 for
the noncurrent version): keep the old set in its own 1Password item until the last of them
has expired, and if the old set was exposed, the bucket's access is the only guard for those
snapshots until then. Under `awskms` the shares are recovery keys: `-target=recovery` on both
lines.

### The seal: Shamir or awskms

`vault_seal` in `infra/aws/kubernetes` (D208). **`shamir`** (the default): no seal stanza, no
AWS identity for the server pods and no egress out of the cluster for them; every pod that
starts is unsealed by hand. **`awskms`** (D189): auto-unseal with `infra/aws`'s key
`alias/ryft-prod-euc1-vault-unseal` through the Pod Identity role of `vault/vault`; pods
unseal themselves, and the five shares become **recovery keys** (they unseal nothing, but
generate-root and rekey still take three). The key stays in `infra/aws` either way (about
$1 a month, no further cost with `awskms`), so the switch needs no `infra/aws` apply.

**Before the bootstrap**, switching is a variable and an apply: the init then prints
recovery keys (`vault operator init -recovery-shares=5 -recovery-threshold=3`), and steps 3
and 5 need no unseal. G1 blocks first (**Hard gates**).

**On an initialised Vault**, Shamir to `awskms` is a seal migration (**to verify** in kind
first, with 2.2.1):
1. G1 holds. Take a snapshot by hand (**Snapshots**).
2. `vault_seal = "awskms"` in `infra/aws/kubernetes/terraform.tfvars`, plan: the unseal Pod
   Identity role and association added (`module.vault_unseal_pod_identity`), the two Vault
   releases changed (the seal stanza, the server's KMS egress), nothing destroyed; anything
   else: stop. Apply. `OnDelete`: nothing restarts yet.
3. Each standby, one at a time: delete the pod, port-forward to it once it runs, and
   `vault operator unseal -migrate -address=https://127.0.0.1:8202` three times (the shares);
   wait for `1/1` and autopilot Healthy before the next.
4. The leader last: `vault operator step-down` (the admin token), restart the
   `svc/vault-active` port-forward, delete the old leader's pod, `unseal -migrate` three times
   on it.
5. `vault status` on each pod: `Seal Type awskms`, `Recovery Seal Type shamir`. Delete one
   standby and watch it come back `1/1` without you. Rename the 1Password items and the
   custody line to *recovery keys*; run the drill (**Unseal keys** → Drill).

Snapshots taken before the migration are expected to open only with the shares (as unseal
keys, in a drill without the KMS stanza), later ones only with the KMS key: **to verify** in
the restore drill right after the migration, with one of each. Back from `awskms` to Shamir is
not this variable alone: Vault's migration needs the seal stanza present with
`disabled = "true"` while the pods unseal with `-migrate` and the recovery keys, which is a
reviewed change of `infra/aws/kubernetes/vault.tf` first.

### Node maintenance

The PodDisruptionBudget `vault-server` (charts/vault-extras) keeps `minAvailable: 2` of 3 with
`unhealthyPodEvictionPolicy: AlwaysAllow` (D196). It counts **ready** pods: a drain never
takes a second ready pod, but a pod that is not ready can always be evicted. Under Shamir the
drained pod comes back sealed, so it is not ready, so the budget then blocks the next drain
until you have unsealed it: that is the guard against losing the quorum, and it means **node
maintenance only with the operator and the shares at hand**. A managed node-group update or
an AMI rollout left alone stalls on the second node and fails after 15 minutes
(`PodEvictionFailure`) instead of taking Vault down. So before any drain, node rotation or
node-group update:
```bash
kubectl --context ryft-prod-euc1 -n vault get pods -o wide -L vault-active                 # all three 1/1
kubectl --context ryft-prod-euc1 -n vault get sts vault -o jsonpath='{.status.updatedReplicas}/{.status.replicas}{"\n"}'   # 3/3
kubectl --context ryft-prod-euc1 -n vault get pdb vault-server                             # ALLOWED DISRUPTIONS 1
vault operator raft autopilot state                                                        # Healthy true, Failure Tolerance 1
```
- `updatedReplicas` below `replicas` means an unrolled template change. A drain recreates the
  pod from the **current** template: an unplanned upgrade in the middle of maintenance. Roll
  first (**Day 2**).
- One node at a time: when the pod is back `Running` and `0/1`, unseal it (**A pod is
  sealed**), and wait for `1/1` and autopilot Healthy before the next. A pod whose volume
  sits in the drained zone stays `Pending` until a node joins in that zone. That is expected.
- **Never `--force`** a drain or a managed node-group update on this cluster. It ignores
  Vault's and RabbitMQ's budgets. A pod that cannot be evicted for 15 minutes fails a node-group
  update (`PodEvictionFailure`). Find out why instead of forcing.

### A pod is sealed

Not ready (`0/1`), but alive. Liveness accepts sealed and uninitialised, so it is not
restarted. The `vault` Services skip it, and a sealed node takes no part in Raft: one sealed
pod costs the failure tolerance (0 until it is unsealed), not the service. Two sealed pods:
**Quorum loss**. `VaultSealed` pages.

**Under Shamir (the default) this is every restart**: a drain, an eviction, an OOM kill, a
node failure, a roll. Unseal it, three shares (**Unseal keys**), in the session shell:
```bash
kubectl --context ryft-prod-euc1 -n vault get pods -L vault-active,vault-sealed
kubectl --context ryft-prod-euc1 -n vault port-forward pod/vault-<n> 8202:8200 >/dev/null &
vault status -address=https://127.0.0.1:8202   # Seal Type shamir, Initialized true, Sealed true
vault operator unseal -address=https://127.0.0.1:8202        # three times, one share per prompt
kubectl --context ryft-prod-euc1 -n vault wait --for=condition=Ready pod/vault-<n> --timeout=5m
vault operator raft autopilot state             # Healthy true, Failure Tolerance 1
```
`Initialized false` on a pod that had data: its volume is new (**A lost volume**), never an
init. While a pod is sealed, the workloads keep running: VSO only syncs, and the Secrets
`ryft-secrets` it already wrote stay as they are (it does not delete a destination when Vault
is unreachable; it retries). What stops: rotations and new syncs, and with two sealed pods
every read.

**Under `awskms`** a sealed pod is a fault: it should unseal itself. The shares are recovery
keys there and cannot unseal it, so don't try.
```bash
kubectl --context ryft-prod-euc1 -n vault logs vault-<n> --tail=100 | grep -iE 'seal|kms|credential'
```
The cause is almost always KMS:
- the Pod Identity association `vault/vault` or its role;
- egress to KMS (NetworkPolicy `vault-server`, the NAT);
- the key disabled or its policy changed (CloudTrail: `Decrypt` by `ryft-prod-euc1-vault-unseal`).

Fix the cause, then delete the pod so that it starts and unseals again.

### The leader is gone

The active pod died or was deleted, and a standby wins the election within seconds (both
standbys unsealed: under Shamir a standby that is sealed cannot). The label
`vault-active=true` moves, and so does `svc/vault-active`. A port-forward to it ends (restart
it), and VSO reconnects on its own. Under Shamir the old leader comes back sealed: unseal it
(**A pod is sealed**).
```bash
kubectl --context ryft-prod-euc1 -n vault get pods -L vault-active   # exactly one true
vault operator raft list-peers                  # a leader; the old one follower (or unreachable until it is back)
```
If no pod is `vault-active=true` for more than a minute, there is no quorum (**Quorum loss**).

**Probe codes.** `/v1/sys/health` answers:

| Code | Meaning | Ready | Alive |
| --- | --- | --- | --- |
| 200 | active, or standby with `standbyok` | yes | yes |
| 429 | standby (without `standbyok`) | yes, via `standbyok` | yes |
| 501 | not initialised | no | yes |
| 503 | sealed | no | yes |
| 474 | a standby that cannot reach the active node (port 8201, NetworkPolicy, certificate, leader gone) | no | yes |
| 530 | a node removed from the Raft cluster (`remove-peer`) | no | yes |

On 474, check the peers' 8201 path and the leader. On 530, the node's data is stale: treat
it as **A lost volume**, but without the `remove-peer`, which already happened.

### Quorum loss

Two of three voters down: no leader, and nothing is read or written. Workloads keep their
Kubernetes Secrets and keep running, but nothing syncs or rotates. Under Shamir the usual
cause is two pods that restarted (two drains at once, a node-group update forced past the
budget, two nodes lost): they are back `Running` and sealed. Unseal both (**A pod is
sealed**): with two of three sealed the first unseal restores the quorum (two voters); with
all three sealed it is the second. Unseal the rest the same way. Under `awskms` the nodes or pods usually
come back and Raft recovers by itself with no action. Watch it with
`kubectl --context ryft-prod-euc1 -n vault get pods -o wide` and `list-peers` once a
leader exists.

If two volumes are gone for good, restore from a snapshot (**Disaster recovery**). The
alternative is Raft's manual recovery (`raft/peers.json` on the survivor, Vault's "Outage
recovery" tutorial). It is **to verify** in the kind drill before it is ever used here.

### A lost volume

One pod's data volume is gone (EBS volume lost, zone gone for good) or holds stale data
(530). The other two keep the quorum. Its node id (the pod name) is still a voter in the Raft
configuration, so the failure tolerance is 0 until it is replaced.

**First, close the collector's path.** The replacement pod starts with a fresh claim and is
**uninitialised** until `retry_join` has joined it to the cluster, which under Shamir
happens only when you unseal it with the cluster's shares. Until then it answers
`PUT /v1/sys/init` without a token (G3's risk) to anything that reaches its 8200. If that call
lands, the node forms a cluster of its own (under `awskms` it auto-unseals with the same key;
under Shamir whoever ran the init holds its shares and unseals it), is labelled
`vault-active` and joins the `vault-active` endpoints next to the real leader, splitting VSO's
and the snapshot job's logins between two Vaults. So, by default, set the peer off before you
start: `vault_collector_peer = false` in `infra/aws/kubernetes/terraform.tfvars`, plan (exactly
`1 to change`, `helm_release.vault_extras`, the NetworkPolicy `vault-server` loses the
collector rule; anything else: stop), apply. The server scrape fails until you turn it back on
(`VaultScrapeDown` may warn). This **narrows** the window, it does not close it: the host-network
`alloy-daemonset` reaches 8200 from its node's address whatever the variable says (Vault metrics
(once), step 2; to verify), and so does anything else on a node. Keep the steps below short.

Then, in the session shell (the `svc/vault-active` port-forward and the admin token, G3;
never `vault login` through `kubectl exec`):
```bash
vault operator raft list-peers                  # vault-<n> Voter, not reachable
vault operator raft remove-peer vault-<n>       # the admin token
kubectl --context ryft-prod-euc1 -n vault delete pvc data-vault-<n> --wait=false
kubectl --context ryft-prod-euc1 -n vault delete pod vault-<n>
kubectl --context ryft-prod-euc1 -n vault wait --for=jsonpath='{.status.phase}'=Running pod/vault-<n> --timeout=10m
kubectl --context ryft-prod-euc1 -n vault port-forward pod/vault-<n> 8202:8200 >/dev/null &
vault status -address=https://127.0.0.1:8202   # Initialized false, Sealed true: never init it
vault operator unseal -address=https://127.0.0.1:8202        # Shamir: three times, the cluster's shares (the join)
kubectl --context ryft-prod-euc1 -n vault wait --for=condition=Ready pod/vault-<n> --timeout=10m
```
The StatefulSet makes a fresh claim, and the pod joins by `retry_join` and receives the data
from the leader. **Two checks before anything else**, once the pod is Ready:
```bash
vault operator raft list-peers                  # vault-<n> back as a Voter of this cluster
kubectl --context ryft-prod-euc1 -n vault get endpoints vault-active -o jsonpath='{.subsets[*].addresses[*].ip}{"\n"}'
# exactly one address: the leader's
vault operator raft autopilot state             # Healthy true, Failure Tolerance 1
```
Both hold: put `vault_collector_peer = true` back (plan exactly `1 to change`, anything else:
stop; apply) and check that `up{job="ryft/vault"}` is 1 for all three pods again.

**Initialised alone** (`vault-<n>` missing from `list-peers`, or two addresses behind
`vault-active`, or the new pod reporting `Initialized true` with a cluster of its own on its
pod port-forward): treat it as G3, a compromise. In this order: first close the path (the peer
stays `false`; if you had kept it on, set it off now as above) and stop every other change;
then delete its claim and pod again (`kubectl --context ryft-prod-euc1 -n vault delete pvc data-vault-<n> --wait=false`,
then the pod) so that it rejoins the real cluster; then find out who reached it (the EKS
audit log for `pods/portforward` and `pods/exec` in `vault`, the node's connections) and
check VSO's and the snapshot job's logins of that period against the real Vault's audit
stream. Until it is understood, no secret is written.

Keep `audit-vault-<n>` unless it is lost too. gp3-encrypted retains the old EBS volume. It
holds only barrier-encrypted data, but delete it in the EC2 console once the pod is healthy.

### Snapshots

**What.** A Raft snapshot of the whole Vault every 6 hours (`17 */6 * * *` UTC; **RPO 6 h**):
every secret, mount, policy, auth method and role, the audit device configuration, the live
tokens. Vault encrypts it with its own keyring, which opens only after an unseal with the
unseal key of the cluster that took it: under Shamir three of **its** shares (**Unseal keys**;
a new init's shares do not open it), under `awskms` the key
`alias/ryft-prod-euc1-vault-unseal`. A snapshot without them is unreadable. S3 encrypts it a
second time with the snapshot key (`alias/ryft-prod-euc1-vault-snapshots`).

**How.** The CronJob `vault/vault-snapshot` (charts/vault-extras, D192). Its init container
(the server's image) logs in through Kubernetes auth with a projected token for audience
`vault` that lives 10 minutes, as the role **`vault-snapshot`** (bound to the service account
`vault/vault-snapshot`, audience `vault`, `token_ttl` = `token_max_ttl` = 10 minutes, no
default policy) with the policy **`snapshot`** (read on `sys/storage/raft/snapshot`, nothing
else). infra/vault creates both (`k8s.tf`); its first apply writes them. It saves the
snapshot from the active node (`vault-active`; a save through a standby is incomplete) and
checks it with `vault operator raft snapshot inspect`. The token is not revoked: without the
default policy it may not revoke itself, so it expires with its TTL. The upload container (the
AWS CLI, pinned by digest; P2 admits it only under the service account `vault-snapshot`) puts
it with one `aws s3api put-object` under the job's Pod Identity role (iam.tf
`vault_snapshot_pod_identity`: `s3:PutObject` under `snapshots/` and `kms:GenerateDataKey` on
the snapshot key through S3, nothing else; it cannot read, list or delete). The snapshot
lives in a memory-backed `emptyDir` (64 Mi) and is removed on every exit path, SIGTERM
included; a failed save removes its partial file.

**Where.** `s3://ryft-prod-euc1-vault-snapshots-<account>/snapshots/vault-<UTC time>.snap`
(eu-central-1), with the snapshot's SHA-256 twice: in its metadata (`x-amz-meta-sha256`, hex)
and as S3's own checksum (`ChecksumSHA256`, base64 of the same digest). The init container
hashes the snapshot between the save and the inspect; the upload sends that hash
(`--checksum-sha256`), so S3 stores the object only if the bytes it receives have it: what is in
the bucket is what was hashed and then inspected. Kept 30 days,
then the noncurrent version 7 more (infra/aws `vault.tf`). The bucket and both keys outlive
the cluster (`prevent_destroy`; the keys' policy denies deletion and disabling).

**Write conditions** (each enforced twice, by the request and by a policy):

| Condition | The job sends | Enforced by |
| --- | --- | --- |
| create-only: no overwrite of an existing snapshot | `--if-none-match '*'` (a put to an existing name answers `412`) | bucket policy `DenyPutWithoutIfNoneMatch` (no `If-None-Match` header: denied, for everyone; also blocks CopyObject and multipart parts) |
| the bucket belongs to this account | `--expected-bucket-owner <account>` | the role's `s3:ResourceAccount` condition |
| encrypted with the snapshot key, named by its full ARN | `--server-side-encryption aws:kms --ssekms-key-id <key ARN> --bucket-key-enabled` | bucket policy `DenyPutWithoutSnapshotKey` and the role's `s3:x-amz-server-side-encryption-aws-kms-key-id` condition |
| the data key only through S3, only for this bucket | (S3 asks KMS) | the role's `kms:ViaService = s3.eu-central-1.amazonaws.com` and `kms:EncryptionContext:aws:s3:arn = <bucket ARN>` |
| TLS | the CLI's default | bucket policy `DenyInsecureTransport` |

**List** (your AWS identity; the job's role cannot list):

```bash
terraform -chdir=infra/aws/kubernetes output -raw vault_snapshot_list_command   # prints the command
aws s3 ls s3://ryft-prod-euc1-vault-snapshots-<account>/snapshots/ --region eu-central-1 | tail -5
kubectl --context ryft-prod-euc1 -n vault get cronjob vault-snapshot   # LAST SCHEDULE, LAST SUCCESSFUL
kubectl --context ryft-prod-euc1 -n vault get jobs -l app.kubernetes.io/name=vault-snapshot
```

**The first snapshot** (right after the bootstrap and infra/vault's first apply, before `make alerts-apply`: a
precondition of the Vault alerts, Monitoring → Vault metrics (once)). Before the init every
scheduled run fails at the login (no role yet), and no alert fires then: no run has succeeded
and no pod is ready. That holds only until the init. Once a server is ready,
`VaultSnapshotFailing` warns 30 minutes after a failed run and `VaultSnapshotStale` pages
after 13 hours without a success; and until one run has succeeded, the alerts' "initialised"
gate rests on the pod labels alone, which lapse an hour after every pod restarts sealed. So
take the first one by hand right away:

```bash
kubectl --context ryft-prod-euc1 -n vault create job --from=cronjob/vault-snapshot vault-snapshot-first
kubectl --context ryft-prod-euc1 -n vault wait --for=condition=complete job/vault-snapshot-first --timeout=10m
kubectl --context ryft-prod-euc1 -n vault logs job/vault-snapshot-first -c snapshot   # "snapshot saved and inspected"
kubectl --context ryft-prod-euc1 -n vault logs job/vault-snapshot-first -c upload     # "snapshot uploaded", key and sha256
aws s3api head-object --bucket ryft-prod-euc1-vault-snapshots-<account> --key <key> --region eu-central-1 \
  --checksum-mode ENABLED \
  --query '{sse: ServerSideEncryption, key: SSEKMSKeyId, bucketKey: BucketKeyEnabled, sha256: Metadata.sha256, s3sha256: ChecksumSHA256}'
printf %s <sha256> | xxd -r -p | base64        # the hex digest as base64: must equal s3sha256
kubectl --context ryft-prod-euc1 -n vault get cronjob vault-snapshot -o jsonpath='{.status.lastSuccessfulTime}{"\n"}'
```

`sha256` (the metadata, hex, also in the upload's log line) and `s3sha256` (S3's checksum,
base64) are one digest in two encodings; the `printf` line converts the first into the second.

The last line must print a time: `create job --from` makes the CronJob the Job's owner, so the
controller records its success, and this status is what the snapshot alerts read (and one
half of their "initialised" gate). Empty: wait a minute and look again (the controller writes
it after the Job completes). Still empty: keep the Job, look at
`kubectl --context ryft-prod-euc1 -n vault describe cronjob vault-snapshot` (events), and
check that the next scheduled run sets it. Once it is set:
`kubectl --context ryft-prod-euc1 -n vault delete job vault-snapshot-first`.

`SSEKMSKeyId` must be the snapshot key's ARN (`aws kms describe-key --key-id alias/ryft-prod-euc1-vault-snapshots --region eu-central-1 --query KeyMetadata.Arn`).
Then prove both create-only rules once, with your own identity:

```bash
KEY_ARN="$(aws kms describe-key --key-id alias/ryft-prod-euc1-vault-snapshots --region eu-central-1 --query KeyMetadata.Arn --output text)"
B=ryft-prod-euc1-vault-snapshots-<account>
# 1. Without If-None-Match: must answer AccessDenied (the bucket policy). If it succeeds, the
#    policy is not applied: delete the object and apply infra/aws.
aws s3api put-object --bucket "$B" --key snapshots/policy-check --body /dev/null \
  --server-side-encryption aws:kms --ssekms-key-id "$KEY_ARN" --region eu-central-1
# 2. With it, twice: the first succeeds, the second must answer PreconditionFailed (412).
aws s3api put-object --bucket "$B" --key snapshots/policy-check-412 --body /dev/null --if-none-match '*' \
  --server-side-encryption aws:kms --ssekms-key-id "$KEY_ARN" --region eu-central-1
aws s3api put-object --bucket "$B" --key snapshots/policy-check-412 --body /dev/null --if-none-match '*' \
  --server-side-encryption aws:kms --ssekms-key-id "$KEY_ARN" --region eu-central-1
unset KEY_ARN B
```

The test object stays until the lifecycle expires it (30 days, then 7 for the version): the
job's role cannot delete, and neither should you need to. It is empty and named
`policy-check-412`, so nothing mistakes it for a snapshot.

**When a run fails** (`VaultSnapshotFailing`, then `VaultSnapshotStale` pages at 13 h):
`kubectl --context ryft-prod-euc1 -n vault logs job/<job> -c snapshot` (or `-c upload`).

| Message | Cause | Fix |
| --- | --- | --- |
| `permission denied` / `invalid role name` at `auth/kubernetes/login` | the role `vault-snapshot` is missing in Vault (infra/vault not applied yet), or its audience or bound service account differs | infra/vault's role (`k8s.tf`: audience `vault`, `vault/vault-snapshot`, policy `snapshot`); the baseline in Vault → Terraform through the port-forward |
| `permission denied` at `sys/storage/raft/snapshot` | the policy `snapshot` changed, or the role lost it | `vault policy read snapshot` (read on `sys/storage/raft/snapshot` only) |
| `connection refused` / `no such host` on `vault-active` | no active node (sealed, uninitialised) | VaultSealed / VaultNoActiveNode first |
| `incomplete snapshot, unable to read SHA256SUMS.sealed file` | the save reached a standby | `VAULT_ADDR` must be `vault-active` (the template) |
| `AccessDenied` on `PutObject` | a missing header (key ARN, `If-None-Match`), the wrong account, or no credentials (the pod started before the association: the next run gets them) | the upload log's request; `aws eks list-pod-identity-associations --cluster-name ryft-prod-euc1 --namespace vault --region eu-central-1` |
| `AccessDenied` mentioning `kms:Decrypt` | S3 asked for Decrypt when reusing the cached bucket key (not documented; the role holds GenerateDataKey only) | a reviewed PR adds `kms:Decrypt` with the same ViaService and context conditions to `vault_snapshot_policy_statements` |
| `BadDigest` | the bytes S3 received do not have the snapshot step's hash (`--checksum-sha256`): the file changed or broke after the init container hashed it, in the `emptyDir` or on the way | none; the next run takes a new snapshot. Repeated: the node's memory |
| `XAmzContentSHA256Mismatch` | the CLI signs the payload's hash before it sends (with a precomputed checksum it does not use the unsigned trailer): the file changed between that read and the send | as `BadDigest` |
| `no valid hash from the snapshot step` (upload log) | `/work/vault.snap.sha256` is missing, empty or not 64 lowercase hex characters (a Job made from an edited template; the chart's init container always writes it) | the snapshot log; the next run |
| `PreconditionFailed` (412) | an object of that name exists (two runs in one second) | none; the next run has a new name |
| Job `DeadlineExceeded` | the Job ran over 10 minutes (the NAT, S3, a slow save). `activeDeadlineSeconds` is the Job's: at the deadline the Job fails and no further retry starts | the Job's events (`kubectl --context ryft-prod-euc1 -n vault describe job <job>`); the next schedule tries again |
| Job `BackoffLimitExceeded` | three pods failed in a row (the first and two retries) | the logs of the last pod, as above |

### Disaster recovery

The way back when the cluster, or Vault's volumes, are gone. Order, each step done before the
next (the Terraform runs are yours):

1. **`infra/aws`**: the VPC, EKS, the unseal and snapshot keys and the bucket. The keys and
   the bucket normally survive (prevent_destroy, the keys' deny); a plan that wants to create
   them means they are gone, see *The unseal key or the shares are lost* below. Under Shamir
   the snapshot opens with the old cluster's shares, not with a key in AWS: have three of
   them at hand (**Unseal keys**) before you start.
2. **The collector peer off.** `vault_collector_peer = false` in
   `infra/aws/kubernetes/terraform.tfvars` **before** the next step: the new Vault comes up
   uninitialised, and `PUT /v1/sys/init` must reach nobody but you (Vault metrics (once),
   step 2). The same before every restore into a fresh, uninitialised cluster.
3. **`infra/aws/kubernetes`**: the add-ons, the Vault add-on among them. Vault comes up
   uninitialised (three pods running, 0/1 ready), the snapshot CronJob with it (its runs fail
   until step 4). Check G3 (Vault → Hard gates): `Initialized false` on all three before
   your init.
4. **Restore the latest snapshot** into the new Vault, in the session shell, with
   port-forwards to each pod (no pod is ready, so `vault-active` has no endpoint yet). Under
   Shamir (the default), a throwaway init on vault-0 only, then the restore, then the **old**
   shares:

   ```bash
   aws s3 ls s3://ryft-prod-euc1-vault-snapshots-<account>/snapshots/ --region eu-central-1 | tail -3
   aws s3 cp s3://ryft-prod-euc1-vault-snapshots-<account>/snapshots/<newest> ./vault.snap --region eu-central-1
   vault operator raft snapshot inspect vault.snap        # offline; a corrupt file fails here
   kubectl --context ryft-prod-euc1 -n vault port-forward pod/vault-0 8200:8200 >/dev/null &
   kubectl --context ryft-prod-euc1 -n vault port-forward pod/vault-1 8201:8200 >/dev/null &
   kubectl --context ryft-prod-euc1 -n vault port-forward pod/vault-2 8202:8200 >/dev/null &
   vault status                                            # Initialized false (G3), on 8201 and 8202 too
   vault operator init -key-shares=1 -key-threshold=1     # a throwaway unseal key and root token
   vault operator unseal                                   # once: the throwaway key
   read -rs VAULT_TOKEN && export VAULT_TOKEN              # the throwaway root token, not echoed
   vault operator raft snapshot restore -force vault.snap
   unset VAULT_TOKEN
   vault status                                            # Sealed true: the restored keyring wants the OLD shares
   vault operator unseal                                   # three times: three of the old cluster's shares
   vault status                                            # Sealed false, HA Mode active
   vault operator unseal -address=https://127.0.0.1:8201   # three times, old shares: vault-1 joins
   vault operator unseal -address=https://127.0.0.1:8202   # three times, old shares: vault-2 joins
   ```

   `-force` because the new cluster's keys differ from the snapshot's (without it:
   `could not verify hash file`). The snapshot brings back the old cluster's keyring, sealed by
   the old cluster's unseal key, so from now on only the **old** shares unseal it, and the
   old token roles and policies apply; the throwaway key and token are void (delete them from
   the screen and from wherever you noted them). **To verify** in the restore drill: whether
   vault-0 seals at once after the restore or only after a restart (`Sealed false` with the
   throwaway still working: delete pod vault-0 once and unseal it with the old shares). Never
   unseal vault-1 or vault-2 with the throwaway key: they would join the throwaway cluster.
   Under `awskms`: `vault operator init -recovery-shares=1 -recovery-threshold=1` instead and no
   unseal at all; the restored keyring is wrapped by the same KMS key, so Vault unseals as
   before, vault-1 and vault-2 join by themselves, and a node that stays sealed is deleted once
   (`kubectl --context ryft-prod-euc1 -n vault delete pod vault-N`). Either way: three voters
   in `vault operator raft list-peers`, then check `vault audit list -detailed`,
   `vault auth list`, `vault secrets list`. Then `rm vault.snap`: the file opens with the old
   shares (or the unseal key), so treat it as every secret. Your disk's encryption (FileVault)
   is what protects the deleted blocks; `shred` is no help on APFS (copy-on-write, SSD) and is
   not on stock macOS.
5. **The collector peer on again**: `vault_collector_peer = true`, plan (exactly `1 to change`,
   anything else: stop) and apply `infra/aws/kubernetes` (Vault metrics (once), step 2: the
   restored Vault is initialised, by your snapshot).
6. **The first snapshot by hand** (Snapshots → The first snapshot), right away. The rebuilt
   CronJob has no `lastSuccessfulTime`, so until a run succeeds the alerts' "initialised" gate
   rests on the pod labels alone, which lapse an hour after every pod restarts sealed.
7. **VSO syncs.** The restored Kubernetes auth reviews tokens as before (Vault's own service
   account, D187): `kubectl --context ryft-prod-euc1 get vaultstaticsecrets -A` shows each
   synced within its `refreshAfter`. A plan of `infra/vault` shows what changed after the
   snapshot (a rotated secret, a new service): apply it.
8. **Argo CD** syncs the workloads (app of apps); pods that started before their Secret
   existed are restarted by VSO's `rolloutRestartTargets`, or by hand.

RPO 6 h: secrets changed after the snapshot come back from step 7's plan (infra/vault holds
them in its variables), so nothing is lost that Terraform knows.

**The unseal key or the shares are lost** (under Shamir fewer than three shares left; under
`awskms` the key deleted after its 30-day window, which the key policy forbids, or the account
gone): no snapshot opens again, and under Shamir no pod that restarts unseals again. Initialise
a new Vault: Vault → Bootstrap from step 1, with the collector peer off as in step 2 above
(the shares and root token are the new bootstrap's). Then apply `infra/vault` from its state
(no import: the state still holds every `random_*`): it recreates the mounts, auth, roles and
policies and writes the KV values from its variables (`service_secrets` in
`terraform.tfvars`, the values Terraform state holds). Then steps 5 to 8, the first snapshot by
hand (step 6) included: the new CronJob has no success yet. Credentials that only lived in
Vault (none by design today) would be lost.

**Restore drill: yearly, and after every change** to the seal, the snapshot job, the Vault
version or the bucket's policies. Into kind on your machine, from the newest real snapshot:

1. `kind create cluster --name vault-drill`, then one Vault 2.2.1 (the pinned image) with Raft
   and a writable `/vault/audit` (the restored file audit device writes there). Under Shamir:
   no seal stanza, and three of production's shares at the machine. Under `awskms`:
   `seal "awskms"` naming the unseal key's ARN, with your own short-lived AWS credentials in
   the pod (`aws configure export-credentials --format env` into a Secret; if
   `vault_unseal_allowed_principal_arns` is set in infra/aws, your role must be on it).
2. Step 4's commands against it (download, inspect, init, `restore -force`, the unseal with
   production's shares under Shamir, `vault status`).
3. Pass: unsealed, `vault operator raft list-peers` answers, `vault audit list` and
   `vault secrets list` show production's mounts, and one `vault kv metadata get` of a service
   path has its versions. Note the date and the minutes it took in `docs/STATUS.md`.
4. `kind delete cluster --name vault-drill`, `rm vault.snap`, delete the credentials Secret's
   source file (FileVault protects what `rm` leaves on the disk). The drill held every
   production secret unsealed on your machine.

A CI variant with a synthetic snapshot (no production key) is test-engineer's ticket; it
proves the mechanics, not that production's snapshots open.

### When a synthetic alert fires

The checks run from outside every 5 minutes from two probes (OBSERVABILITY → Synthetic
Monitoring). First look, read-only; the `job` label names the check:

```bash
# what the probes see, the way they see it (no redirects followed)
curl -sI https://ryftapp.de/ | grep -iE "^HTTP|content-type"                                     # ryft-site-home: 200, text/html
curl -s https://ryftapp.de/privacy | grep -c 'Art. 9(2)(a) GDPR'                               # ryft-site-privacy: 1 or more
curl -sI https://ryftapp.de/.well-known/apple-app-site-association | grep -iE "^HTTP|content-type|location"   # ryft-site-aasa: 200, application/json, no location
curl -s https://ryftapp.de/.well-known/apple-app-site-association | grep -c 'M77SKHKG63.dev.timkrebs.ryft'    # 1 or more
curl -s -o /dev/null -D - https://www.ryftapp.de/ | grep -iE "^HTTP|location"                                    # ryft-site-www-redirect: 301, https://ryftapp.de/
echo | openssl s_client -connect ryftapp.de:443 -servername ryftapp.de 2>/dev/null | openssl x509 -noout -enddate   # the served certificate
# inside
kubectl -n argocd get applications ryft-platform
kubectl -n ryft-web get pods -l app=web -o wide
kubectl -n ryft-web get ingress,certificate
kubectl -n ryft-web logs -l app=web --tail=50
```

- **SiteDown, all `curl`s fine:** the probes' view differs from yours, so look at the check
  in Grafana (Synthetics → the check → the failed run's logs name the assertion that
  failed: status code, header or body regexp). A regexp that no longer matches after a web
  deploy is the usual cause: the privacy marker (`Art. 9(2)(a) GDPR`) after a policy
  revision, the AASA after an app ID change. If the page is right and the regexp is stale,
  fix `deploy/grafana/synthetics/ryftapp.json` and `make synthetics-apply`; if the page is
  wrong, roll back the web pin ("Deploy and roll back") and fix forward.
- **SiteDown, `curl` fails:** pods not ready or none (`get pods`), the Ingress or the
  Traefik service (`kubectl -n kube-system get pods -l app.kubernetes.io/name=traefik`), DNS (`dig +short ryftapp.de`, ExternalDNS
  in `infra/aws/kubernetes`), the certificate. The AASA wrong or missing means universal
  links and password AutoFill stop working for testers: treat it like a down site.
- **SiteProbeFlapping:** a single failed run is noise, which is why the rule needs two in
  30 minutes. Open the check, compare the probes, and look at the failed runs' reason: a
  timeout from one probe (its network), a 429 (the edge's rate limit in `overlays/eks/web.yaml`,
  20 requests/s per address; the probes send about 1 per minute each, so a 429 means
  something else is hitting the limit), a 5xx (one pod: `kubectl -n ryft-web logs <pod>`). If it recurs for days,
  replace the probe in the JSON.
- **SiteWwwRedirectBroken:** the `www-to-apex` Middleware (`overlays/eks/web.yaml`) and the
  Ingress' second host; the check wants 301 or 308 with `Location: https://ryftapp.de/`.
- **SiteCertificateExpiring:** `kubectl -n ryft-web describe certificate ryftapp-de-tls`
  and `get challenges,orders -n ryft-web` (DNS-01), cert-manager's log (the flow:
  "EKS", Certificates). A renewed certificate shows in the next run; Traefik may need a
  moment to pick up the secret.
- **SyntheticsMissing:** the `job` label names the check that stopped reporting (one alert
  per job; all four at once means Synthetic Monitoring itself). In the Synthetics app: is
  that check there and enabled, is the stack inside its execution limit. The apply (the
  subshell in "Monitoring (Grafana Cloud)", with a fresh token) recreates deleted checks.
  Until it is fixed that URL is unwatched: run the block above after every web deploy.

The block above uses GET where it matters: `curl -I` sends HEAD, and Traefik answers a HEAD
for `www` with 308 where a GET gets 301 (the check accepts both).

## Data protection (logs)

- **What is logged:** one access line per request (method, path, status, bytes,
  duration, route, request id, user id) and what the services decide: a sync's counts
  and device id, a training import's counts (`train import`: source, result, items per
  status, days), which day was scored by which model (`scored day`: `day`,
  `model_version`, `inputs_changed`), a push's category and day, errors with their
  cause. Paths carry dates and resource ids (`/v1/days/2026-10-19`,
  `/v1/workouts/<uuid>`), so the lines still show when someone used the app and which
  days they opened: personal data, read and kept as below.
- **Never logged:** health values (no score, sample, sleep or workout value, baseline,
  learned sleep need or readiness state, neither as a field nor in an error's text: a
  body that does not decode is named by its field and type, not by its value), request
  or response bodies, query strings, tokens (APNs device tokens too: a failed push's
  error does not quote its URL), the `Authorization` header, email addresses (the smoke
  user's too), device names, feedback messages and diagnostics, invite notes. Supabase's
  admin API errors are logged as the status and GoTrue's `error_code`, never the body.
- **Exceptions**, both from bugs and rare: a panic's stack trace (`debug.Stack()` in
  `httpx.Recover`) shows the arguments of the calls on it as hex words, and pgx's error
  for an argument it cannot encode (an int64 too large for an `int4` column) quotes that
  argument. Fixing the bug needs both; read such lines as health data.
- **Tests pin it:** `TestEngineLogsNoHealthValues` (scoring at debug level, every
  line's keys allowlisted), `TestSyncLogsCountsOnly` and
  `TestSyncErrorPathsLogNoHealthData` (ingest), `TestWritesLogNoBodies`,
  `TestErrorPathsLogNoBodies` and `TestTrainImportLogsCountsOnly` (api), `TestSyncStripsNULBeforeTheDatabase` and
  `TestWritesRefuseNULBeforeTheDatabase` (a NUL removed, or refused with `422`/`400`,
  logs no text), `TestDecodeErrorsQuoteNoValues` (events), `TestJSONErrorDropsTheValue`
  (logx), `TestTransportErrorsHideTheDeviceToken` (apns), `TestAdminErrorsHoldNoBody`
  (auth). A new line on the paths they run fails them until its keys are listed there.
  - **Value kinds:** each allowed key also has a kind of value, pinned by the test-only
    package `internal/logx/logcheck` (a depguard rule keeps production code from importing
    it): UUIDs for user, request and device ids, `YYYY-MM-DD` for days, closed enums for
    category, code, gate, method, level, service and model version, booleans for flags,
    non-negative integers for counts (bounded where a bound is known: `request_ids` at most
    20, rescored days at most `MaxRangeDays`), an integer 100 to 599 for a status, RFC 3339
    for the time. A float, a score or a string under a count key fails; so does a key that
    appears twice on a line (`encoding/json` keeps the last, and logx appends `user_id` and
    the request's keys after the call site's, so a duplicate would hide one). The known
    values of each test (recovery, readiness, device tokens, the seeded samples) are
    scanned for in the raw line. `TestSyncLogKindsRejectMutations`,
    `TestWriteLogKindsRejectMutations`, `TestImportLogKindsRejectMutations`, `TestEngineLogKindsRejectMutations` and
    `TestNotifyLogKindsRejectMutations` feed the checker synthetic lines (a float under
    `applied`, a score under a renamed key, a non-UUID `user_id`, a duplicate key, …) and
    require a problem that names the mutated key; `TestNotifyLogsNoHealthValuesOrTokens`
    pins the notify service's lines.
  - **Third-party errors:** the admin (GoTrue), Sign in with Apple and APNs errors that are
    logged or shown hold the response's status code with the standard phrase
    (`logx.StatusLine`, never `resp.Status`, whose text is the server's), and from the body
    only a bare code: `error_code` / `error` as `[a-z_0-9]{1,64}`, an APNs `reason` as
    letters only (else "no error code" / "unrecognised"); an undecodable GoTrue body is a
    fixed "undecodable response". The AMQP URL is logged redacted.
  - **Accepted gaps:** an integer health value under an integer count key (`samples`,
    `days`, `bytes`) passes by type; only a known bound or the test's known values catch
    it. `err` is free text up to 1 KiB (including pgx's "unable to encode" quote of an
    argument, see above), covered only by the scans for the values a test knows.
    `client_request_id` accepts what httpx accepts (`[A-Za-z0-9._:-]{1,128}`, the
    contract of `X-Request-ID`), digits and dots included. The lines of the amqpbus and
    events panic paths, of auth, httpx and the account, admin and train handlers, and of
    `cmd/notify`'s stale-check loop have no key test yet.
- **Older lines:** before this change `scored day` carried the day's scores and inputs
  (readiness, state, recovery, strain, sleep, nap, sleep need, HRV, resting HR), a
  failed push's error the device token (`refresh push`, `sync stale` and the broker's
  retry lines), and a `bad event` line the number it could not decode, which the dead
  letter's `Ryft-Error` header kept as well. CloudWatch and the dead-letter queues keep
  14 days, so all of it is gone 14 days after the deploy of this change (the first
  `deploy: images` PR after it merged; `docs/STATUS.md` has the date).
- **A rescore by hand** (`scripts/rescore_all.sh`: `kubectl exec … /app rescore`)
  prints to the operator's terminal, not to the pod's log, so none of it reaches
  CloudWatch; its `scored day` lines hold no values now. Output saved from a run before
  this change holds every day's scores: delete it.
- **Where and how long:** stdout of each pod (on the node until the pod goes); CloudWatch
  Logs (Fluent Bit ships the `ryft-*` namespaces), **14 days**, encrypted with a key only
  `/ryft/*` groups may use (`infra/aws/kubernetes/logs.tf`, D52). **Not in Grafana
  Cloud** (the user's decision, 2026-10-21): `ryft-.*` is excluded from pod-log
  collection in Fleet Management, so Grafana Labs receives the services' metrics only
  (counters and route labels, no user data), and the privacy text names it for that. Check
  in Grafana → Explore → Loki that `{namespace=~"ryft-.*"}` returns nothing.
- **Who can read them:** the AWS account's administrators (CloudWatch, `kubectl logs`).
  Nobody else.
- **Vault (the Vault in the cluster, namespace `vault`; D197, D198):** the one exception
  that goes to Grafana Cloud. The server log (JSON, `info`) and the `stdout` audit device
  go from the node's container log to the stack's hosted Logs (alloy-daemonset, namespace
  `vault` only), **14 days**. The complete local record is `/vault/audit/audit.log` on each
  pod's audit volume. No app user's data passes through Vault. Values, including the demo
  and smoke users' emails, are HMAC'd in every audit line (`log_raw=false`,
  `hmac_accessor=true`, set explicitly at the bootstrap). Paths and key names are system
  data. The only personal data is the operator's, and only indirectly: there is no OIDC
  login (D209), so no line carries a name, an email or an external subject. A session shows
  as a root token (`auth_display_name="root"`), then one admin token (`token-admin`), and the
  time and accessor of each admin action; one person holds the shares, so those lines are
  that person's. **Who reads it:** the stack's members, Grafana
  Labs (processor, UK), Fleet's remote config, and in the cluster anyone with `pods/log` in
  `vault` (argocd-server's ClusterRole included, D180). `log_raw=true` on either device
  would hand every credential to Grafana Labs in clear. If it happens, rotate every
  credential and ask for deletion through Loki's delete API. The same holds for a mount or
  auth method tuned with `audit_non_hmac_request_keys` or `audit_non_hmac_response_keys`:
  that field's values then reach both devices in clear. The policy terraform refuses those
  keys on a tune, and the post-apply baseline (OPERATIONS → Vault → Terraform through the
  port-forward) reads every mount's tune back.

## Backups

**Supabase (EKS).** The database is Supabase's, and so are the backups: Database →
Backups. **The free plan keeps none and pauses a project after a week without
activity**, so the project moves to **Pro** before the first tester's data arrives: daily
backups kept 7 days; point-in-time recovery is an add-on (worth it once losing a day of
syncs matters more than its price; the app re-uploads only what HealthKit still holds).
There is no dump job in the cluster. Before restoring a backup:

1. In the SQL editor, run `SELECT * FROM deleted_users` and download the result as CSV.
   Accounts deleted after the backup was taken would otherwise come back.
2. Restore in the dashboard.
3. Insert the tombstones back: SQL editor → import the CSV into a temporary table,
   then `INSERT INTO deleted_users SELECT * FROM <tmp> ON CONFLICT (id) DO NOTHING`.
4. `argocd app sync ryft-platform` to run the migrate hook again, which sets the role
   passwords in case the backup predates them. The api's deletion reconciler erases the restored
   accounts at start-up.

**Restore drill, monthly** (Pro): restore the latest backup into a new scratch project
(Database → Backups → *Restore to a new project*). Then:

1. Compare `SELECT count(*)` of `users`, `samples` and `daily_scores` with production.
2. Run the services against it and smoke them: the compose stack in Supabase mode with
   the scratch project's pooler URL (`DATABASE_URL`, its `postgres` user) and project ref,
   then `make smoke-supabase` with the scratch project's `SUPABASE_URL` and anon key and
   the smoke user (restored with the backup, auth included):

   ```bash
   AUTH_MODE=supabase SUPABASE_PROJECT_REF=<scratch ref> DATABASE_URL='postgres://postgres.<scratch ref>:…@aws-…pooler.supabase.com:5432/postgres?sslmode=require' make up
   SUPABASE_URL=https://<scratch ref>.supabase.co SUPABASE_ANON_KEY=… SMOKE_EMAIL=… SMOKE_PASSWORD=… make smoke-supabase
   ```
3. Note the date and how long the restore took in `STATUS.md`, then delete the scratch
   project and `make down`: it holds real health data.

**In-cluster Postgres (`local-postgres`).** `pg-backup` in `ryft-postgres` runs
`pg_dump --format=custom` nightly at 03:30 Europe/Berlin into the `pg-backups` PVC
(10 Gi) and deletes dumps older than 14 days. Files are named
`ryft-YYYYMMDDTHHMMSSZ.dump`; a dump is written as `.partial` and renamed when complete.

```bash
kubectl -n ryft-postgres create job --from=cronjob/pg-backup pg-backup-manual   # back up now
kubectl -n ryft-postgres logs job/pg-backup-manual                              # lists /backups
```

The PVC lives in the cluster, often on the same disk as Postgres. Copy dumps off it:
`kubectl -n ryft-postgres cp pg-restore:/backups/<file> ./<file>`, using the restore pod
below.

### Restore (local-postgres)

Verified against the compose stack: restoring into an empty database and over an
existing one both reproduce every row. Dumps hold the `public` schema only, so they also
restore into Supabase. Restoring a plain-Postgres database into Supabase needs the RLS
step from `SUPABASE.md`, and then the migrate job. Accounts deleted after the dump was
taken come back with it, so keep the current tombstones across the restore (steps 2b
and 3b).

```bash
# 1. stop writers (HPA does not scale a Deployment that is at 0)
for s in api ingest scoring; do kubectl -n ryft-$s scale deploy/$s --replicas=0; done

# 2. a pod with the backups mounted, allowed to reach Postgres (label app: pg-backup)
kubectl apply -f - <<'EOF'
apiVersion: v1
kind: Pod
metadata: { name: pg-restore, namespace: ryft-postgres, labels: { app: pg-backup } }
spec:
  restartPolicy: Never
  automountServiceAccountToken: false
  securityContext: { runAsNonRoot: true, runAsUser: 70, runAsGroup: 70, fsGroup: 70, seccompProfile: { type: RuntimeDefault } }
  containers:
    - name: restore
      image: postgres:17-alpine
      command: ["sleep", "3600"]
      securityContext: { allowPrivilegeEscalation: false, capabilities: { drop: [ALL] } }
      env:
        - name: DATABASE_URL
          valueFrom: { secretKeyRef: { name: ryft-secrets, key: DATABASE_URL } }
      volumeMounts: [{ name: backups, mountPath: /backups }]
  volumes:
    - name: backups
      persistentVolumeClaim: { claimName: pg-backups }
EOF
kubectl -n ryft-postgres wait --for=condition=Ready pod/pg-restore
kubectl -n ryft-postgres exec pg-restore -- ls -lh /backups

# 2b. save the current tombstones (deleted accounts)
kubectl -n ryft-postgres exec pg-restore -- sh -c 'psql "$DATABASE_URL" -c "\copy deleted_users TO /tmp/tombstones.csv CSV"'

# 3. restore (drops and recreates every object in the dump)
kubectl -n ryft-postgres exec pg-restore -- sh -c 'pg_restore --clean --if-exists --no-owner -d "$DATABASE_URL" /backups/ryft-20261018T013000Z.dump'

# 3b. put the tombstones back
kubectl -n ryft-postgres exec pg-restore -- sh -c 'psql "$DATABASE_URL" -v ON_ERROR_STOP=1 \
  -c "CREATE TEMP TABLE t (LIKE deleted_users)" -c "\copy t FROM /tmp/tombstones.csv CSV" \
  -c "INSERT INTO deleted_users SELECT * FROM t ON CONFLICT (id) DO UPDATE SET auth_deleted_at = COALESCE(deleted_users.auth_deleted_at, EXCLUDED.auth_deleted_at)"'

# 4. clean up; re-run migrate (grants and role passwords), restart; the HPAs take api/ingest back to 2
kubectl -n ryft-postgres delete pod pg-restore
make k8s-apply-local KUBE_CONTEXT=<context>
for s in api ingest scoring; do kubectl -n ryft-$s scale deploy/$s --replicas=1; done
```

To restore a dump from your machine instead, run
`kubectl -n ryft-postgres cp ./ryft-….dump pg-restore:/backups/` before step 3. The PVC
must have room.

## Upgrading

From the scaffold: api and ingest no longer set `replicas` (the HPA owns it). Because the
old manifest did, the first `kubectl apply` drops the field and the Deployments briefly
fall back to 1 replica until the HPA scales them to 2 — harmless, but expect it.

Migrations run in the migrate job before the services (they wait for it; advisory lock,
so two migrate runs at once are safe).
New columns on `daily_scores` (readiness, sleep detail, strain detail, baselines) are
filled when a day is scored (`steps` and `active_kcal` too), and source
de-duplication (`SCORING.md`) changes strain and sleep for anyone with two devices. Rescore history once after upgrading to this
version:

```bash
curl -fsS -X POST https://<host>/v1/recompute -H "Authorization: Bearer $ACCESS_TOKEN" \
  -H 'Content-Type: application/json' \
  -d "{\"from\":\"$(date -v-90d +%F 2>/dev/null || date -d '-90 days' +%F)\",\"to\":\"$(date +%F)\"}"
```
