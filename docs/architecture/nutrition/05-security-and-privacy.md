# Security and privacy

| Data | Purpose | Access and retention |
| --- | --- | --- |
| Shared catalog | Find foods and establish nutrient provenance | Available through gated, authenticated API reads. The importer or operator changes provider-sourced rows. |
| Private foods and submissions | Private food logging and optional moderation referral | Owner-scoped with no direct Data API grant. Until account deletion. Pending moderation records stay private. |
| Meals, snapshots, goals | Logging, review and daily totals | Owner-scoped with account deletion cascades. Meal deletion removes contents and keeps only the opaque retry ID until account deletion. Goal revisions support history. |
| CGM readings | Estimate meal-related glucose impact | Account-only access through scoped transactions. The caller can erase readings independently of meals. Account deletion cascades. |
| Raw source dumps | Reproducible ingest | Operator-staged public datasets. Temporary downloads are removed. Artifacts and source metadata carry their licenses. |

Nutrition uses the normal API authentication, App Attest and rate limits. Product routes also use beta admission. Repo predicates use the verified account. Nutrition RLS is enabled on plain PostgreSQL and Supabase. Each transaction sets its account scope using transaction-local configuration and the scope disappears at commit or rollback. The `ryft_api` role cannot write a shared food, set approval metadata or access import jobs. Ordinary Supabase Data API roles have no schema grant. A compromised API runtime could still set a different account scope, so the API role remains a trusted service boundary. The search function is a narrow schema-owner exception for PostgreSQL index selection. It returns only compact matches, requires a transaction account and applies the owner predicate inside the function. The scheduled Python importer uses the `ryft_nutrition_etl` role for public catalog operations. Admin catalog tools and migrations use separate operator access.

The existing account deletion path removes Nutrition tables by foreign key cascade. Admin account merge refuses the source when either Nutrition flag is active for it or it holds Nutrition records. After withdrawal, current-consent checks stop new health uploads and score processing. Authenticated meal, CGM and profile erasure routes remain available to owners independent of Nutrition flags, subject to standard admission. `GET /v1/me/nutrition-export` returns only the owner's meal and item snapshots with a bounded cursor and no cache. Export remains available after consent withdrawal or loss of a Nutrition flag or beta access. It leaves other account data to the reviewed account rights process, including private foods, goal history, CGM, optional weight samples and derived insights. Product rollout still needs a policy for retention periods, item-level erasure beyond meal deletion, and recovery or purge from backups. [Meal export contract](../../API.md#nutrition)

Search terms and barcodes travel in bodies. Application logs use route templates and generic database errors and omit free text, photos, payloads and private object IDs. Hosted request logs and edge rules still need staging verification for retention and URL metadata, particularly meal UUIDs and date ranges. Database logging must avoid parameter values and failing-row details for Nutrition writes. Access logs, database logs and data export are independent surfaces.

## Private Storage design

Use distinct private Supabase buckets for meal photos and short-lived label/OCR inputs. Bind a server-generated UUID to the caller, purpose and expiry before issuing an upload authorization. Object keys use the account UUID and an unguessable asset UUID. Validate allowed MIME and size at signing, verify magic bytes and decode within resource limits before promotion, strip EXIF metadata, and use short-lived signed reads only after an ownership check. The authorization service, image worker and deletion process should have scoped credentials. Keep uploads pending until validated. Reconcile expired upload intents and unreferenced objects, clean assets after meal/account deletion, and cover pending and signed links in two-account tests. Record the post-deletion URL expiry bound in policy. Provisioning the buckets, signed upload and read flows, retention timers and storage ownership tests are release work for the photo phase.

## GDPR and rollout

Treat meal patterns and derived health associations as sensitive personal data. Confirm the Article 6 lawful basis and, where data concerns health, an Article 9 condition with counsel. Confirm transparency, purpose limitation, access, withdrawal, erasure, portability, data retention and whether a DPIA is required under Article 35. Existing infrastructure docs place the database in Frankfurt and Cloud Run in Belgium. Confirm Storage, backups, log regions, subprocessors and any transfers before rollout. The Nutrition flag stays dark pending the policy update and staging review. [GDPR, EUR-Lex](https://eur-lex.europa.eu/eli/reg/2016/679/oj/), [RYFT Supabase configuration](../../SUPABASE.md)
